Abstract

Press brake sheet metal bending is an important manufacturing process, but robotic
implementations often still require manual programming. Operators define motion
sequences, teach waypoints, and adapt programs for each new workpiece, which
increases effort and limits flexibility.
This thesis presents an automated planning system for robotic press brake bending.
The approach combines workpiece orientation determination, constraint-based grip
planning, automatic regrip handling, and trajectory generation in a modular pipeline
driven by geometric input and configuration data. The system generates robot
programs without manual waypoint definition and includes validation steps for safe
and feasible execution.
Evaluation in a virtual simulation environment covers varying workpiece dimensions,
arbitrary initial orientations, regripping, and opposite-face bending. The results
show executable robot programs and reduced programming effort compared with
manual programming, supporting adaptable press brake automation for flexible
manufacturing.

Keywords: robotic press brake bending; automatic robot program generation; grip
planning; regrip planning; trajectory generation; flexible manufacturing.

1 Introduction

1.1   Background and Motivation

Sheet metal bending on press brake machines is a common manufacturing process
for producing functional sheet metal parts [1], [2]. In such processes, the bend se-
quence, tooling conditions, workpiece handling, and collision constraints are closely
connected. When a robot is added to the press brake cell, the planning task be-
comes more demanding because grasp positions, repositions, and robot motion
plans must also be considered [1], [2]. Although robotic systems can reduce direct
manual handling, programming these systems still requires considerable engineer-
ing effort, especially when robot motions and process steps have to be adapted for
new parts [3], [4].
In conventional robotic bending workflows, engineers often still define key poses,
motion sequences, and process logic for each workpiece. This becomes inefficient
when the sheet geometry, initial placement, or required bending sequence changes,
because the robot program may need to be adjusted, checked, or recreated before
execution [1], [2], [3].
The increasing need for flexible manufacturing highlights the importance of reducing
manual intervention in robot programming. For robotic press brake bending, this
means that program generation, grip selection, regripping decisions, and motion
validation should be handled in a more systematic way. The motivation of this
thesis is therefore to investigate how an automated planning pipeline can support
faster and more repeatable preparation of robotic bending tasks [1], [3].


1.2   Problem Statement

Despite the use of robots in press brake bending, many workflows still depend
on manually defined motion sequences and process logic. This creates high pro-
gramming effort and makes the result strongly dependent on the experience of the
programmer [3], [4].
A further limitation is the lack of automatic adaptation to changes in workpiece po-
sition, orientation, or geometry. In robotic bending, such changes influence grasp
feasibility, reachability, collision conditions, and the required bending sequence.
Without automated planning support, these changes often lead to manual adjust-
ments and reduced flexibility [1], [2].
Regripping and multi-stage bending are especially difficult because they require
coordinated decisions about where the workpiece is held, when it must be repo-
sitioned, and whether the next bend remains reachable. If these decisions are
predefined manually, the system becomes harder to adapt to new workpieces or



                                                                                   1
process sequences [1], [2].
These limitations indicate the need for a systematic and automated approach that
can generate robot programs dynamically while checking feasibility, safety, and
consistency before execution.


1.3   Research Objectives

The primary objective of this thesis is to develop an automated system for robotic
press brake bending that reduces manual programming effort while improving
adaptability to varying workpiece conditions. The proposed approach aims to make
the preparation of robotic bending tasks more structured by reducing operator
intervention and by introducing systematic decision-making within the planning
pipeline.
To achieve this objective, several specific goals are defined. First, the system is
designed to automatically generate robot programs based on geometric input pa-
rameters, reducing the need for manual motion definition. In addition, the system
enables adaptive handling of workpiece variations, including changes in position,
orientation, and geometry.
A key aspect of the work is the integration of multiple planning components into a
unified framework. These components include orientation determination, grip plan-
ning, regrip handling, and trajectory generation, all of which are essential for en-
suring feasible and continuous execution of the bending process. Furthermore, the
system incorporates structured validation mechanisms to ensure safe and collision-
free operation during program execution.
Finally, the overall objective is to reduce operator dependency while maintaining
consistent and repeatable system behaviour. By automating critical planning tasks,
the proposed solution aims to support more flexible robotic bending workflows.


1.4   Scope of Work

This thesis focuses on the development and evaluation of an automated planning
system for robotic press brake bending within a virtual simulation environment. The
primary scope of the work is limited to the generation of robot programs and the
validation of their execution feasibility using simulated data, without direct imple-
mentation on a physical robotic system.
The system is developed using a collaborative industrial robot from the Universal
Robots family. This platform is selected because its payload, reach, repeatability,
and available communication interfaces are suitable for developing and testing a
structured robotic handling workflow in simulation [5].
The implementation is tailored to sheet metal bending tasks with defined geometric
properties, allowing for controlled evaluation of the proposed planning approach.
However, the work does not aim to address all possible industrial variations or com-



                                                                                   2
plex multi-process workflows, such as highly customised production scenarios or
integration with additional manufacturing processes.
Furthermore, the evaluation is conducted entirely in a simulation environment, fo-
cusing on functional validation, feasibility assessment, and performance analysis.
While this approach enables systematic testing and development, it does not in-
clude experimental validation on a physical robotic system, which is considered
outside the scope of this thesis and a potential direction for future work.


1.5      Methodology Overview

The proposed solution follows a structured methodology that combines concept eval-
uation, modular system design, and systematic validation. The overall approach
is designed to ensure that the developed system meets both functional and non-
functional requirements while supporting reliable automated robot program gener-
ation.
Initially, multiple solution concepts are analysed and compared based on a set of
defined evaluation criteria. These criteria include the ability to support automated
program generation, as well as the extent to which each concept satisfies the iden-
tified functional requirements, non-functional requirements, and software design
constraints. Based on this evaluation, the most suitable concept is selected for
further development.
The selected concept is then implemented as a modular planning pipeline, consist-
ing of distinct components responsible for orientation determination, grip planning,
regrip handling, and trajectory generation. This modular structure enables clear
separation of responsibilities and facilitates scalability, maintainability, and future
extensions of the system.
To support robust system behaviour, the architecture is designed using a layered ap-
proach, ensuring that different levels of functionality are logically separated. Valida-
tion mechanisms are integrated at multiple stages within the pipeline to guarantee
safe, consistent, and feasible execution of the generated robot programs.
Finally, the system is evaluated through a series of test scenarios to assess its
functional correctness, performance, and adaptability to varying input conditions.
A comparison with conventional manual programming approaches is conducted
to quantify improvements in programming efficiency and execution time, thereby
demonstrating the effectiveness of the proposed methodology.

2 State of the Art and Literature Review

2.1   Fundamentals of Industrial Robotics

Industrial robots are a central part of modern manufacturing because they combine
repeatability, precision, and the ability to perform physically demanding operations
over long production cycles. The international standard ISO 8373 describes an in-
dustrial robot as a reprogrammable and multipurpose manipulator with three or
more programmable axes [6]. In practice, such systems are used for handling,
assembly, welding, forming, and many other operations in which stable and repeat-
able motion is required.
A typical industrial robot consists of several actuated joints that provide the degrees
of freedom (DOF) needed to position and orient an end-effector in three-dimensional
space. The task-relevant reference point is usually defined by the Tool Center Point
(TCP), which links the robot motion to the physical tool or gripper. Forward and
inverse kinematics describe the relationship between joint variables and the Carte-
sian pose of this reference point, forming the basis for motion planning and robot
control [7].
Robot programming can be understood as a spectrum of abstraction levels. At the
lower end, the operator or programmer explicitly defines poses, trajectories, and
process sequences. At higher levels, the user specifies the intended task, while the
system derives executable actions and motion commands. Industrial practice still
relies heavily on manual and offline programming, but research has increasingly
moved toward higher levels of abstraction, including task-level programming and
skill-based approaches that reduce the need for detailed low-level motion specifica-
tion [3], [8].
This shift is especially important for manufacturing tasks that are not simple rep-
etitions of a fixed motion. In applications such as robotic sheet metal bending,
the robot must handle changing workpiece geometry, limited workspace, tool ac-
cess constraints, and possible reorientation steps. These characteristics make the
task more demanding than conventional pick-and-place operations and motivate the
need for a broader review of robot programming methods, press brake automation,
and integrated planning approaches.


2.2   Sheet Metal Bending and Press Brake Systems

Sheet metal bending is a forming process in which a flat metal sheet is plastically
deformed along one or more bend lines. In a press brake, the sheet is positioned
between a punch and a die, and the bending result depends on tool geometry,
material properties, sheet thickness, bend sequence, and applied force [9]. The



                                                                                     5
process is common in industrial production because it can create a wide range of
functional parts from relatively simple sheet blanks.
Figure 2.1 illustrates a typical robotic press brake setup, where an industrial robot
is integrated with the bending machine to automate handling operations.




Figure 2.1: Robotic press brake bending system with integrated robot handling (Source:
[10]).

In automated press brake cells, the robot usually picks the flat sheet, positions
it at the tooling, supports it during bending, reorients it between process steps,
and unloads the final component. This automation can improve repeatability and
reduce direct operator involvement, particularly in repetitive production settings
[2]. However, the process is difficult to automate fully because each bend changes
the physical shape of the part.


2.2.1   Process Characteristics and Automation Challenges

The changing geometry of the workpiece is one of the defining characteristics of
sheet metal bending. A motion that is feasible before one bend may become infea-
sible after the sheet has been formed, because the part envelope, tool accessibility,
and collision conditions have changed. Process planning must therefore consider
the bend sequence, the accessibility of the tooling, and the handling strategy to-
gether rather than as isolated decisions [1].
For robotic handling, these process characteristics lead to several practical chal-
lenges. The robot must maintain a stable grasp, avoid collisions with the press brake
and the partially formed workpiece, remain inside its reachable workspace, and pre-
serve a suitable orientation for the next operation. In many cases, a single grasp is
not sufficient for the full bending sequence, so the workpiece must be placed down
and grasped again in a different configuration. These issues are introduced here



                                                                                    6
as process-level constraints; the detailed planning problems of regripping, grasp
selection, and trajectory generation are discussed later in Section 2.6.


2.3     Manual and Teach Pendant Programming

Manual programming with teach pendants is one of the most established methods
for programming industrial robots. In this approach, an operator defines the robot
motion by jogging the robot to desired positions or by entering Cartesian or joint
coordinates. The resulting positions are stored as waypoints and executed in a
defined sequence by the robot controller [11].
Figure 2.2 illustrates a typical teach pendant interface used for manual robot pro-
gramming.




Figure 2.2: Teach pendant interface for manual robot programming (Source: own work).

Teach pendant programming remains useful because it gives the operator direct
control over the robot and allows immediate verification of individual motions. For
stable, repetitive, and well-known tasks, this can be a practical and reliable method.
Its limitations become more visible when the process requires many coordinated
motions or frequent adaptation to new workpieces.


2.3.1    Limitations of Manual Programming

The main limitation of manual programming is the amount of expert effort required.
The operator must understand the robot coordinate system, tool frame, reachabil-
ity limits, process constraints, and possible collision situations. As the number of
waypoints grows, the programming task becomes slower and more dependent on
individual experience.
Manual programming is also poorly suited to frequent product changes. If the ge-
ometry of the workpiece changes, the robot program often has to be adapted or
recreated, even when the process logic remains similar. This makes manual pro-
gramming inefficient for flexible manufacturing environments with high part vari-
ation [3]. In addition, reachability, collision avoidance, and path quality are not




                                                                                    7
automatically guaranteed; they must be checked and corrected by the program-
mer.


2.3.2    Challenges in Complex Manipulation Tasks

Robotic sheet metal bending exposes these limitations clearly. The task is not a
single transfer motion, but a sequence of handling, positioning, bending, reorienta-
tion, and possibly regripping steps. The operator must anticipate how the sheet will
change after each bend and must define motions that remain feasible throughout
the process.
Regripping is particularly difficult to program manually because it requires coordina-
tion between placement, release, new grasp selection, and the next bending oper-
ation. Small changes in part dimensions or bend order can alter the required inter-
mediate positions. As a result, manual programming can become time-consuming,
difficult to reuse, and vulnerable to inconsistent decisions between operators.


2.3.3    Transition Towards Automated Programming

The limitations of manual programming have encouraged the development of meth-
ods that raise the level of abstraction. Instead of manually defining every pose,
engineers increasingly use virtual commissioning, offline programming, task-level
programming, and rule-based planning to reduce direct interaction with the robot.
These approaches do not remove all engineering effort, but they shift part of the
work from manual waypoint teaching toward model-based planning and validation.


2.4     Offline Programming Approaches for Industrial Robots

Offline programming (OLP) enables robot programs to be prepared and tested in a
virtual environment before they are executed on the physical robot. In contrast to
teach pendant programming, OLP decouples programming from production, allow-
ing engineers to develop, simulate, and validate robot tasks without occupying the
real workcell [3].
Figure 2.3 illustrates an offline programming environment, where a virtual model of
the robot, tooling, and workcell is used to simulate and validate motion trajectories.
OLP systems commonly use geometric models of the robot, tooling, fixtures, and
surrounding equipment. These models allow engineers to evaluate reachability,
motion paths, and possible collisions before deployment. In this way, offline pro-
gramming can reduce floor trial-and-error and support earlier detection of workcell
or path problems before production is interrupted [3], [12].


2.4.1    Digital Twin and Simulation-Based Programming

Digital twin concepts extend simulation-based programming by linking the virtual
representation more closely to the physical system. A digital twin can support mon-


                                                                                    8
Figure 2.3: Offline robot programming environment with CAD-based simulation (Source:
[12]).


itoring, validation, and adjustment by combining model-based simulation with data
from the real process. In manufacturing, digital twin approaches have been dis-
cussed as an important element of smart production systems because they support
analysis, synchronisation, and cyber-physical integration [13].
In industrial robotics, tools such as RoboDK, ABB RobotStudio, KUKA.Sim, and
drag&bot provide virtual environments for programming and validation. They sup-
port tasks such as visualising the workcell, checking reachability, identifying colli-
sions, and generating executable robot code. These capabilities make simulation-
based programming valuable for complex cells where direct trial-and-error program-
ming would be slow or risky.


2.4.2   Limitations of Offline Programming

Despite these advantages, offline programming does not automatically solve the
programming problem. The quality of the generated program depends strongly on
the accuracy of the virtual model. Differences between the simulated workcell and
the real cell can lead to deviations during execution, requiring calibration or manual
correction.
Another limitation is that many OLP tools still require the engineer to define the task
sequence, waypoints, and process logic manually. The software can validate and
simulate a program, but it does not necessarily decide which grasp to use, when
to regrip, or how to generate a complete strategy for a changing workpiece. This
limits the usefulness of conventional OLP for processes such as robotic sheet metal
bending, where the task geometry and constraints evolve during execution.

2.5     Automatic Robot Program Generation and Rule-Based Ap-
        proaches

Automatic robot program generation aims to reduce the need for manual waypoint
definition by deriving robot actions from task descriptions, process parameters, ge-
ometric input, or formal rules. Instead of programming every motion explicitly,
the system computes feasible actions based on the available information and the
constraints of the process.


2.5.1    Task-Level Programming and Abstraction

Task-level programming is based on the idea that users should describe what the
robot should achieve, while the system determines how the task can be executed.
Early work on robot programming introduced abstraction layers and symbolic task
descriptions as a way to separate task intent from low-level robot motion [14].
More recent approaches use skills, motion primitives, and reusable task modules. A
skill may represent an operation such as approaching, grasping, placing, or moving
along a constrained path. By combining such skills, complex robot programs can be
assembled in a more modular way [8]. This improves reusability, but the system
still needs reliable mechanisms for selecting valid actions and checking whether the
resulting motion is feasible.


2.5.2    Rule-Based and Constraint-Based Planning

In structured industrial environments, automatic program generation is often im-
plemented through rules and constraints. Rules may describe how a workpiece
should be approached, which orientations are allowed, when a regrip is necessary,
or which motion types should be used. Constraint-based planning extends this idea
by explicitly evaluating geometric, kinematic, and process-related conditions before
selecting a solution.
Such methods are attractive because they can produce deterministic behaviour in
well-defined applications. However, when product variants and process constraints
increase, the engineering effort required to define, adapt, and validate these rules
also increases. In robotic sheet metal bending, this issue is especially relevant
because bend sequencing, tooling, grasp selection, and robot motion planning are
closely coupled [1], [3].
For complex manipulation tasks, the main challenge is not only to generate iso-
lated decisions, but to coordinate several planning components. Grasp planning,
regrip planning, trajectory generation, reachability checking, and collision avoid-
ance influence each other. If these components are developed separately, a locally
valid decision may still lead to an infeasible overall process. Robotic manipulation
research therefore emphasizes the importance of integrated planning frameworks,
especially when grasping and motion constraints are tightly coupled [15].

2.6     Robotic Sheet Metal Bending Systems

Robotic sheet metal bending systems combine an industrial manipulator with a press
brake to automate the handling and positioning of sheet metal parts. The robot
transfers the sheet, aligns it with the tooling, supports it during bending, and pre-
pares it for subsequent process steps. This integration can improve repeatability
and reduce direct manual handling, but it also creates a planning problem that is
more complex than ordinary material transfer.
Figure 2.4 illustrates a typical robotic bending setup, where the robot operates
in coordination with the press brake to execute a sequence of manipulation and
forming operations.




Figure 2.4: Robotic sheet metal bending system with integrated robot and press brake
(Source: [4]).

The process usually starts with a flat sheet, but after every bend the shape of
the workpiece changes. This affects collision boundaries, grasp accessibility, tool
clearance, and reachable robot configurations. Research on robotic bending has
therefore shown that successful automation depends on coordinating process plan-
ning with robot motion planning [1]. The following subsections discuss the main
planning aspects that are relevant for this thesis.


2.6.1    Regrip Planning in Sheet Metal Bending

Regripping is often necessary when the robot cannot execute all bending steps with
a single grasp. The required orientation for later bends may conflict with the initial
grasp, or the formed geometry may make the original grasp unsuitable. In such
cases, the robot places the workpiece at an intermediate location, releases it, and
grasps it again in a new configuration.
From a robotics perspective, regrasp planning can be formulated as a search over
feasible grasps and transitions between them. A valid sequence must consider
grasp stability, reachability, collision avoidance, and the availability of intermediate
placements [16]. In industrial bending cells, however, regripping is often handled


                                                                                     11
through predefined sequences or manually designed rules. This can be reliable for
known parts, but it reduces flexibility when the workpiece geometry or bend order
changes.


2.6.2   Challenges of Regrip Integration in Industrial Systems

The difficulty of regripping is not limited to selecting a new grasp. A regrip decision
affects the following trajectory, the accessibility of the next bend, and the risk of
collision with both the workpiece and the press brake. Therefore, regrip planning
cannot be treated independently from motion planning. In robotic press brake
process planning, tooling, grasping, and moving are coupled planning tasks, so a
valid bending strategy has to be checked across the process sequence rather than
at one isolated step [1].
In many existing workflows, grasp selection, regrip decisions, and trajectory valida-
tion are performed as separate steps. This separation can create practical problems:
a grasp may be stable but unreachable, a regrip pose may be geometrically valid but
difficult to approach, or a trajectory may become infeasible after the part has been
bent. These dependencies show why integrated planning is important for scalable
robotic bending.


2.6.3   Grasp Planning for Sheet Metal Handling

Sheet metal parts are challenging to handle because they are thin, often large
relative to their thickness, and may deform or slip if the grasp is poorly chosen.
Vacuum grippers are widely used because they can hold flat sheet surfaces without
requiring mechanical clamping around the part. Their performance depends on
suction cup placement, contact quality, available holding force, and the distribution
of loads during motion [17].
General grasp planning methods consider object geometry, contact conditions, and
task constraints when selecting stable grasp configurations [15]. In sheet metal
bending, the selected grasp must also leave the bend line and tool access region
free. A grasp that is suitable for picking the flat sheet may interfere with a later
bending operation, especially after the workpiece geometry has changed. As a
result, grasp planning must be linked to the process sequence and not only to the
initial sheet geometry.


2.6.4   Trajectory Planning in Robotic Bending Systems

Trajectory planning in robotic bending must produce motions that are collision-free,
reachable, and compatible with the process constraints. The robot operates close
to the punch, die, workpiece, and other cell components, leaving limited room for
large avoidance motions. At the same time, it must maintain a suitable orientation
so that the sheet can be positioned accurately at the tooling.




                                                                                    12
Classical trajectory generation methods provide useful foundations for creating
smooth and continuous robot motions [18]. However, robotic bending introduces
additional constraints because the workpiece geometry changes during the process.
The planner must account for evolving collision conditions, workspace limits, possi-
ble singularities, and the need to coordinate motion with grasp and regrip decisions
[1]. In many industrial systems, these challenges are handled by conservative
motion templates or manually defined waypoints, which improves reliability but
limits adaptability.


2.6.5    Limitations of Existing Robotic Bending Systems

Existing robotic bending systems have demonstrated that press brake automation
is technically feasible, but several limitations remain. Many systems rely on pre-
defined handling strategies and carefully engineered programs. This makes them
effective for stable production scenarios, but less suitable for flexible environments
where part geometry and process requirements change frequently.
A central limitation is the separation of planning tasks. Grasp planning, regrip plan-
ning, trajectory generation, and process validation are often treated as separate
activities. This can produce fragmented workflows in which a decision that is valid
in one module creates problems in another. For example, a selected grasp may be
stable but unsuitable for the next trajectory, or a manually defined path may work
for one part variant but fail when the geometry changes.
Another limitation is the continued dependence on expert intervention. Even when
simulation and offline programming tools are available, engineers commonly define
motion sequences, check reachability, adjust waypoints, and validate process logic
manually. This increases setup time and makes adaptation to new parts more diffi-
cult. These limitations point toward the need for a unified approach that can com-
bine constraint-aware planning, automated trajectory generation, and structured
execution.


2.7     Industrial Software Platforms and System Implementations

Industrial robot applications are commonly developed with software platforms
that support programming, simulation, validation, and execution. These platforms
bridge the gap between theoretical planning methods and practical deployment by
giving engineers structured tools for building and testing robotic workflows.


2.7.1    Simulation and Offline Programming Environments

Simulation and offline programming environments allow robot programs to be pre-
pared, simulated, and generated before they are executed in the physical cell. They
can support reachability checks, collision evaluation, motion visualisation, and the
generation of controller-specific robot code, although the exact capability depends



                                                                                   13
on the software platform [3], [12]. These capabilities reduce commissioning risk
and make it easier to identify errors before production is interrupted.
Nevertheless, such environments are usually not fully automatic planning systems.
They provide powerful tools for validation and development, but the user often
remains responsible for defining the task sequence, selecting key poses, and con-
figuring the logic that connects individual operations. For complex manipulation
processes, this manual configuration remains a significant part of the engineering
effort.


2.7.2     Graphical Programming and Integrated Execution Systems

Graphical programming platforms such as drag&bot further reduce the barrier to
robot programming by allowing users to assemble workflows from modular function
blocks [19]. Such systems can combine user interaction, robot communication,
and runtime execution in one environment. They are useful for implementing and
operating robotic applications without requiring extensive low-level programming.
At the same time, graphical execution systems usually depend on workflows and
logic that are defined by the user. They can execute and monitor a process, but they
do not inherently solve the planning problem of deciding where to grasp, when to
regrip, or how to generate a complete trajectory sequence for a changing workpiece.
This distinction is important for robotic bending, where the main difficulty lies in
coordinating several dependent planning decisions.


2.7.3     Relevance to This Thesis

Existing industrial platforms provide a useful foundation for simulation, communi-
cation, and execution. Their limitation is not that they lack practical value, but that
they still leave much of the task strategy to the engineer. For press brake bending,
this means that grasp selection, regrip handling, and trajectory generation often
remain manually configured or only partially automated.
The approach developed in this thesis builds on the strengths of such platforms
while adding an automated planning layer. The aim is not to replace industrial exe-
cution environments, but to reduce the amount of manual task definition required
for robotic bending. By generating and validating motion-relevant decisions within
a structured pipeline, the system can use existing runtime tools while improving
adaptability to changing workpiece conditions.


2.8     Research Gap and Motivation

The literature shows a clear development from manual robot programming toward
simulation-supported and partially automated methods. Manual programming re-
mains reliable for stable tasks, but it does not scale well when workpiece geometry
changes frequently. Offline programming improves safety and commissioning ef-



                                                                                    14
ficiency, yet it still depends on user-defined task sequences and accurate virtual
models. Automatic programming and rule-based methods reduce manual effort
further, but many approaches focus on individual decisions rather than on the com-
plete bending workflow.
In robotic sheet metal bending, this separation is a major obstacle. The workpiece
changes shape after each bend, and this affects grasp feasibility, regrip require-
ments, collision conditions, and reachable trajectories. A planning decision cannot
be evaluated properly if it is isolated from the rest of the process. A grasp that is
acceptable at one stage may block tool access later; a regrip pose may be geomet-
rically possible but difficult to reach; a trajectory may be smooth in isolation but
unsuitable once the formed part is attached to the robot.
The resulting research gap is the lack of a practically deployable workflow that inte-
grates grasp planning, regrip planning, and constraint-aware trajectory generation
for robotic press brake bending. Existing methods and tools provide important foun-
dations, but they do not sufficiently address these interdependent planning tasks
as one coordinated process under workspace, kinematic, and process constraints.
Addressing this gap is important for flexible automation. A system that can gener-
ate valid target poses, evaluate process constraints, and transform these decisions
into executable robot motions can reduce engineering effort and improve adaptabil-
ity. This thesis therefore proposes an integrated and constraint-aware approach in
which automated trajectory generation, workspace-aware planning, and determin-
istic execution are combined within a structured pipeline.
The identified gap and the proposed direction form the basis for the concept devel-
opment presented in the following chapter.

3 System Concept and Methodology

3.1   Problem Definition and Objectives

Industrial robots are already used in press brake sheet metal bending, but in many
cases they are still programmed manually or through predefined routines. Those
approaches work well as long as part geometry, pickup conditions, and bend se-
quences remain stable.     Their limitations become much more visible in flexible
production environments, where frequent part variation leads to repeated manual
adjustment, longer setup times, and reduced efficiency.
The main technical challenge comes from the changing geometry of the workpiece.
After each bending operation, the shape of the part changes, and that change af-
fects robot reachability, grip feasibility, valid grip locations, and the set of trajec-
tories that can still be executed safely. Handling and regripping therefore cannot
be treated as isolated steps. They have to be planned in relation to the full pro-
cess sequence, which makes robotic bending difficult to scale when programming
is performed largely by hand.
From a methodological perspective, conventional robot programming still operates
at a relatively low level of abstraction. Paths, tool settings, and waypoints are
defined explicitly, which ties the resulting program closely to one specific robot
setup, one grip configuration, and one process sequence. Programs created in this
way are difficult to adapt when reorientation or regripping becomes necessary, and
they scale poorly in manufacturing settings that require frequent adjustment [3].
Research has already explored higher-level programming approaches that bring
planning and motion execution closer together. Even so, these ideas have not been
transferred fully into press brake bending scenarios in which changing workpiece ge-
ometry and handling conditions must be considered explicitly. A clear gap therefore
remains between general robot-programming research and a practical workflow for
robotic sheet metal bending.
Based on these observations, the central problem addressed in this thesis can be
stated as follows:
There is no systematic method for automatically generating robot programs for
press brake sheet metal bending that explicitly considers changing workpiece geom-
etry, handling feasibility, and regripping requirements while also reducing manual
programming effort.
The main objective of this thesis is therefore to enable the automatic generation
of robot programs for sheet metal handling and bending operations in a way that
reduces manual effort and improves adaptability to varying workpiece geometries.
To address this objective, this work develops a conceptual and methodological
framework that brings bending, handling, regripping, and orientation management



                                                                                    16
together in one workflow. The intention is to generate robot trajectories and exe-
cution logic automatically from process inputs, without relying on manually defined
waypoint sequences.
The specific objectives of this work are:

   • Develop a method for the automatic generation of robot programs based on
      workpiece geometry and process parameters.

   • Generate feasible robot trajectories while considering geometric, kinematic,
      and workspace constraints.

   • Support multi-stage bending operations, including reorientation and regripping
      of the workpiece.

   • Develop a method for determining feasible grip points based on geometry,
      accessibility, and process stage.

   • Enable integration with an industrial robot programming environment through
      a communication interface.

   • Reduce manual programming effort while ensuring consistent and reliable sys-
      tem behaviour.

The proposed approach is evaluated in a virtual simulation environment compatible
with industrial robot systems. Accordingly, the scope of this thesis is limited to
conceptual development and simulation-based validation.

The system concept developed in this thesis is guided by a defined set of require-
ments derived directly from the problem outlined in Section 3.1. These require-
ments specify the expected functionality, describe the intended system behaviour,
and make the operational boundaries explicit.
To keep the development process transparent, the requirements are organised into
functional, non-functional, system-level, and software-specific categories.   This
structure supports consistent design, implementation, and validation and also
makes later traceability easier to establish.


3.2.1    Functional Requirements

The functional requirements define the capabilities that the system must provide in
order to generate robot programs automatically for sheet metal bending operations.
In practical terms, they describe how the system processes input data, produces
robot motion, and maintains feasibility over several stages of the bending process.
The most important requirement is the automatic generation of robot programs
from operator-defined inputs. This directly addresses the limitations of manual



                                                                                17
programming identified in the previous chapters and forms the core of the proposed
solution.
Meeting that requirement involves more than creating a nominal path. The system
has to generate feasible robot trajectories for handling and bending operations on
the basis of target poses and process parameters, and those trajectories must sat-
isfy the relevant geometric and kinematic constraints within the defined workspace.
Because the shape of the sheet changes after each bending step, the system must
also support multi-stage processes that include reorientation and regripping. Grip
points cannot be fixed once at the beginning of the process; they have to be deter-
mined according to the current process stage, accessibility, and workpiece state so
that stable handling remains possible throughout the sequence.
All generated motions must also be validated before execution. If infeasible condi-
tions are detected, such as unreachable poses or invalid configurations, the system
must either trigger replanning or terminate execution safely when recovery is not
possible.
Finally, the complete program must be checked in simulation before execution. This
makes it possible to verify the generated sequence in a controlled environment and
to confirm that the solution remains consistent with the defined system constraints.

3.2.3   System Constraints and Assumptions

The proposed system is developed within a deliberately limited set of constraints
and assumptions. These boundaries define the scope of the work and help keep the
resulting behaviour predictable and reproducible.
At the geometric level, the workpiece model is restricted to rectangular sheet metal
components with exactly four edges aligned to the global coordinate system. Ro-
tated or non-axis-aligned sheet configurations are excluded. A single global wall
height parameter is assumed for all bending operations, so edge-specific wall-height
variation is not supported. Internal features are represented only as circular holes
defined by centre coordinates and radius; more complex shapes such as polygonal
cut-outs or irregular contours are outside the present scope.
The bending process is simplified in a similarly explicit way. Only right-angle (90◦ )
bends are considered, and user-defined bend angles are not supported. Each sheet
edge can be assigned to only one bending operation, which creates a one-to-one
relationship between edges and bends and keeps the sequence deterministic. The
number of bends is also limited to four on each side of the workpiece, including
both primary and opposite-side bending stages.
On the system side, the robot configuration, tooling setup, and workspace layout are
assumed to remain fixed during operation. Motion generation relies on a predefined
tool centre point configuration, and all generated trajectories are expressed relative
to that reference. The work also assumes a vacuum-based gripping mechanism with
a predefined input-output configuration. Changes in tool geometry, TCP definition,
or wiring are not handled dynamically and therefore require manual reconfiguration.
The execution environment is likewise assumed to remain structured and predefined.
The workflow depends on consistent identification and positioning of workpieces and
support structures, so deviations from the expected setup may lead to incorrect
execution behaviour. For that reason, the present implementation remains tightly
coupled to the defined virtual cell.
With respect to gripping, only vacuum-based strategies are considered. Grip feasi-
bility is evaluated using simplified physical considerations such as pressure distribu-
tion, friction, and load capacity. Alternative gripping methods, including mechanical,
magnetic, or multi-fingered grippers, are excluded.
Finally, the scope of the work is limited to rule-based program generation, geomet-
ric reasoning, and simulation-based validation. More advanced capabilities, such
as dynamic collision-free trajectory generation, real-time motion adaptation, and
environment-aware path optimisation, are intentionally left out. This keeps the sys-
tem aligned with the thesis focus on deterministic automatic program generation in
a controlled industrial setting.

The planning module must also communicate with the execution environment

separates planning, validation, and execution concerns.
Simulation-based validation prior to execution is also required at the software level.
In this way, the generated trajectories can be checked against process constraints
before runtime execution is attempted.

4 Development of Concepts

4.1     Purpose and Scope of Concept Development

Concept development is a fundamental stage in systematic engineering design, in
which alternative solution principles are generated and evaluated prior to imple-
mentation. By comparing different approaches against defined criteria, the risk of
selecting an unsuitable design solution is reduced [9].
The research gap identified in Section 2.8 highlights the absence of a systematic ap-
proach for automatic robot program generation in press brake sheet metal bending.
In particular, existing methods do not adequately address changes in workpiece ge-
ometry, gripping, regripping, and pre-execution validation while minimizing manual
programming effort. These challenges are translated into measurable engineering
objectives and requirements in Chapter 3, including functional requirements (FR-00
to FR-07), non-functional requirements (NFR-01 to NFR-05), and software platform
requirements (SR-01 to SR-03), as summarised in Table 3.3.
To address this gap, three conceptually distinct solution approaches are developed
and evaluated in this chapter. Concept A represents a structured manual program-
ming workflow, Concept B proposes a rule-based automatic program generation
approach, and Concept C explores a CAD-integrated offline programming method-
ology [3], [11]. These concepts are formulated based on different automation
paradigms and are evaluated to identify the most suitable approach for the defined
problem.
The selection of the final concept is performed using the Weighted Sum Model
(WSM), a quantitative decision-making method in which evaluation criteria are as-
signed relative weights and each concept is scored accordingly. This ensures that
the concept selection process is systematic, transparent, and aligned with the de-
fined requirements.


4.2     Concept A – Structured Operator Workflow with Guided Teach-
        In Programming

4.2.1    Methodological Framework

Concept A follows a structured manual programming approach in which the operator
defines robot motions and process steps explicitly, supported by a guided workflow.
In this approach, robot trajectories, gripper actions, and execution sequences are
created manually by the user, while the system provides a structured interface to
organise the programming process.
This concept is based on conventional manual robot programming practices, as

logic [11]. The introduction of a guided workflow improves usability by structuring
the sequence of operations and reducing unstructured interaction, but it does not
change the underlying requirement for manual definition of all robot motions.
Concept A may be implemented within the drag&bot environment using manually
configured function blocks for robot motion, gripper control, and execution sequenc-
ing. In this case, the operator constructs the workflow by placing and configuring
the required functional blocks, including motion commands and input-output oper-
ations. However, all program logic, including waypoint definition, gripping strategy,
regripping operations, and process sequencing, remains user-defined. As shown in

4.2.2     System Structure

The system structure of Concept A consists of two main layers: a manual workflow
construction layer and an execution layer. In the first layer, the operator defines the
complete process sequence manually by specifying robot motions, gripper actions,
and task order using function blocks or equivalent programming elements within
the robot programming environment.
In the second layer, the execution environment interprets and executes the man-
ually defined sequence. No intermediate planning or decision-making layer exists
for automatic trajectory generation, geometric reasoning, or constraint evaluation.
As a result, the system relies entirely on operator-defined logic and does not incor-
porate automated validation or adaptive behaviour prior to execution.


4.2.3     Critical Evaluation

Concept A is straightforward to implement and can be applied within existing robot
programming environments, including drag&bot. Its operation is transparent and
fully controlled by the operator, allowing direct modification of robot motions and
process sequences. These characteristics make it suitable for simple and repetitive
production scenarios with limited variability.
However, the limitations of this concept are significant in the context of the research
objectives. The programming effort remains high, as all robot motions, handling
steps, gripper actions, and process logic must be defined manually for each task.
This requires substantial operator expertise in robot kinematics, tooling constraints,
and process sequencing [3], [11]. As a result, the concept does not reduce man-
ual programming effort and therefore fails to address the primary objective of this
thesis.
Furthermore, the approach lacks scalability and adaptability. Changes in workpiece
geometry, process sequence, or setup conditions require manual modification of
the program, which limits its applicability in flexible manufacturing environments.
In addition, Concept A does not provide automatic grip point determination, regrip-
ping strategies, or configuration-driven trajectory generation. Operations such as
opposite-side bending and recovery from infeasible configurations remain entirely
dependent on operator intervention.
Another limitation is the absence of integrated validation and decision-making. The
system does not evaluate geometric feasibility, reachability, or handling constraints
prior to execution. As a result, infeasible configurations are typically identified only
during execution, which may lead to operational inefficiencies and potential safety
risks.

Although Concept A can utilise the drag&bot environment as an execution platform,
it remains a manually programmed solution and does not support automatic pro-
gram generation, adaptive planning, or rule-based decision-making. Therefore, it
does not satisfy the functional and non-functional requirements defined in Chap-
ter 3, particularly those related to automation, adaptability, and validation.
For these reasons, Concept A is not suitable as the final solution for addressing the
identified research gap.


4.3     Concept B – Automatic Program Generation Based on Rules
        with Integrated Constraint Validation

4.3.1    Methodological Framework

Unlike Concept A, which relies on manual waypoint definition, Concept B eliminates
manual programming entirely by introducing a rule-based automatic program gen-
eration approach. Concept B differs fundamentally from CAD-based offline program-
ming approaches by generating robot programs dynamically from configuration pa-
rameters and runtime validation, rather than relying on pre-defined digital models
of the robot cell.
In this approach, all robot waypoints, grip positions, regripping sequences, and
opposite-side handling strategies are derived automatically from geometric input
parameters and a structured configuration file. Operator interaction is limited to
selecting process options and confirming execution, while all motion generation and
decision-making processes are handled by the system. This significantly reduces
manual effort and directly addresses the primary objective of automatic program
generation defined in Chapter 3. This approach directly satisfies FR-00 by enabling
automatic generation of robot programs without manual intervention.
The system communicates with the robot execution environment through the Any-
Robot interface provided within the drag&bot platform, using a WebSocket-based
communication mechanism [19]. This architecture establishes a clear separation
between the planning logic and execution environment, which is consistent with
modular automation design principles [20]. As a result, the system operates inde-
pendently of specific robot controller implementations while maintaining compati-
bility with the defined execution platform.
A key component of the methodology is the evaluation of workpiece orientation and
feasibility prior to motion generation. The system retrieves workpiece pose informa-
tion and evaluates admissible orientations using a structured multi-stage validation
strategy. This ensures that valid handling configurations are identified regardless of
the initial placement of the workpiece. Additionally, workspace constraints and ad-
missible zones are defined through configuration parameters, allowing adaptation
to different setups without modifying the underlying logic. This approach satisfies
the adaptability requirement defined in NFR-02.
Grip planning is performed using a parameterised approach based on workpiece



                                                                                   30
geometry, suction cup properties, and physical constraints. Candidate grip positions
are evaluated against edge clearance, spacing constraints, and vacuum holding
force requirements [17]. Only physically feasible and stable grip configurations are
considered for further processing, ensuring safe handling conditions prior to motion
planning.
The system detects unsafe or infeasible conditions prior to execution and initiates
replanning where possible, or terminates execution if recovery is not feasible, en-
suring safe and reliable operation.
When a target pose cannot be reached with the current grip configuration, the
system automatically initiates a regripping sequence. This sequence involves repo-
sitioning the workpiece and re-establishing a new grip configuration that restores
reachability. This automated handling of regripping directly satisfies functional re-
quirement FR-03.
The methodology also supports opposite-side bending operations through a dedi-
cated workflow. After completing primary bending operations, the system evaluates
whether opposite-side processing is required and executes a structured sheet reori-
entation and handling sequence. All validation steps, including orientation checking,
grip feasibility, and reachability assessment, are consistently applied throughout the
process [1].
Robot trajectories are generated using linear Cartesian motion commands, ensur-
ing smooth and predictable motion execution. The use of smooth motion profiles
reduces dynamic loading on the workpiece and supports stable vacuum gripping
[17]. In addition, kinematic constraints such as singularity avoidance are consid-
ered during motion generation to ensure feasible and safe robot operation [11].
All motion targets are defined relative to a predefined TCP, ensuring consistency
between the planning module and execution environment. This requirement directly
satisfies SR-03 and guarantees that generated trajectories are aligned with the
physical configuration of the robot tool.
Overall, Concept B represents a configuration-driven, rule-based methodology that
enables automatic program generation, integrated validation, and adaptive handling
of changing workpiece conditions. The system operates deterministically based on
defined input parameters, ensuring repeatability and reproducibility of generated
robot programs.


4.3.2   System Structure

The structure of Concept B consists of five layers, as defined in Section 5.2. The in-
put and configuration layer collects all required inputs for programming. The geom-
etry and constraints evaluation layer applies grip feasibility rules, edge-clearance
checks, and zone-based orientation constraints. The planning and decision logic
layer determines whether the program can be executed directly or whether regrip-
ping or workpiece flipping is required, based on reachability and orientation validity.
The trajectory planning layer produces linear Cartesian waypoints with minimum-



                                                                                   31
jerk velocity profiles. The safety and validation layer applies a pre-execution pose
check before the command is published to the robot runtime.
The WebSocket channel of the AnyRobot interface connects all five layers to the
drag&bot virtual simulation runtime [19]. The configuration-driven approach sepa-
rates all process parameters from the program logic, allowing the solution to handle
new workpiece geometries by modifying configuration files. This directly satisfies
non-functional requirement NFR-02, as described in Section 3.2.2.


4.3.3   Critical Evaluation

Concept B is aligned with the research gap stated in Section 2.8 for every di-
mension identified in the literature. It defines waypoints, plans regrips, and se-
quences opposite-side operations automatically from geometric parameters. A pre-
execution pose validator guards against unsafe execution states before motion
starts. This enables a configuration-driven architecture that can adapt to new part
geometries without source code changes, satisfying FR-01, NFR-03, NFR-04, and
NFR-05. Configuration-driven parameterization satisfies NFR-02. The system oper-
ates exclusively within the drag&bot runtime via the AnyRobot Interface, satisfying
SR-01 and SR-02. All motion targets reference the pre-defined tool center point,
satisfying SR-03. All requirements in Chapter 3 are therefore addressed by the
concept design.
The primary constraints under which Concept B operates are identified in Sec-
tion 3.2.3. The system assumes rectangular sheet geometry with fixed 90-degree
bend-angle constraints. Integration with the KEBA robot controller hardware, which
is part of the KEBA robot driver layer within the drag&bot software stack [19], is

4.4      Concept C – CAD Integrated Offline Programming with Digital
         Twin Simulation

4.4.1     Methodological Framework

Unlike Concept B, which performs rule-based program generation dynamically dur-
ing execution, Concept C relies on a complete CAD-based digital model of the robot
cell to generate and validate robot programs offline prior to execution.
Concept C follows a CAD integrated OLP approach, in which a digital representation
of the robot, tooling, and workpiece is used to plan and simulate robot operations.
In this methodology, robot programs are generated within a simulation environment
based on the geometric model of the workpiece and the digital representation of the
production cell. All motion planning, collision checking, and feasibility evaluation are
performed prior to execution, without requiring direct interaction with the physical
robot.
The OLP system evaluates bending sequences, grip positions, regripping strategies,
and kinematic feasibility using the CAD model of the workpiece and environment.
The generated robot program is validated within the simulation environment and
then transferred to the robot controller for execution. This approach corresponds
to established offline programming methods used in industrial robotics [3].
Industrial OLP tools such as ABB RobotStudio, KUKA.Sim, and FANUC ROBOGUIDE
implement similar methodologies and are widely used in structured production en-
vironments [3]. The use of digital twin-based simulation enables early detection of
unreachable poses, collisions, and process inconsistencies before actual execution,
thereby reducing operational risks [21].
The key conceptual difference between Concept B and Concept C lies in how robot
programs are generated and validated. Concept B follows a configuration-driven
and rule-based approach, where robot trajectories and handling strategies are gen-
erated dynamically using input parameters and validated at runtime. In contrast,



                                                                                     33
Concept C follows a model-driven approach, where all planning and validation are
performed within a CAD-based simulation environment before execution. As a re-
sult, Concept B offers higher flexibility and adaptability to changing workpiece con-
figurations, whereas Concept C depends on accurate digital models and requires
significant preparation effort for each new scenario.


4.4.2    System Structure

This concept consists of four layers. A CAD modelling layer provides digital repre-
sentations of the robot, press brake, tools, and workpiece. An OLP and simulation
layer uses Unified Robot Description Format (URDF) representations to plan robot
programs through a built-in kinematic solver. A post-processing layer converts the
generated programs into controller-specific syntax, and the robot controller layer
executes the generated program. Accurate digital-twin representations of all cell
components are required at the modelling layer; small modelling errors in the digital
twin can propagate as execution errors that require manual reprogramming during
commissioning [3], [11].


4.4.3    Critical Evaluation

Concept C offers meaningful automation advantages for structured, high-volume
production environments where accurate cell models are available and OLP tool
investment is justified. Simulation-based validation provides strong pre-execution
assurance, and the approach is supported by mature commercial software [11],
[21]. These characteristics make it the dominant paradigm in industrial robotic
bending automation at the time of writing.
For the scope of this thesis, Concept C presents three fundamental disadvantages
that result in its rejection. First, the implementation requires accurate CAD models
of the complete robot cells, including the robot, press brake, tooling, fixtures, and
workpieces — which represents a substantial engineering preparation effort that is
not available within the thesis timeframe.
Second, commercial OLP systems involve high license fees while demanding expert-
level instruction, both of which are unavailable within this project’s constraints [9].
Besides cost, mainstream OLP platforms lack native compatibility with both the
drag&bot simulation framework and the AnyRobot WebSocket system, which define
the core setup targeted here [19]. Connecting such a tool would require a custom
bridge to the drag&bot engine, adding implementation effort that is not justified by
the scope of this thesis. Even if the first two limitations were resolved, this third
limitation would disqualify Concept C, because SR-01 and SR-02 are non-negotiable
constraints from the industrial partner environment.

4.6     Concept Decision Using the Weighted Sum Model

4.6.1    Methodology

The concept selection in this work is performed using the WSM, a structured multi-
criteria decision-making method widely used in engineering design. The WSM en-
ables quantitative comparison of alternative concepts by evaluating them against a
defined set of criteria derived from the system requirements.
Each evaluation criterion is assigned a weighting factor based on its relative im-
portance in addressing the research objectives. The concepts are then evaluated
against each criterion using a consistent scoring scale from 1 to 5, where 1 indi-
cates minimal or no satisfaction and 5 indicates a high level of satisfaction. The
overall score for each concept is obtained by multiplying the assigned weight with
the corresponding score and summing the results across all criteria.
This method ensures that the concept selection process remains transparent, sys-
tematic, and aligned with the functional, non-functional, and system-level require-
ments defined in Chapter 3. It also reduces subjectivity by providing a structured
framework for comparing alternative solution approaches.

5.2     System Architecture

5.2.1    Layered Architecture Design and Data Flow

The system adopts a layered architecture in which each module depends exclu-
sively on the module in the layer directly beneath it. This architectural pattern is
selected because the press brake automation context imposes three key constraints
that cannot be satisfied by an unstructured design: independent testability of con-



                                                                                                                                                                             43
straint evaluation, maintainability and safe replaceability of components, and strict
enforcement of safety ordering. Testability is achieved by enabling modules to be
evaluated using synthetic pose data and YAML-based configuration inputs, without
requiring an active WebSocket connection. This isolation is essential for verifying
orientation classification and grip feasibility computations, which cannot be reliably
validated from live system behaviour alone.
Replaceability is ensured through modular separation, where modifications to the
grip planning algorithm are confined to the constraint evaluation layer. The planning
and motion layers remain independent of these modules, supporting maintainability
and satisfying NFR-02.
Safety ordering is enforced structurally by implementing pre-execution validation in
a dedicated layer that is executed prior to any motion generation. This guarantees
that safety checks cannot be bypassed or reordered, satisfying FR-07 and NFR-03.
Five distinct layers are defined within the system architecture, each with a clearly
assigned responsibility. Layer 1 (Input and Configuration) is responsible for acquir-
ing all required parameters from the input file, along with the operator’s bend-side
selection, prior to the establishment of any WebSocket connection. Layer 2 (Geome-
try and Constraint Evaluation) performs the computation of geometric and physical
constraints based on input pose data, while remaining strictly limited to evalua-
tion tasks and producing no motion commands. Layer 3 (Planning and Decision
Logic) determines the overall execution strategy and coordinates the interaction
between Layers 2 and 4, without directly generating motion instructions. Layer 4
(Motion Generation and Communication) serves as the exclusive interface for robot
communication, generating Linear motion command (LIN) and Point-to-point mo-
tion command (PTP) waypoints, converting them into JavaScript Object Notation
(JSON) format, and transmitting them via an authenticated WebSocket connection.
Layer 5 (Safety and Validation) is implemented as an independent top-level layer
that is executed prior to any motion generation and enforces mandatory validation
and operator confirmation, preventing further execution until all safety conditions
are satisfied. The complete architectural structure is illustrated in Figure 5.2.

is positioned within Layer 5, which is not imported by any lower layer. This separa-

runtime. Instead, safety checks are enforced strictly at the beginning of a session,
ensuring that they cannot be bypassed or reordered during execution. Third, the
trajectory generator serves as the sole interface for dispatching motion commands
to the runtime. All waypoint sequences are routed through this module, ensuring
that workspace constraints and singularity checks are consistently applied before
execution.


5.2.3    Communication Stack and Authentication Interface Specification

All runtime communication passes through the AnyRobot Interface, as it is the only
supported external Application Programming Interface (API) for drag&bot. Direct
ROS client libraries are excluded because they would couple the planning software
to a specific ROS version, violating NFR-02 [19] [22]. The AnyRobot Interface
translates JSON over a persistent WebSocket channel into native ROS operations
using the RosBridge v2 protocol, enabling the entire planning software to run in
standard Python 3 without a ROS installation on the planning machine.
WebSocket is selected over Hypertext Transfer Protocol (HTTP) due to its ability to
maintain a persistent connection that supports continuous data exchange. Unlike
HTTP, which follows a request–response model and requires a new connection for
each interaction, WebSocket enables uninterrupted communication over a single


                                                                                    47
channel. In applications involving robotic motion execution, where a large number
of trajectory points must be transmitted sequentially, repeated connection over-
head can introduce noticeable delays. These delays may accumulate and lead to
interruptions in command streaming, potentially affecting smooth robot operation.
By using a persistent communication mechanism, WebSocket reduces transmission
overhead and ensures more stable and efficient delivery of motion commands, mak-
ing it well suited for real-time robotic control scenarios [23].
Figure 5.3 presents an overview of the system communication architecture. The
planning software establishes a persistent WebSocket connection to the robot con-
troller via a defined network endpoint (e.g., ws://192.168.x.x:9091). Communica-
tion is organized through a set of dedicated interfaces, each responsible for a specific
function within the system.
WebSocket-based middleware is widely used in robotics to enable platform-
independent communication between external applications and ROS-based sys-
tems [24]. Such approaches rely on a persistent socket connection and lightweight
message serialization to support continuous data exchange required for real-time
operation.
In the implemented system, the Ros Bridge v2 interface is used to transmit mo-
tion commands, while the rosauth service ensures secure authentication using the
Secure Hash Algorithm 512-bit (SHA-512) hashing algorithm. Motion trajectories
are transmitted in batches via the /command_list interface, and real-time object in-
formation is retrieved through /dnb_object_manager/list_objects. Gripper control
is performed using /robot/set_digital_ios, whereas object attachment and detach-
ment are handled through the corresponding manager interfaces. User interactions
are managed via the human_interaction/request_hi interface.
The YAML configuration is not part of the runtime communication. It is loaded once
during system initialization and shared across the relevant modules, ensuring that
missing or incorrect parameters are detected early before execution begins.
On connection establishment, the WebSocket client performs the rosauth SHA-512
authentication handshake, because the drag&bot WebSocket port is accessible to
any process on the local network and an unauthenticated endpoint would allow
arbitrary motion command injection. The Message Authentication Code (MAC) is
computed by hashing with SHA-512 concatenation of the shared runtime secret,
the interface identifier, destination, a fixed nonce, session timestamps, and the
access level string.
The authentication token is computed based on the procedure defined in the
drag&bot AnyRobot Interface specification [19]:


             MAC = SHA-512(secret ∥ id_string ∥ dest ∥ nonce ∥ t ∥ level)         (5.1)

makes pre-image and collision attacks computationally infeasible within the oper-
ational context of this application. The shared secret is stored as an environment

     over JSON primarily due to its support for inline comments. This allows engineers
     to document the meaning and physical relevance of individual parameters directly
     within the configuration file, eliminating the need to consult external documentation.

     method, which prevents the execution of unintended code in the event that the file

     within the configuration file. In contrast, storing these poses independently could

5.3.2   Virtual Cell Layout and Spatial Zone Classification

The simulated robotic cell within the drag&bot environment includes the robot, press
brake, orientation table, and a tracked sheet object, which serves as the reference
for all geometric computations. The spatial configuration of these elements reflects
the intended physical setup, ensuring that simulation results are representative of
real-world operation.
At the beginning of each execution cycle, the system retrieves the six-degree-of-
freedom pose of the sheet from the object tracking service. The pose is expressed
in the robot world coordinate frame, where the origin is located at the robot base.
Accurate pose acquisition is a fundamental requirement in robotic manipulation sys-
tems and is widely addressed in modern robotics literature [11]. Based on this
information, the position of the sheet centroid in the XY plane is used to classify the
workpiece into one of four spatial zones.
The workspace is partitioned into four regions relative to the robot base. A centroid
with negative X and positive Y corresponds to Zone 1 (rear-left), while negative X
and negative Y defines Zone 2 (front-left). Positive X and positive Y correspond
to Zone 3 (rear-right), and positive X with negative Y defines Zone 4 (front-right).
The classification is based on threshold values of ±10 mm in the X direction and
±50 mm in the Y direction. These thresholds account for measurement uncertainty
and reflect the physical layout of the robotic workspace [11].
Zones 3 and 4 lie within the primary reachable workspace of the robot and there-
fore allow direct execution of pickup and bending operations. In contrast, Zones 1
and 2 correspond to regions with limited reachability. In these cases, the system
automatically initiates a repositioning step, moving the workpiece to an intermedi-
ate configuration within the reachable workspace before continuing execution. This
ensures that all subsequent operations remain within kinematic limits without re-
quiring operator intervention.
If the sheet centroid lies within the dead-band region defined by |x| < 10 mm or



                                                                                     56
|y| < 50 mm, the classification is considered unresolved. This occurs near the coor-
dinate axes, where small variations in tracking data may lead to inconsistent zone
assignment. To prevent incorrect execution, the system terminates the current
session and prompts the operator to reposition the workpiece before restarting.

5.4     Pre-Execution Safety Validation

Safety validation is performed prior to motion generation to ensure that unsafe
conditions and infeasible configurations are identified before robot execution, in ac-
cordance with NFR-03, NFR-04, and NFR-05 [11]. The system incorporates three
complementary mechanisms: a fixture pose deviation check, a blocking operator
confirmation dialog, and a runtime motion error monitoring module. In addition, all
trajectory waypoints are generated and verified using robot kinematics to ensure
reachability and feasibility before execution, thereby preventing invalid motion com-
mands from being issued [11].


5.4.1    Fixture Pose Deviation Validation

The fixture pose deviation check retrieves the current poses of critical fixtures from
the drag&bot object manager and compares them with reference poses obtained
during initial cell calibration. The monitored elements include the primary sheet
object at the press brake, the finished-part placement positions on the regrip table,
and the placement and attachment references at the flip station. These fixtures
are treated as fixed references within the planning system, as all grip positions, tra-
jectory waypoints, and placement operations are computed under the assumption
that their positions remain unchanged. Any deviation from these reference poses
can therefore result in motion targets that are geometrically valid but physically
incorrect.
The deviation check is applied uniformly across all spatial zones. Each fixture is
evaluated using both positional and orientation criteria. The positional deviation is
computed as:

                                     √
                            ∆pos =    (∆x)2 + (∆y)2 + (∆z)2                      (5.2)

and the orientation deviation is defined as:


                         ∆ang = max (|∆RZ|, |∆RY |, |∆RX|) .                     (5.3)

A fixture is considered out of tolerance when ∆pos exceeds 5 mm or ∆ang exceeds
0.10 rad (5.7◦ ). The positional threshold is selected to remain below the minimum
clearance used in grip planning. This ensures that fixture misalignment does not
produce misleadingly valid grip configurations. The angular threshold corresponds
to the minimum deviation that would affect the accuracy of vacuum cup contact on
the sheet surface.
The primary sheet object is evaluated using the same criteria as other fixtures.
Since the planning system relies on the current sheet pose for all geometric com-
putations, any deviation may lead to incorrect motion generation and is therefore
treated as a configuration error.
If one or more fixtures exceed the defined thresholds, the system generates a



                                                                                   58
structured warning listing all affected fixtures together with their measured posi-
tional and angular deviations. This warning is presented through a blocking human
interaction (HI) dialog titled Fixture position warning, allowing the operator to either
proceed with explicit acknowledgement or cancel execution for further inspection.
The operator’s decision is recorded, ensuring that responsibility for accepting out-
of-tolerance conditions remains with the human operator.
If a fixture is not detected in the object manager response, it is treated as missing
and automatically flagged as a validation failure.


5.4.2    Operator Authorization and Runtime Error Monitoring

The operator confirmation dialog is positioned as the first step in the planning or-
chestrator startup sequence, preceding all subsequent processes including fixture
validation, visualization, and motion execution. The dialog enforces a mandatory
decision: either initiate the automated workflow or cancel execution. The orches-
trator does not proceed until a response is received from the HI service, ensuring
that execution cannot begin without explicit operator authorisation. If the operator
selects cancel, the process terminates without issuing any command to the robot
runtime.
In addition to pre-execution validation, runtime supervision is implemented through
a motion error monitoring module operating as a background subprocess. This com-
ponent subscribes to the /command_result ROS topic via an independent WebSocket
connection, enabling continuous monitoring of execution outcomes without inter-
rupting the main command flow. When a non-zero result code is detected, indicating
a motion execution failure, the system immediately triggers a modal HI notification
to inform the operator.
The monitoring module does not directly interrupt the execution pipeline. Instead,
it provides immediate feedback through the HI interface and requires operator ac-
knowledgement before further interaction is permitted. This ensures that execution
anomalies are not overlooked while maintaining operator authority over subsequent
decisions.
Together, these mechanisms establish a layered safety structure. Pre-execution val-
idation ensures safe initial conditions, while runtime monitoring provides immediate
feedback on execution failures. Both mechanisms utilise the drag&bot HI service,
ensuring a consistent and controlled interface for safety-related interactions. With
these safeguards in place, the subsequent section addresses the workpiece orien-
tation strategy.


5.5     Workpiece Orientation Strategy

Following pre-execution safety validation, the first geometric step in each bend-
ing cycle is the determination of a valid pickup orientation for the sheet.        This
is required because the sheet may be placed in arbitrary orientations within the



                                                                                     59
workspace, while only a subset of these orientations is kinematically feasible for
the target bending operation. The orientation strategy evaluates the tracked sheet
pose, applies a structured selection process, and produces a validated pickup pose
for subsequent grip planning.


5.5.1   Zone-Based Rotation Admissibility

The admissible range of sheet rotation about the Z-axis is defined by a zone-
dependent window [RZmin , RZmax ]. This constraint reflects the limited rotational
capability of the robot end-effector within different regions of the workspace [11].
Since the reachable orientation range varies with the spatial position of the sheet,
zone classification is performed prior to orientation evaluation. The admissibility
limits are retrieved from the configuration to ensure that only kinematically feasible
orientations are considered. This prevents the selection of geometrically valid but
unreachable poses.


5.5.2   Pickup Orientation Validation

Before applying the selection strategy, the tracked pose is validated to ensure that
the gripper approaches the sheet from above. This is evaluated using the condition
cos(RX) · cos(RY ). If the value is below −0.10, the tool Z-axis is oriented downward
and no modification is required. Otherwise, a corrective transformation is applied:


           RZ ′ = wrap(RZ + 180◦ ),   RY ′ = −RY,    RX ′ = wrap(RX + 180◦ )        (5.4)

This transformation ensures proper tool alignment with the sheet surface without
modifying the pickup position.


5.5.3   Three-Level Orientation Selection Strategy

To ensure that a valid pickup orientation is always obtained, a three-level selection
strategy is applied. The levels are evaluated sequentially, and execution terminates
as soon as a valid orientation satisfying admissibility constraints is identified. This
guarantees robustness while prioritising geometrically consistent and kinematically
feasible configurations.
The workpiece is defined using four reference faces established during system com-
missioning, each associated with a fixed angular offset about the sheet’s local verti-
cal axis (0◦ , 180◦ , +90◦ , −90◦ ). These offsets allow the system to normalise arbitrary
orientations into a consistent reference frame.


Level 1: Reference-Face Equivalent Orientation             At the highest priority level,
the tracked orientation is converted into a reference-face equivalent by removing
the face-specific offset:

5.6     Workpiece Handling and Gripper Control

Once a valid pickup orientation has been determined, the system must establish a
reliable physical interaction between the gripper and the sheet while maintaining
consistency between the physical robot state and the virtual simulation. Any mis-
match between the vacuum state of the gripper and the attachment state in the
simulation leads to incorrect pose propagation and invalid trajectory computation
in subsequent stages. This consistency is ensured through two coordinated mech-
anisms: digital IO control of the vacuum gripper and kinematic object attachment
within the simulation environment.


5.6.1    Vacuum Gripper Digital Input and Output Sequence

The vacuum gripper is actuated using two digital output signals mapped within the
drag&bot IO management system. One signal activates the vacuum by closing the
suction valve, while the other releases the vacuum by opening the exhaust valve.
These signals are strictly mutually exclusive; simultaneous activation is avoided to
prevent conflicting pressure states and potential hardware damage.
Control commands are issued via the /robot/set_digital_ios interface, which trans-
mits structured IO instructions specifying the target output and its Boolean state.
To ensure reliable gripping, a dwell period of approximately 250 ms is applied after
vacuum activation. This delay allows the suction cups to establish a stable seal
with the sheet surface, which is necessary for maintaining grasp stability during
subsequent motion [28].
A secondary delay of approximately 150 ms is introduced after each IO operation
to ensure that the state transition propagates through the communication layer
before further commands are issued. This prevents timing inconsistencies between
command execution and runtime state updates.


5.6.2    Kinematic Object Attachment and Detachment

Within the simulation environment, the physical coupling between the gripper and
the sheet is represented through kinematic attachment. When the gripper suc-
cessfully establishes contact, the corresponding object is attached to the robot tool
frame, ensuring that subsequent robot motions are reflected in the object pose.




                                                                                  63
When the vacuum is released, the object is detached and remains fixed in its last
known position.
Attachment is performed using the /dnb_object_manager/attach interface without
enforcing a position override. This avoids introducing discontinuities between the
tracked object pose and the simulated state, as the tracked pose may not exactly
coincide with the instantaneous tool frame position. Position override is reserved
only for controlled initialization procedures where explicit alignment is required.
Detachment is executed using the /dnb_object_manager/detach interface within the
same reference frame. To maintain consistency, attachment and detachment oper-
ations are always executed in a fixed sequence together with the corresponding IO
commands:

   • Grasp sequence: vacuum ON → dwell → attach

   • Release sequence: vacuum OFF → dwell → detach

This sequence is encapsulated within centralized helper routines that are invoked by
all modules performing grasp or release operations. Centralizing this logic ensures
that the physical and virtual system states remain synchronised at all times and
prevents inconsistent conditions in which the vacuum state and attachment state
do not correspond.
With physical grasping and state synchronisation established, the next step is to
determine feasible suction cup positions on the workpiece surface.


5.7     Grip Position Planning and Feasibility Validation

Following the determination of a valid pickup orientation and the establishment of
a consistent gripper control mechanism, the system must identify feasible suction
cup placements on the sheet surface. Arbitrary placement is not sufficient, as it
may violate geometric constraints or fail to provide adequate holding force during
handling. The grip planner therefore evaluates both geometric feasibility and physi-
cal stability to ensure a reliable and executable grasp configuration. This structured
approach directly addresses the limitations identified in Chapter 2, where manual
or heuristic-based gripping strategies lack consistency and adaptability. This ap-
proach enables deterministic and repeatable grip planning, which is essential for
automated program generation in an industrial environment.


5.7.1    Sheet Geometry and Hole Detection

The sheet is modelled as a planar rectangular surface with uniform mass distribution,
defined by its length, width, thickness, and mass obtained from the configuration.
If the mass is not explicitly specified, it is estimated from the sheet volume and the
material density defined in the configuration.




                                                                                      64
In addition to the outer boundary, internal features such as holes are extracted
from the STL mesh during the geometry analysis stage. Each hole is represented
by its centre position and radius in the sheet coordinate frame. These regions are
explicitly excluded from the feasible gripping area, since suction cups cannot form
a stable seal over discontinuities. This ensures that only physically valid contact
regions are considered during grip planning.

5.7.3   Grip Candidate Search and Selection

Candidate suction cup positions are generated using a multi-resolution grid-based

identify feasible regions, followed by progressive refinement to improve placement
accuracy in promising areas. Additional candidates are generated near hole bound-
aries to maximise usable surface area while maintaining required clearances.
Each candidate position is evaluated against geometric constraints. The cup centre
must satisfy minimum edge clearance requirements, avoid overlap with hole regions
including a defined buffer zone, and comply with spacing constraints in multi-cup
configurations. For the two-cup case, candidate positions are evaluated in pairs,

geometric and physical constraints are retained.
The remaining candidates are ranked using a scoring function that balances multi-
ple criteria, including edge clearance, distance from internal features, and spatial
distribution across the sheet. In multi-cup configurations, the scoring additionally
promotes wider spacing between cups to improve stability during transport. This
structured evaluation replaces heuristic placement strategies commonly found in
manual programming approaches and ensures consistent selection of robust grip
configurations.

     5.8    Regrip Planning and Execution

     Even when a valid pickup orientation and a feasible grip configuration are estab-
     lished, the current grasp may not permit the robot to reach the required bending
     pose. This limitation arises when the target configuration lies outside the reach-



                                                                                        68
able workspace or when kinematic constraints, such as joint limits or proximity to
singularities, prevent a valid motion solution [27]. To address this, the system
implements an automatic regrip planning strategy that determines the required re-
orientation dynamically. This approach directly addresses the limitations identified
in the state of the art, where regrip operations are typically predefined or manually
programmed.


5.8.1    Regrip Decision Strategy

In contrast to conventional approaches based on fixed regrip sequences, the pro-
posed system evaluates a discrete set of candidate workpiece orientations and se-
lects a configuration that satisfies kinematic feasibility. This enables the system to
determine both the required orientation and the number of regrip steps automati-
cally.
The candidate set consists of discrete orientation increments corresponding to phys-
ically achievable rotations on the orientation table. For each candidate orientation,
the system performs the following sequence:

   • Update the workpiece pose according to the candidate orientation

   • Determine a valid pickup orientation using the strategy described in Section 5.5

   • Compute feasible grip positions using the planner described in Section 5.7

   • Evaluate kinematic feasibility using inverse kinematics and trajectory valida-
     tion

A candidate orientation is accepted only when all feasibility conditions are satis-
fied. The evaluation follows a sequential selection strategy in which candidates are
tested in a predefined order, and the first feasible solution is selected. This ensures
computational efficiency while maintaining robustness for real-time execution.
The number of required regrip steps is implicitly determined from the difference
between the current orientation and the selected feasible configuration. This ap-
proach avoids unnecessary intermediate operations while ensuring that the final
pose remains reachable and executable within the robot workspace.
Algorithm 4 summarises the decision process. The evaluation reuses the existing
planning pipeline, ensuring consistency with orientation selection, grip planning,
and trajectory generation.

The regrip execution sequence operates within the existing motion framework and

determine the number of regrip steps.

separation between decision-making and execution ensures modularity and allows
the regrip strategy to be extended without modifying the motion execution layer.
Compared to configuration-driven approaches, the proposed method improves

5.9     Opposite-Face Bending Workflow

After completing all primary-side bending operations, the system evaluates whether
additional bends are required on the opposite face of the sheet. These operations
cannot be executed directly from the initial pickup configuration, as the required
face is not accessible to the press brake tool. Consequently, the workpiece must be
reoriented through a controlled flip operation before continuing the bending process.


5.9.1    Pre-Flip Verification and Transition Correction

Before initiating the flip sequence, the system verifies that the current sheet pose
corresponds to the expected reference configuration. This verification is performed
using a wrap-safe six-degree-of-freedom pose comparison, with a positional toler-
ance of 2 mm and an angular tolerance of 1◦ .
This validation step is required because the sheet may have undergone regrip op-
erations during the primary bending sequence. Any deviation from the expected
pose would propagate errors into subsequent motion planning stages, leading to
incorrect trajectory generation.
If the verification fails, a transition correction step is executed. The system first
restores the reference orientation using the strategy described in Section 5.5. A
controlled pickup and repositioning sequence is then performed to re-establish a
consistent and verified alignment between the robot and the workpiece.
If the verification is successful, the correction step is omitted and the system pro-
ceeds directly to the flip sequence.


5.9.2    Sheet Flip Sequence and Opposite-Face Bending Execution

The flip operation is performed using a dedicated station within the robotic cell.
The workpiece is transferred through two predefined reference positions to achieve
a physically feasible reorientation.
First, the robot transports the sheet to the flip station placement position while main-
taining the current grasp. The workpiece is then released in a controlled manner.
The robot subsequently moves to an intermediate standoff pose and re-approaches
the sheet from the opposite side, establishing a new grasp that results in the flipped
orientation.
This two-stage transfer is preferred over a direct in-gripper rotation. A direct rota-
tion would require a continuous motion that exceeds the kinematic capabilities of
the robot and may violate workspace or collision constraints [27].




                                                                                    71
Following the flip operation, the sheet is aligned such that the previously inaccessi-
ble face is oriented towards the press brake tool. The system then applies the same
validation pipeline used for primary-side bending, including zone classification, ori-
entation determination, grip position planning, and trajectory generation.
Reusing the same processing pipeline ensures consistent system behaviour across
both primary and opposite-side operations. It also avoids the need for separate
handling logic, thereby maintaining modularity and reducing system complexity.

5.10     Trajectory Generation

Trajectory generation constitutes the final stage of the planning pipeline, where
validated task-level poses are transformed into executable robot motion. The input
to this stage is an ordered sequence of TCP poses obtained from upstream modules,
including grip planning, regrip handling, and opposite-face operations. Each pose
defines the desired end-effector position and orientation within the robot world
frame.
Rather than executing direct point-to-point transitions, the system constructs a con-
tinuous and smooth trajectory composed of intermediate waypoints. This approach
ensures kinematic feasibility, reduces dynamic loading, and improves execution
stability during sheet handling.


5.10.1    Three-Phase Linear Trajectory Structure

Each motion segment is generated using a structured three-phase trajectory: lift,
lateral transfer, and descent.
In the lift phase, the TCP is translated vertically to a predefined safe height to avoid
collisions with the workpiece, fixtures, or surrounding environment. In the lateral
transfer phase, the robot moves towards the target position while maintaining this
clearance height. During this phase, the end-effector orientation is constrained
to limit excessive joint rotations and reduce proximity to kinematic singularities.
Finally, in the descent phase, the TCP is lowered to the target pose, where the
required orientation for task execution is fully applied.
To further improve motion feasibility, an intermediate rotation pose is introduced
above the target location. This ensures that major orientation adjustments are
completed before the final approach, reducing the risk of instability near contact

Each interpolated TCP waypoint is mapped to a corresponding robot joint configu-
ration using inverse kinematics. For each waypoint, a feasible solution is selected
based on continuity with the previous configuration, avoiding abrupt joint changes
and ensuring smooth motion across the trajectory.
As the robot executes the sequence, all joints evolve continuously, resulting in a
smooth end-effector motion that closely follows the planned Cartesian path.


5.10.4    Workspace Constraints and Singularity Handling

To ensure execution feasibility, each waypoint is validated against workspace con-
straints. The TCP pose is transformed into the corresponding flange pose, and its
position is checked against the allowable workspace limits. If a waypoint exceeds
these limits, it is projected onto the nearest feasible boundary.
Singularity avoidance is addressed by restricting orientation changes during the
lateral motion phase. Large orientation adjustments are deferred to the approach
phase, where the robot operates in a more stable configuration. This reduces the
risk of excessive joint velocities and improves overall motion robustness.


5.10.5    Motion Execution and Path Reduction

The interpolation process generates a dense set of waypoints, which may exceed the
processing capacity of the robot controller. To address this, a path reduction strat-
egy is applied, retaining only those waypoints that exceed predefined positional or
rotational thresholds. This preserves the essential characteristics of the trajectory
while reducing communication overhead.
The resulting waypoint sequence is transmitted as a series of linear motion com-
mands, which are executed by the robot controller using blending techniques. This
allows smooth transitions between consecutive waypoints without stopping, produc-
ing continuous and stable motion.
Overall, the trajectory generation module forms a deterministic transformation
pipeline in which validated task-level poses are converted into executable robot mo-
tion through interpolation, kinematic mapping, constraint validation, and controlled
execution.

5.11.2   Mitigation Strategies

Several design measures have been incorporated to reduce both the likelihood and
impact of identified failure modes.
Geometric consistency is ensured through structured validation stages, including
fixture pose deviation checks and orientation admissibility constraints. These mech-
anisms prevent incorrect pose assumptions from propagating into motion genera-
tion.
Grip reliability is addressed through combined geometric filtering and physical fea-
sibility validation. By enforcing edge clearance, hole avoidance, and vacuum force
constraints, the system ensures that only stable grip configurations are selected.
Trajectory-related risks are mitigated through interpolation-based motion genera-
tion and workspace validation. The use of minimum-jerk profiles and waypoint fil-
tering ensures smooth motion while avoiding excessive controller load. In addition,
singularity avoidance strategies and orientation constraints are applied to maintain
kinematic stability throughout execution.
Regrip and flip operations are implemented as structured sequences with defined
intermediate poses, ensuring collision-free transitions and consistent object han-
dling. The use of deterministic execution pipelines further reduces uncertainty by
enforcing a fixed order of validated operations.


5.11.3   Discussion

The FMEA results indicate that the most critical risks are associated with pose accu-
racy and trajectory feasibility, as these directly influence all downstream planning
and execution stages. These risks are effectively mitigated through layered valida-
tion, constraint-based planning, and structured motion generation.
Overall, the system demonstrates a balanced reliability profile in which high-severity
failure modes are either low in occurrence or mitigated through strong detection
and validation mechanisms. This confirms that the proposed architecture not only
enables automated bending operations but also ensures safe and predictable exe-
cution under varying operating conditions.


5.11.4   Conclusion

This chapter presented the complete implementation of the proposed system for
automated press brake sheet metal bending, based on the selected Concept B. The
implementation translates the conceptual design into a fully functional software
architecture that integrates geometric reasoning, constraint-based planning, and
robotic motion execution within a unified framework.


                                                                                   78
A layered system architecture was developed to ensure modularity, testability, and
strict enforcement of execution order. Each functional component, including ori-
entation determination, grip planning, regrip handling, and trajectory generation,
was designed as an independent module with clearly defined responsibilities. This
structure enables traceability between system requirements and implementation,
while also supporting future extensibility.
The system demonstrates the capability to generate robot programs automatically
from configuration data and geometric inputs, eliminating the need for manual
waypoint definition. By incorporating structured validation mechanisms at multi-
ple stages, including pre-execution safety checks, grip feasibility validation, and
workspace-constrained trajectory generation, the system ensures reliable and safe
operation.
A key contribution of this work lies in the integration of adaptive regrip planning
and opposite-face handling within a deterministic execution pipeline. Unlike con-
ventional approaches that rely on predefined sequences, the system dynamically
evaluates feasible configurations and determines the required manipulation strat-
egy at runtime. This improves flexibility while maintaining computational efficiency
suitable for industrial applications.
The trajectory generation framework further enhances system robustness by com-
bining smooth interpolation techniques with kinematic validation and path reduction

6 Experimental Evaluation and Validation

6.1     Experimental Setup

To evaluate the performance and robustness of the implemented system, a struc-
tured experimental setup is defined. The evaluation is conducted under controlled
conditions to ensure repeatability and consistency across all test scenarios. This
section outlines the test environment, the selected scenarios, and the metrics used
to assess system performance.


6.1.1    Test Environment

All experiments are conducted within the virtual environment used during system
development. This ensures consistency between implementation and evaluation,
allowing the behaviour of the system to be assessed under identical conditions.
The evaluation setup includes the complete system pipeline operating on simulated
workpiece data. The environment enables controlled testing of different scenarios
without external disturbances, ensuring that observed results are attributable to
the system behaviour rather than environmental variability. This approach supports
repeatable experimentation and reliable comparison across multiple test runs.


6.1.2    Test Scenarios

To assess the adaptability of the system, a set of representative test scenarios is
defined based on variations in workpiece geometry and initial placement conditions.
These scenarios are designed to reflect the key operational challenges addressed
by the system.
The evaluated scenarios include:

  • Variations in sheet dimensions and mass properties

  • Arbitrary initial orientations of the workpiece

  • Placement across different spatial regions of the workspace

  • Configurations requiring regrip operations due to kinematic constraints

  • Tasks involving both primary and opposite-face bending operations

Each scenario is executed multiple times to verify that the system produces consis-
tent and repeatable results under identical conditions.




                                                                                  83
6.1.3      Evaluation Metrics

The system performance is assessed using a combination of quantitative and qual-
itative metrics. These metrics are selected to evaluate both functional correctness
and operational efficiency.
The primary evaluation metrics include:

   • Execution success rate: proportion of scenarios completed without failure

   • Planning time: time required to generate a complete motion plan

   • Execution time: total duration of the bending operation

   • Number of regrip operations: indicator of handling efficiency

   • Failure occurrence: identification and classification of unsuccessful execu-
      tions

In addition, qualitative observations are used to assess motion smoothness, stability
of gripping, and overall system behaviour during execution.
Together, the defined environment, scenarios, and metrics provide a consistent and
comprehensive basis for evaluating the effectiveness of the implemented system.


6.2     Functional Validation

This section evaluates the correctness of the core functional components of the
implemented system. Each module of the planning pipeline is assessed based on
its ability to produce valid and consistent outputs under varying input conditions.
The validation focuses on confirming that the system behaves as expected rather
than describing how each module operates.


6.2.1      Orientation Strategy Validation

The orientation strategy is evaluated using scenarios in which the workpiece is
placed in arbitrary initial poses across different spatial regions. The results con-
firm that the system consistently determines a feasible pickup orientation for all
tested configurations.
In cases where the initial orientation satisfies admissibility constraints, the detected
pose is preserved. When this is not possible, the system successfully applies correc-
tive transformations or fallback strategies to generate a valid orientation. Across
all evaluated scenarios, a feasible pickup orientation is obtained without requiring
manual adjustment, demonstrating robust handling of non-deterministic input con-
ditions.




                                                                                     84
6.2.2    Grip Planning Validation

The grip planning module is validated by assessing its ability to generate stable
and feasible suction cup placements under geometric and physical constraints. Test
cases include variations in workpiece size and configurations containing internal
cut-outs.
The results show that all selected grip configurations satisfy geometric constraints,
including edge clearance and exclusion of hole regions. Furthermore, the force
validation step ensures that only configurations with sufficient holding force are
accepted. In multi-cup scenarios, the system consistently selects configurations
that improve stability through appropriate spacing. These results confirm that the
grip planner produces reliable and physically feasible solutions.


6.2.3    Regrip Planning Validation

The regrip planning strategy is evaluated using scenarios in which the initial config-
uration is not directly executable due to kinematic limitations. The results indicate
that the system correctly identifies such cases and determines an alternative con-
figuration that enables successful execution.
For all evaluated scenarios requiring regrip, the system selects a feasible orientation
and completes the required reorientation sequence without failure. The number of
regrip operations is minimized through the selection strategy, confirming that the
approach avoids unnecessary intermediate steps while maintaining feasibility.


6.2.4    Opposite-Face Bending Validation

The opposite-face bending workflow is validated through scenarios that require
bending operations on both sides of the workpiece. The evaluation confirms that
the system successfully performs the flip operation and continues execution using
the same planning pipeline.
After the flip, the system re-establishes a valid configuration and completes the re-
maining bending operations without inconsistencies. The results demonstrate that
multi-stage operations are handled seamlessly, without requiring separate control
logic for different workpiece orientations.
Overall, the functional validation confirms that all major components of the system
operate correctly and produce consistent results across a range of test conditions.
The evaluation demonstrates that the implemented system satisfies the core func-
tional requirements defined in Chapter 3.

all evaluated scenarios, the system successfully generated and executed complete
robot programs without requiring manual intervention.
The results demonstrate that the planning pipeline operates cohesively, with each
module providing valid input to subsequent stages. Orientation determination, grip
planning, regrip handling, and trajectory generation function together to produce a
complete and executable workflow. The system consistently adapts to varying initial
conditions, confirming its ability to handle non-deterministic workpiece placement.

Workspace constraints and singularity avoidance mechanisms prevent the genera-

the system adapts the trajectory to remain within valid bounds. This confirms that
the generated motions are both feasible and reliable for execution.

In addition to functional correctness and performance, the robustness of the system

The system is tested under scenarios designed to trigger potential failure modes, in-

or during execution.
For example, configurations with insufficient vacuum holding force are rejected dur-

collision-free operation in highly constrained scenarios. These limitations highlight
areas for future improvement and potential extension of the system.

The integration of orientation determination, grip planning, and regrip handling
allows the system to operate under a wide range of conditions. This represents a

The system also achieves a high degree of modularity, as demonstrated by the
layered architecture presented in Chapter 5. Each module performs a well-defined
function and contributes to the overall pipeline, supporting maintainability and ex-
tensibility.

Overall, the system addresses key gaps identified in the state of the art by providing

7 Conclusion and Future Work

7.1   Conclusion

This thesis presented the development and evaluation of an automated robotic sys-
tem for press brake sheet metal bending. The objective was to reduce manual
programming effort while improving adaptability and execution reliability in indus-
trial bending operations.
The analysis of the state of the art in Chapter 2 identified key limitations in exist-
ing approaches, including a strong dependence on manual programming, limited
adaptability to changing workpiece conditions, and a lack of integrated planning
frameworks. Based on these observations, a set of functional and non-functional
requirements was defined in Chapter 3, focusing on automation, flexibility, and
system robustness.
In Chapter 4, multiple solution concepts were evaluated, leading to the selection
of Concept B as the most suitable approach. This concept introduced a structured
planning pipeline that integrates orientation determination, grip planning, regrip
handling, and trajectory generation into a unified system.
Chapter 5 described the complete implementation of the selected concept. The
system was realised as a modular software architecture with clearly defined lay-
ers, enabling separation of concerns and maintainability. Key functionalities such
as constraint-based grip planning, automatic regrip determination, and structured
trajectory generation were implemented to support fully automated operation.
The evaluation presented in Chapter 6 demonstrated that the system successfully
fulfils the defined requirements. Functional validation confirmed that each compo-
nent of the planning pipeline operates correctly under varying conditions. System-
level evaluation showed that the integrated solution produces consistent and feasi-
ble robot programs without manual intervention.
A comparison with manual programming approaches highlighted a significant re-
duction in programming effort and adaptation time. Tasks that traditionally require
manual adjustment and reprogramming can be handled automatically by the sys-
tem, enabling faster and more consistent operation. This demonstrates that the
primary objective of reducing operator dependency and improving efficiency has
been achieved.
Overall, the developed system provides a systematic and adaptable solution for
robotic press brake bending. By combining automated decision-making with struc-
tured validation, the approach addresses key limitations of existing methods and
contributes to the advancement of flexible robotic manufacturing systems.

The main contributions of this thesis can be summarised as follows:

   • Development of a fully automated planning pipeline for press brake bending,
      integrating orientation determination, grip planning, regrip handling, and tra-
      jectory generation

   • Introduction of a constraint-based grip planning method that ensures both

   • Design of an adaptive regrip strategy that determines required reorientation
      dynamically without predefined sequences

   • Implementation of a structured trajectory generation approach that ensures
      smooth and feasible robot motion

   • Integration of validation mechanisms for safety and feasibility, including pre-
      execution checks and runtime monitoring

   • Demonstration of reduced programming effort and improved adaptability
      through comparison with manual programming approaches

These contributions collectively address the challenges identified in the state of the
art and provide a foundation for further development of automated robotic bending

7.3    Limitations

Despite the successful implementation and evaluation of the system, several limi-
tations remain.
The evaluation was conducted entirely within a virtual simulation environment.
While this enables controlled testing, it does not fully capture real-world factors
such as sensor noise, calibration inaccuracies, and mechanical tolerances.
In addition, the system does not include comprehensive collision detection or ad-
vanced dynamic modelling of contact interactions. These aspects are important for
ensuring safe operation in more complex or constrained environments.
Furthermore, the current implementation focuses on a specific class of sheet metal
geometries and bending operations. More complex geometries or multi-step indus-
trial processes may require additional extensions to the planning pipeline.


7.4    Future Work

Based on the identified limitations, several directions for future work can be pro-
posed.



                                                                                   91
Although the developed system achieves a functional and structured approach to
robotic sheet handling and bending, it is inherently constrained by a series of sim-
plifying assumptions introduced during the design phase. These constraints, while
beneficial for ensuring stability and predictability, limit the system’s applicability to
more complex and realistic industrial scenarios. Consequently, several avenues for
future work emerge, aimed at improving flexibility, intelligence, and robustness.
A key limitation of the current system lies in its strict assumption of rectangular
sheet geometries aligned with the global coordinate frame.          In practical manu-
facturing environments, components often exhibit irregular shapes and arbitrary
orientations. Future work should therefore focus on generalizing the geometric rep-
resentation to support non-rectangular profiles, including polygonal and free-form
geometries. Additionally, enabling the system to operate independently of fixed axis
alignment would significantly enhance its adaptability. This would require a more
advanced geometric abstraction layer capable of handling arbitrary edge definitions
and diverse feature types, including non-circular cutouts.
The bending capabilities of the system also present a significant opportunity for
advancement. The restriction to single, 90-degree bends per edge simplifies the
planning process but does not reflect the complexity of real-world fabrication tasks.
Future developments should introduce support for variable bend angles and multi-
ple bends along a single edge. More importantly, this necessitates the formulation
of an intelligent bend sequence planning framework capable of optimizing opera-
tion order, minimizing regrip requirements, and ensuring process feasibility. Such
a framework could leverage constraint-based optimization or heuristic search meth-
ods to generate efficient and manufacturable bending strategies.
From a robotics perspective, motion planning remains an area with considerable
scope for improvement. The current system demonstrates reduced efficiency when
handling certain orientations, particularly those involving significant rotational trans-
formations. Future work should integrate advanced motion planning techniques that
ensure collision-free, time-optimal trajectories. Furthermore, introducing adaptive
calibration mechanisms would allow the system to remain functional even when the
robot base or surrounding fixtures are repositioned, thereby reducing dependency
on manual reconfiguration. The incorporation of learning-based methods could fur-
ther enhance performance by enabling the system to refine its motion strategies
through repeated execution.
The gripping subsystem, currently limited to vacuum-based handling, represents an-
other constraint on system versatility. While effective for flat and uniform surfaces,
vacuum gripping is not universally applicable. Expanding the system to support
multiple gripping modalities, including mechanical and magnetic solutions, would
broaden its operational scope. In addition, the integration of sensor feedback, such
as force or slip detection, would enable real-time validation of grasp stability and
improve overall reliability.
Regrip operations in the present implementation are restricted to discrete rotational




                                                                                      92
increments, which limits the flexibility of part orientation. Future work should ex-
plore continuous orientation control and develop more sophisticated regrip planning
strategies aimed at minimizing intermediate handling steps. Streamlining opposite-
side operations into a unified workflow, rather than relying on separate scripts,
would further improve system efficiency and maintainability.
Safety considerations represent a critical gap in the current system. The absence
of collision detection and trajectory validation poses a significant limitation for de-
ployment in real-world environments. Future enhancements should prioritize the
integration of real-time collision avoidance mechanisms and safe motion planning
algorithms. Expanding the scope of the safety monitoring system to account for dy-
namic interactions between the robot, workpieces, and surrounding infrastructure
would also be essential.
Finally, the system’s reliance on fixed object identifiers and predefined configura-
tions reduces its robustness in dynamic environments. Future work should investi-
gate the integration of perception-driven approaches, such as vision-based object
recognition and tracking, to enable more flexible and autonomous operation. Addi-
tionally, incorporating error detection and recovery strategies would allow the sys-
tem to handle unexpected deviations more effectively, thereby improving overall
resilience.
In conclusion, future developments should aim to transition the system from a
rigid, rule-based framework toward a more adaptive and intelligent architecture.
By addressing limitations in geometry handling, bending flexibility, motion plan-
ning, gripping strategies, regrip operations, safety, and system adaptability, the
proposed solution can evolve into a more comprehensive and industrially viable
robotic automation platform.


7.5   Final Remarks

This thesis demonstrates that automated planning and execution of robotic press
brake bending is both feasible and beneficial. By reducing manual programming ef-
fort and improving adaptability, the developed system contributes to more efficient
and flexible manufacturing processes.
The presented approach provides a structured foundation for future research and
development in robotic bending and related automation tasks.
