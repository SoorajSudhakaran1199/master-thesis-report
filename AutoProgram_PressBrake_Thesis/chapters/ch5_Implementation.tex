\subsection {Layered Architecture Design and data flow}
\label{sec:layered_architecture}
The system adopts a layered architecture in which each module depends exclusively on module in the layered directly beneath it. This pattern is selected because the press brake automation context imposes three constraints that unstructured flat module design cannot satisfy simultaneals, independently testable constraints evaluation, maintenance safe replicability and structural enforced safety ordering.
\par Testability is achieved by enabling the module to be evaluated using synthetic pose data and YAML-based configuration inputs, without the need for an active WebSocket connection. This isolation is essential for verifying the orientational classification mathematics and grip feasibility calculations, because that computation cannot be inferred correctly from a live system alone. Replaceability is ensured by a modular architectural approach in which changes to the grip position algorithm are localized within the constraint evaluation layer. The planning and motion layers are structurally isolated and maintain no direct dependencies on constraint evaluation modules, thereby satisfying the requirements of NFR-02. Safety ordering is maintained through a structured design in which pre-execution safety validation is implemented in an independent layer executed prior to any motion commands. This approach ensures that future modifications cannot inadvertently reposition safety checks after motion initiation, thereby satisfying FR-07 and NFR-03.
\par Five distinct layers are defined within the system architecture, each with a clearly assigned responsibility. Layer 1 (Input and Configuration) is responsible for acquiring all required parameters from the input file, along with the operator’s bend-side selection, prior to the establishment of any WebSocket connection. Layer 2 (Geometry and Constraint Evaluation) performs the computation of geometric and physical constraints based on live tracker data, while remaining strictly limited to evaluation tasks and producing no motion commands. Layer 3 (Planning and Decision Logic) determines the overall execution strategy and coordinates the interaction between Layers 2 and 4, without directly generating motion instructions. Layer 4 (Motion Generation and Communication) serves as the exclusive interface for robot communication, generating LIN and PTP waypoints, converting them into JSON format, and transmitting them via an authenticated WebSocket connection. Layer 5 (Safety and Validation) is invoked at the beginning of every session and enforces a mandatory validation step, preventing further execution until explicit operator confirmation is obtained. The progression of data throughout a bending cycle follows a structured transformation across the system layers. At the initial stage, sheet geometry, bend-side selection, and TCP parameters are provided as input. These inputs are subsequently interpreted through geometric and constraint-based evaluation, where raw tracker pose data is converted into a validated pickup orientation and a feasible grip position. Based on this processed information, an appropriate execution strategy is established before being translated into motion commands, which are encoded in LIN-based JSON format and transmitted to the runtime environment.
\par The reliability of the overall process depends on a small number of critical transformation stages. Any inaccuracy introduced at these points propagates forward and affects all subsequent computations and decisions. In particular, the correct determination of pickup orientation is essential for successful workpiece acquisition. Likewise, the evaluation of grip feasibility ensures stable handling under dynamic conditions and prevents slippage during motion. During trajectory generation, a balance must be maintained between path fidelity and the limited processing capacity of the robot controller. This requires a controlled reduction of trajectory points while preserving the essential characteristics of the intended motion.

\subsection{Communication Stack, Authentication interface Specification}
\label{sec:communication_stack}

All runtime communication passes through the AnyRobot Interface, selected because it is the only supported external API for drag and bot. Direct ROS client libraries are excluded because they would couple the planning software to a specific ROS version, violating NFR-02 \cite{dragandbot_anyrobot_2025} \cite{quigley2009ros}. The AnyRobot Interface translates JSON over a persistent WebSocket channel into native ROS operations using the RosBridge v2 protocol, enabling the entire planning software to run in standard Python 3 without a ROS installation on the planning machine.
\par WebSocket (RFC 6455) is chosen over HTTP because it supports a persistent connection that allows continuous data transfer. In contrast, HTTP requires a new TCP connection for each request, which introduces a delay of approximately 3–15 ms per batch. When sending a trajectory of 400 points in batches of 50 commands, these delays accumulate to 24–120 ms. This added delay can cause the robot controller’s command buffer to run empty, leading to interruptions during motion execution. By maintaining a continuous connection, WebSocket avoids this overhead and ensures smooth and uninterrupted command transmission.
\par Figure \ref{fig:communication_architecture} presents an overview of the system communication architecture. The planning software establishes a persistent WebSocket connection to the robot controller via a defined network endpoint (e.g., \texttt{ws://192.168.x.x:9091}). Communication is organized through a set of dedicated interfaces, each responsible for a specific function within the system. The Ros Bridge v2 interface is used to transmit motion commands, while the \texttt{rosauth} service ensures secure authentication using the SHA-512 hashing algorithm. This method encodes authentication data into a non-reversible format, preventing the transmission of sensitive information in plain text. Motion trajectories are transmitted in batches via the \texttt{/command\_list} interface, and real-time object information is retrieved through \texttt{/dnb\_object\_manager/list\_objects}. Gripper control is performed using \texttt{/robot/set\_digital\_ios}, whereas object attachment and detachment are handled through the corresponding manager interfaces. User interactions, such as confirmations and prompts, are managed via the \texttt{human\_interaction/request\_hi} interface. The YAML configuration is not part of the runtime communication. It is loaded once during system initialization and shared across the relevant modules. This approach ensures that missing or incorrect parameters are detected early, before any communication with the robot is initiated \cite{python_ref_2024}.

\begin{figure}[htbp]
    \centering
    \includegraphics[width=\textwidth]{figures/communication_architecture.png}
    \caption{Communication architecture of the implemented system, illustrating the interaction between the planning software, the drag\&bot runtime environment, and the robot controller (adapted from~\cite{dragandbot_anyrobot_2025}).}
    \label{fig:communication_architecture}
\end{figure}

\par On connection establishment, the WebSocket client performs the rosauth SHA-512 authentication handshake, because the drag and bot WebSocket port is accessible to any process on the local network and an unauthenticated endpoint would allow arbitrary motion command injection. The MAC is computed by hashing with SHA-512 concatenation of the shared runtime secret, the interface identifier, destination, a fixed nonce, session timestamps, and the access level string.

The authentication token is computed based on the procedure defined in the drag\&bot AnyRobot Interface specification~\cite{dragandbot_anyrobot_2025}:

\begin{equation}
\mathrm{MAC} = \mathrm{SHA\text{-}512}(\text{secret} \parallel \text{id\_string} \parallel \text{dest} \parallel \text{nonce} \parallel \text{t} \parallel \text{level})
\label{eq:sha512_mac}
\end{equation}

\par SHA-512 is selected due to its strong cryptographic properties, as its 512-bit output makes pre-image and collision attacks computationally infeasible within the operational context of this application. The shared secret is stored as an environment variable to prevent exposure to version control systems. The concatenation order is strictly defined by the AnyRobot interface specification and must be followed precisely. Any deviation from this order results in a mismatch of the generated hash, causing the runtime system to reject the connection.

\FloatBarrier
Listing~\ref{lst:sha512_auth} presents an illustrative Python implementation of the authentication token computation described in Equation~\ref{eq:sha512_mac}, following the drag\&bot AnyRobot Interface specification~\cite{dragandbot_anyrobot_2025}.

\begin{lstlisting}[caption={Illustrative Python implementation of SHA-512-based authentication token computation following the drag\&bot AnyRobot Interface specification.}, label={lst:sha512_auth}]
import hashlib
import os

secret = os.getenv('RUNTIME_SECRET')

id_string = 'library'
dest = 'interface'
nonce = 'example_nonce'
timestamp = 0
role = 'user'

raw = secret + id_string + dest + nonce + str(timestamp) + role

mac = hashlib.sha512(raw.encode()).hexdigest()

auth_msg = {
    'operation': 'auth',
    'mac': mac,
    'nonce': nonce,
    'timestamp': timestamp,
    'role': role
}
\end{lstlisting}

\subsection{Configuration Architecture and YAML File Structure}
\label{Configuration Architecture }
The YAML configuration file serves as the central entry point for all process-related parameters and provides a flexible mechanism for adapting the system to different workpieces without requiring modifications to the underlying source code, thereby fulfilling NFR-02. At the beginning of each session, the file is parsed once, and the resulting configuration data is stored as a dictionary that is shared across all modules in Layers 2 to 4. The structure of the file is organized into six clearly defined top-level sections, each corresponding to a specific functional aspect of the system architecture, which supports clarity and maintainability.
YAML is selected over JSON primarily due to its support for inline comments. This allows engineers to document the meaning and physical relevance of individual parameters directly within the configuration file, eliminating the need to consult external documentation. To ensure robustness and security, the configuration is loaded using a safe parsing method, which prevents the execution of unintended code in the event that the file is modified or corrupted.
A key design decision concerns the handling of spatial consistency during the regrip process. Rather than defining approach and placement poses independently, all such poses are derived relative to a single reference pose defined for the orientation table. For example, the approach position is calculated by applying a fixed vertical offset to the placement pose. This design ensures that any change in the position of the orientation table requires only a single modification within the configuration file. In contrast, storing these poses independently could introduce inconsistencies: if the table position is updated but the corresponding approach position is not, the system may execute motions based on outdated spatial data. Such inconsistencies are particularly problematic because they may not be detected during configuration validation, as each parameter remains individually valid despite being collectively incorrect.

\subsection{Operator interface – interactive 3d sheet bending viewer}
\label{Operator interface – interactive 3d sheet bending viewer}

Operator input for each execution cycle is provided through an interactive three-dimensional sheet bending viewer developed in this work (hereafter referred to as the \textit{3D viewer}), rather than a conventional text-based interface. This design decision is primarily motivated by the spatial nature of bend side selection. By presenting the workpiece directly as a 3D model, the operator can identify relevant surfaces and orientations more intuitively than by relying on abstract side labels. In practice, this reduces the likelihood of incorrect selections while keeping the interaction simple, as the operator performs only visually guided inputs and the system handles the underlying computations.
\par The 3D viewer is implemented as a web-based application using Plotly Dash and renders the workpiece as an interactive mesh derived from the corresponding STL file. It operates as a local service and is integrated into the drag\&bot Operator Cockpit through the Custom URL panel mechanism. A new panel of type \textit{Custom URL} is added to the dashboard via the dashboard configuration interface, where the local viewer address is specified as the target. Once configured, the viewer is rendered as an embedded panel within the cockpit, allowing the operator to interact with the 3D mesh and associated controls without leaving the drag\&bot environment. The configuration is stored as part of the dashboard definition and remains available across sessions, ensuring a consistent setup for repeated operation.
\par This integration ensures that configuration, monitoring, and execution are performed within a single interface, eliminating unnecessary context switching and providing a more coherent workflow from the operator’s perspective. \section{Development and simulation Environment}
\label{sec:development_and_simulation_environment}

With the architectural foundation established in Section \ref{fig:system_architecture}, the implementation requires a defined environment in which all modules can be executed, tested, and validated before involving any physical robot. This section outlines the environment, including the drag and bot virtual simulation platform, the UR5e robot model with its TCP configuration, and the spatial zone classification used to divide the workspace and determine the execution path for each bending session.

\subsection{Simulation Platform, Robot Model, and TCP Configuration}
\label{Simulation Platform, Robot Model, and TCP Configuration}
The drag and bot platform is used as the primary environment for development, integration, and testing within this thesis, as it combines a virtual robot controller and the AnyRobot WebSocket Interface within a single system, eliminating the need for additional simulation tools or direct access to physical hardware \cite{dragandbot_anyrobot_2025}. All Python-based modules are implemented and validated within this environment. The platform operates on the same Ubuntu system as the planning software, enabling communication through the local loopback interface and avoiding timing variations caused by external network conditions. The planning software establishes a single authenticated WebSocket connection to ws://<local-ip>:9091, which is used to handle all command types, including motion execution, IO operations, object manager interactions, and operator HI dialog requests.
All session-related parameters are loaded from operator input during initialization and are explicitly passed to each module through function arguments. This approach ensures that dependencies remain transparent at the interface level and prevents modules from accessing outdated values from shared contexts. The same principle is consistently applied across all twenty-seven modules, with the configuration structure described in Section \ref{Configuration Architecture }.
\par Within the simulation environment, the Universal Robots UR5e is selected as the manipulator model, as it corresponds to the robot used in the physical KEBA press brake system and is supported by a validated kinematic representation in the drag and bot platform \cite{dragandbot_anyrobot_2025}. The UR5e provides six degrees of freedom, a maximum reach of approximately 850 mm, and a payload capacity of 5 kg, which are sufficient for handling the sheet metal workpieces considered in this implementation \cite{universalrobots_ur5e}. All motion targets generated by the planning software are evaluated against this kinematic model, allowing reachability limitations to be identified during simulation rather than during operation on the physical system.
\par The Tool Centre Point applied to all motion targets is defined through the drag and bot tool management entry project\_3\_tcp, in accordance with SR-03 in Section \ref{Software Platform and Tool requirement} and based on a system requirement specified by the company. This ensures a consistent reference for tool geometry so that all generated poses correspond to the actual gripper configuration. The TCP is defined using the ZYX Euler convention with the following offsets relative to the robot flange frame: x = 0.000 m, y = 0.034 m, z = 0.194 m, RZ = −90.0°, RY = −75.0°, RX = 0.0°. The Z offset of 194 mm represents the distance from the flange to the suction contact surface, while the Y offset of 34 mm reflects the asymmetric arrangement of the suction cups along the gripper. All coordinates computed by the planning software are defined at this TCP, allowing the drag and bot runtime to derive the corresponding flange pose through inverse transformation without requiring the planning layer to explicitly consider flange geometry. The TCP identifier project\_3\_tcp is stored in operator input, enabling flexible adaptation of the system. If adjustments are required in the future, the TCP can be updated by the user through parameter changes in the operator interface, without requiring modifications to the source code.

\subsection{Virtual Cell Layout and Spatial Zone Classification}
\label{Virtual Cell Layout and Spatial Zone Classification}
The drag and bot simulation cell includes the UR5e robot, the press brake model, the orientation table, and a sheet metal workpiece whose tracked pose (primary tracked sheet object) forms the basis for all geometric calculations in the planning software. In addition, a secondary sheet object is registered to support two-holder operation, allowing the system to track whichever workpiece is active during execution. All fixture positions, workspace limits, and zone thresholds defined in operator input module, which is aligned with the physical cell layout, ensuring that the simulation results correspond directly to the real system configuration.
\par At the start of each bending session, the spatial zone classifier retrieves the six-degree-of-freedom pose of the sheet from the object tracking service in the robot world coordinate frame. The origin of this frame is located at the robot base, with the X axis defined laterally and the Y axis longitudinally across the cell. Based on this reference, the XY position of the sheet centroid is evaluated using a threshold-based rule to assign the workpiece to one of four spatial zones. This process is performed automatically using live tracking data without operator input. The classification is defined relative to the robot base position, which must be correctly specified in the operator input configuration.
\par The XY plane is divided into four regions around the robot base. A centroid with negative X and positive Y is assigned to Zone 1 (rear-left), while negative X and negative Y correspond to Zone 2 (front-left). Positive X combined with positive Y defines Zone 3 (rear-right), and positive X with negative Y defines Zone 4 (front-right). The classification thresholds are set to ±10 mm in the X direction and ±50 mm in the Y direction. These asymmetric limits reflect the physical cell geometry and account for increased tracking uncertainty along the longitudinal axis \cite{Siciliano2016Robotics}. Zones 3 and 4 lie within the primary reachable workspace of the UR5e and therefore allow direct execution of the pickup and bending sequence from the nominal home configuration. In contrast, Zones 1 and 2 are in a region with limited reachability, requiring an automatic repositioning phase. In this phase, the robot moves to an automatically calculated predefined intermediate configuration within the reachable workspace, after which the standard bending sequence is executed. This repositioning is triggered by the classified zone and is performed without operator intervention. A subsequent tracking update verifies that the sheet lies within the reachable region before execution continues.
\par If the sheet centroid lies within the dead-band region defined by |x| < 10 mm or |y| < 50 mm, the classifier returns to an unresolved state. This occurs near the coordinate axes, where small tracking variations may lead to inconsistent zone assignment. To prevent incorrect execution, the system terminates the session and issues blocking notification instructing the operator to reposition the workpiece before restarting.

\par Having defined the simulation environment, robot model, TCP configuration, and zone classification, the following sections describe the functional subsystems in the execution order of a bending session, starting with safety validation, followed by orientation determination, grip planning, and trajectory generation.

\begin{algorithm}[htbp]
\caption{Spatial zone classification based on sheet centroid position}
\label{alg:zone_classification}
\begin{algorithmic}[1]
\State Retrieve sheet centroid coordinates $(x, y)$ in the robot world frame
\If{$|x| < x_{\text{th}}$ \textbf{or} $|y| < y_{\text{th}}$}
    \State Return \textit{unresolved zone}
\ElsIf{$x < 0$ \textbf{and} $y > 0$}
    \State Assign Zone 1
\ElsIf{$x < 0$ \textbf{and} $y < 0$}
    \State Assign Zone 2
\ElsIf{$x > 0$ \textbf{and} $y > 0$}
    \State Assign Zone 3
\Else
    \State Assign Zone 4
\EndIf
\end{algorithmic}
\end{algorithm}
Algorithm~\ref{alg:zone_classification} summarises the zone classification procedure in an abstract form. The classification is based on the sign of the centroid coordinates in the robot world frame, with a threshold-based dead-band region around the origin to prevent unstable assignments due to tracking noise. Implementation-specific details are omitted to comply with confidentiality constraints.

\section{Pre-Execution Safety Validation}
\label{Pre-Execution_Safety_Validation}

Safety validation is carried out before any motion is generated to ensure that unsafe conditions and infeasible configurations are identified prior to robot execution, in accordance with NFR-03, NFR-04, and NFR-05. The system incorporates three complementary mechanisms to achieve this: a fixture poses deviation check, a blocking operator confirmation dialog, and a runtime command error watcher. In addition, all trajectory waypoints are generated automatically and verified using robot kinematics to confirm reachability and feasibility before execution, preventing invalid motion commands from being issued.

\subsection{Fixture Pose Deviation Validation}
\label{Fixture_Pose_Deviation_Check}
The fixture pose deviation check retrieves the current poses of six critical fixtures from the drag\&bot object manager and compares them with reference poses obtained during the initial calibration of the cell. The monitored elements include the primary sheet object at the press brake, the finished-part position on the regrip table base and support, and the placement and attachment references at the flip station. These fixtures are treated as fixed references within the planning software, since all grip positions, trajectory waypoints, and placement operations are computed under the assumption that their positions remain unchanged. Any deviation from these reference poses can therefore result in motion targets that are geometrically valid but physically incorrect.

The deviation check is applied uniformly across all spatial zones. Each fixture is evaluated using both positional and orientation criteria. The positional deviation is computed as the Euclidean distance
\begin{equation}
\Delta_{pos} = \sqrt{(\Delta x)^2 + (\Delta y)^2 + (\Delta z)^2}
\end{equation}
and the orientation deviation is defined as
\begin{equation}
\Delta_{ang} = \max\left(|\Delta RZ|, |\Delta RY|, |\Delta RX|\right).
\end{equation}
A fixture is considered out of tolerance when $\Delta_{pos}$ exceeds 5~mm or $\Delta_{ang}$ exceeds 0.10~rad (5.7$^\circ$). The positional threshold is selected to remain below the minimum clearance used in grip planning, ensuring that fixture misalignment does not produce misleadingly valid grip configurations. The angular threshold corresponds to the minimum deviation that would affect the accuracy of the vacuum cup contact on the sheet surface.
The primary sheet object is evaluated using the same deviation criteria as all other fixtures. Since the planning software relies on the current sheet pose for all geometric computations, any displacement from the expected reference may lead to incorrect motion generation. Therefore, the sheet is included in the deviation evaluation in the same manner as other fixtures, and any detected deviation is treated as a potential configuration error.
If one or more fixtures exceed the defined thresholds, the system generates a structured warning that lists all affected fixtures using their generic labels, together with the measured positional and angular deviations. This warning is presented through a blocking HI dialog titled \textit{Fixture position warning}, which allows the operator to either continue with explicit caution or cancel the operation for further inspection. The operator’s decision is recorded, as the responsibility for accepting out-of-tolerance conditions remains with the human operator.
If a fixture is not detected in the object manager response, it is treated as missing and is automatically flagged regardless of zone classification.

\subsection{Operator Authorization and Runtime Error Monitoring}

The operator confirmation dialog is positioned as the first step in the planning orchestrator startup sequence, preceding all subsequent processes including fixture validation, visualization, and motion command transmission. The dialog enforces a mandatory decision: either initiate the automated workflow or cancel execution. This behavior is structurally enforced, as the orchestrator does not proceed until a response is received from the HI service. Consequently, execution cannot begin without explicit operator authorisation, ensuring compliance with safety requirements. If the operator selects cancel, the orchestrator terminates without issuing any command to the robot runtime.

\par In parallel with this confirmation step and all subsequent execution phases, a motion error watcher operates as a background subprocess. This ensures that execution errors are identified and communicated in real time.

\par The error watcher does not directly interrupt or terminate the orchestrator. This design ensures that execution anomalies do not pass unnoticed, while maintaining operator authority over subsequent actions.

\section{Workpiece Orientation Strategy}
\label{sec:workpiece_orientation}
Following pre-execution safety validation, the first geometric step in each bending cycle is the determination of a valid pickup orientation for the sheet. This is necessary because the sheet may be placed in arbitrary orientations within the workspace, while only a subset of these orientations is kinematically feasible for the target bending operation. The orientation strategy evaluates the tracked sheet pose, applies a structured selection process, and produces a validated pickup pose for subsequent grip planning.

\subsection{Zone-Based RZ Admissibility}
\label{Zone-Based RZ Admissibilitye}

The admissible range of the sheet rotation about the Z-axis is defined by a zone-dependent window $[RZ_{\min}, RZ_{\max}]$. This constraint reflects the limited rotational capability of the robot end-effector within different regions of the workspace. Since the reachable orientation range varies with the spatial position of the sheet, zone classification is performed prior to orientation evaluation. The corresponding admissibility window is retrieved from the configuration, ensuring that only feasible orientations are considered. This approach avoids selecting poses that appear valid geometrically but are unreachable during execution.

\subsection{Pickup Orientation Validation}
\label{sec:pickup_orientation_validation}

Before applying the orientation selection strategy, the tracked pose is validated to ensure that the gripper approaches the sheet from above. This is evaluated using the product $\cos(RX)\cdot\cos(RY)$. If the value is below $-0.10$, the tool Z-axis is oriented downward and no modification is required. Otherwise, a corrective transformation is applied:

\begin{equation}
RZ' = \mathrm{wrap}(RZ + 180^\circ), \quad
RY' = -RY, \quad
RX' = \mathrm{wrap}(RX + 180^\circ)
\end{equation}

This transformation ensures that the gripper is correctly aligned with the sheet surface without altering the pickup position.

\subsection{Three-Level Orientation Selection Strategy}

To ensure that a valid pickup orientation can be determined for any initial placement, a three-level selection strategy is employed. The strategy is evaluated sequentially in a strict priority order, and execution terminates as soon as a valid orientation satisfying the admissibility constraints is identified. This approach guarantees robustness against arbitrary initial sheet orientations while maintaining preference for geometrically consistent and kinematically favorable configurations.

The workpiece is defined with four reference faces established during system commissioning, each associated with a fixed angular offset about the sheet’s local vertical axis. These faces provide a structured reference for interpreting the tracked orientation. The offsets correspond to $0^\circ$, $180^\circ$, $+90^\circ$, and $-90^\circ$ relative to the reference face. By compensating for these offsets, the system can normalise any detected orientation into a common reference frame, enabling consistent evaluation across different initial conditions.

\paragraph{Level 1: Reference-Face Equivalent Orientation}

At the highest priority level, the tracked orientation is converted into its reference-face equivalent by removing the face-specific angular offset. This is achieved by applying an inverse rotation about the sheet’s local Z-axis:

\begin{equation}
R_{\text{new}} = R_{\text{raw}} \cdot R_z(-d)
\end{equation}

where $d$ represents the angular offset associated with the detected face. The resulting rotation matrix is then decomposed into ZYX Euler angles using:

\begin{equation}
R = R_z(\alpha)\cdot R_y(\beta)\cdot R_x(\gamma)
\end{equation}

\begin{equation}
RZ = \operatorname{atan2}(R_{10}, R_{00}), \quad
RY = \arcsin(-R_{20}), \quad
RX = \operatorname{atan2}(R_{21}, R_{22})
\end{equation}

The computed $RZ$ value is then evaluated against the zone-specific admissibility window $[RZ_{\min}, RZ_{\max}]$. If the orientation lies within this range, it is selected as the pickup pose. This level is preferred because it aligns all configurations to a common reference frame, resulting in more predictable motion generation and reduced trajectory complexity.

\paragraph{Level 2: Detected-Pose Evaluation}

If the reference-face equivalent orientation falls outside the admissible range, the strategy proceeds to evaluate the raw tracked orientation directly. This level accounts for cases where the sheet is already positioned within a valid orientation relative to the robot workspace, and the reference-face conversion would unnecessarily shift it outside the admissible window.

The raw $RZ$ value is therefore checked against the same admissibility limits. If it satisfies the constraint, the raw pose is accepted as the pickup orientation. This level preserves valid initial configurations without enforcing additional transformations.

\paragraph{Level 3: Inverted-Pose Fallback}

If both the reference-face equivalent and the raw orientation fail to satisfy the admissibility condition, a fallback orientation is generated by applying a $180^\circ$ inversion:

\begin{equation}
RZ' = \mathrm{wrap}(RZ \pm 180^\circ), \quad
RY' = -RY, \quad
RX' = -RX
\end{equation}

This transformation effectively rotates the sheet about its vertical axis while reversing its orientation about the horizontal axes. The inverted pose expands the set of reachable configurations and ensures that a pickup orientation can always be produced, even when the initial pose lies outside the calibrated admissible region.

However, since this orientation may not strictly satisfy the predefined admissibility constraints, it is marked with an \textit{admissibility unconfirmed} flag. This flag is propagated to downstream modules, including the grip planner and trajectory generator, allowing them to apply additional safety margins or conservative motion constraints when executing the operation.

\begin{algorithm}[htbp]
\caption{High-level orientation selection strategy}
\label{alg:orientation_selection}
\begin{algorithmic}[2]
\State Retrieve tracked sheet pose and active zone
\State Load zone-specific admissibility window $\{R_Z^{\min}, R_Z^{\max}\}$
\State Validate pickup orientation and apply downward-tool correction if required
\State Compute reference-face equivalent orientation
\If{reference-face equivalent satisfies admissibility window}
    \State Select reference-face orientation
    \State Set admissibility status to confirmed
\ElsIf{detected orientation satisfies admissibility window}
    \State Select detected orientation
    \State Set admissibility status to confirmed
\Else
    \State Compute inverted orientation
    \State Select inverted orientation
    \State Set admissibility status to unconfirmed
\EndIf
\State Forward selected orientation and admissibility status to downstream planning modules
\end{algorithmic}
\end{algorithm}
Algorithm~\ref{alg:orientation_selection} summarises the implemented orientation strategy at an abstract level. It reflects the execution order of the internal software pipeline without exposing implementation-specific source code, which is omitted due to confidentiality constraints.

\paragraph{Strategy Outcome}

The three-level strategy guarantees that a pickup orientation is always determined while prioritising configurations that are both kinematically feasible and geometrically consistent. By enforcing a strict evaluation order and incorporating a controlled fallback mechanism, the approach balances robustness and operational safety. The final selected orientation, together with its admissibility status, is forwarded to subsequent planning stages for execution.

\section{Workpiece Handling and Gripper Control}

Once a valid pickup orientation has been determined, the system must establish a reliable physical interaction between the gripper and the sheet while maintaining consistency between the physical robot state and the virtual simulation. Any mismatch between the vacuum state of the gripper and the attachment state in the simulation would lead to incorrect pose propagation and invalid trajectory computation in subsequent stages. This consistency is ensured through two coordinated mechanisms: digital IO control of the vacuum gripper and kinematic attachment within the simulation environment

\subsection{Vacuum Gripper Digital IO Sequence}
The vacuum gripper is actuated using two digital output signals on the UR5e controller, mapped to DO[0] and DO[1] in the drag\&bot IO management system. DO[0] activates the vacuum by closing the suction valve, while DO[1] releases the vacuum by opening the exhaust valve. These signals are strictly mutually exclusive; at no point are both outputs activated simultaneously, as this would result in conflicting pressure states and potential hardware damage.
\par Control commands are issued via the \texttt{/robot/set\_digital\_ios} service of the AnyRobot Interface, which accepts structured IO commands specifying the target pin and its Boolean state. To ensure reliable gripping, a dwell period of 250~ms is applied after activating the vacuum. This delay allows sufficient time for the suction cups to establish a stable seal with the sheet surface\cite{mahler2017dexnet} . Initiating further operations before this stabilization would result in a virtual attachment being applied to a physically unstable grasp.
A secondary delay of 150~ms is introduced after each IO operation to ensure that the state transition propagates through the ROS communication layer before subsequent commands are executed. This prevents race conditions between command execution and system state updates.

\subsection{Kinematic Object Attachment and Detachment}

In the simulation environment, the physical coupling between the gripper and the sheet is represented through kinematic attachment. When the gripper successfully grasps the sheet, the corresponding object is attached to the robot’s tool frame, ensuring that all subsequent robot motions are reflected in the sheet’s pose. Conversely, when the vacuum is released, the object is detached and remains fixed in its last known position.
\par Attachment is performed using the \texttt{/dnb\_object\_manager/attach} service without enforcing a position override. This avoids introducing discontinuities between the tracked object pose and the simulated state, as the tracker may not exactly match the instantaneous tool frame position. Position override is reserved exclusively for controlled initialization procedures where explicit alignment is required.
\par Detachment is executed through the \texttt{/dnb\_object\_manager/detach} service using the same reference frame. To maintain consistency, attachment and detachment operations are always executed in a fixed sequence together with the corresponding IO commands:

\begin{itemize}
\item Grasp sequence: vacuum ON $\rightarrow$ dwell $\rightarrow$ attach
\item Release sequence: vacuum OFF $\rightarrow$ dwell $\rightarrow$ detach
\end{itemize}

This sequence is encapsulated within centralized helper routines that are invoked by all modules performing grasp or release actions. Centralizing this logic ensures that the physical and virtual states remain synchronised at all times and prevents invalid states where the vacuum is active without a corresponding attachment, or vice versa.

\section{Grip Position Planning and Feasibility Validation}
\label{sec:grip_planning}

With a valid pickup orientation and gripper control mechanism established, the system must determine feasible suction cup placement on the sheet surface. Arbitrary placement is not acceptable, as it may violate geometric constraints or fail to provide sufficient holding force during transport. The grip planner therefore evaluates both geometric and physical constraints to ensure a stable and executable grip configuration.

\subsection{Sheet Geometry and Hole Detection}
\label{subsec:sheet_geometry_holes}

The sheet is modelled as a rectangular surface with uniform mass distribution, defined by its length, width, thickness, and mass from the configuration. When the mass is not explicitly provided, it is estimated from the sheet volume and the configured material properties.

In addition to the outer boundary, circular hole regions are identified from the STL mesh using the geometry analysis stage described previously. Each hole is represented by its center position and radius in the sheet coordinate frame. These hole regions are incorporated into grip planning so that candidate cup positions overlapping any hole are excluded, since such placements would prevent the formation of a reliable vacuum seal and would therefore compromise workpiece retention during transport.

\subsection{Vacuum Holding Force Validation}
\label{subsec:vacuum_force_validation}

For each candidate grip configuration, the planner evaluates whether the available vacuum force is sufficient to retain the sheet under gravitational and dynamic loading conditions. The contact area of a single suction cup is defined as

\begin{equation}
A_{\text{cup}} = \pi \left(\frac{d}{2}\right)^2
\label{eq:cup_area}
\end{equation}

The available vacuum holding force across $n$ cups is then given by

\begin{equation}
F_{\text{vacuum}} = n \cdot \Delta P \cdot A_{\text{cup}} \cdot \eta
\label{eq:vacuum_force}
\end{equation}

The required holding force is computed as

\begin{equation}
F_{\text{required}} = SF \cdot m \cdot \sqrt{a_{xy}^2 + (g + a_z)^2}
\label{eq:required_force}
\end{equation}

A configuration is considered feasible only when $F_{\text{vacuum}} \geq F_{\text{required}}$. This validation ensures that only physically stable grip configurations are passed to the subsequent candidate evaluation stage.

\subsection{Grip Candidate Search and Selection}
\label{subsec:grip_candidate_search}

Candidate suction cup positions are generated using a multi-resolution grid-based search over the sheet surface. The search begins with a coarse discretization and progressively refines candidate positions in feasible regions to improve placement accuracy. In addition to grid-based sampling, supplementary candidate positions are generated near hole boundaries to maximize usable gripping area while maintaining clearance constraints.

Each candidate position is evaluated against geometric constraints. The cup center must maintain a minimum distance from sheet edges, avoid overlapping with hole regions including the configured clearance buffer, and satisfy spacing constraints in the case of multi-cup configurations. In the two-cup configuration, candidate positions are evaluated as pairs, and the spacing between cup centers is constrained to ensure an adequate grip span across the workpiece.

All candidates are first filtered using geometric constraints and vacuum holding feasibility before being evaluated by a scoring function. The scoring considers edge clearance, hole clearance, and center bias, while in the two-cup configuration the span between cups is additionally maximized to improve stability during transport. The implemented search procedure is summarized in Algorithm~ \ref{alg:grip_planning}.

\begin{algorithm}[htbp]
\caption{Grip position planning procedure}
\label{alg:grip_planning}
\begin{algorithmic}[3]
\State Load sheet geometry and gripping parameters
\State Validate vacuum holding feasibility
\State Generate candidate positions on the sheet surface
\State Filter candidates using geometric constraints
\If{two-cup configuration}
    \State Evaluate candidate pairs
\EndIf
\State Score feasible candidates
\State Select best configuration
\State Compute A1, B1, R1 waypoints
\State Forward result to trajectory generation
\end{algorithmic}
\end{algorithm}
The highest-scoring candidate configuration is selected as the final grip position. Based on this position, three key waypoints are computed: the approach pose (A1), the attachment pose (B1), and the retreat pose (R1). These waypoints are derived from the selected grip position together with the sheet surface height and tool geometry offsets, ensuring a consistent and collision-free pickup sequence.

\section{ Regrip Planning and Execution}
\label{sec:regrip}

Even when a valid pickup orientation and a feasible grip position are established, the current gripper configuration may not allow the robot to reach the target bending pose. This occurs when the required flange pose lies outside the robot workspace, or when kinematic constraints such as joint limits or singularity proximity prevent a feasible motion solution. To address this, the system implements an automatic regrip planning strategy that determines the required reorientation dynamically. This strategy directly addresses the limitations identified in the State of the Art by enabling automatic determination of regrip requirements within an industrially applicable framework.
%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%
\subsection{Regrip Decision Strategy}

In contrast to conventional approaches that rely on predefined regrip steps, the proposed system evaluates a discrete set of candidate workpiece orientations and selects a configuration that satisfies kinematic feasibility. This enables the system to determine both the required orientation and the number of regrip steps automatically.

The candidate set consists of discrete orientation increments that correspond to physically achievable rotations on the orientation table. For each candidate orientation, the system performs the following sequence:

\begin{itemize}
\item Update the workpiece pose according to the candidate orientation
\item Determine a valid pickup orientation using the orientation strategy described in Section\ref{sec:workpiece_orientation}
\item Compute feasible grip positions using the grip planner described in Section \ref{sec:grip_planning}
\item Evaluate kinematic feasibility using inverse kinematics and trajectory validation
\end{itemize}

A candidate orientation is accepted when all feasibility checks are satisfied. The evaluation follows a heuristic selection strategy, where the first feasible orientation is selected to ensure computational efficiency suitable for real-time execution. The number of required regrip steps is implicitly determined based on the difference between the current orientation and the selected feasible orientation. This approach avoids unnecessary reorientation operations while ensuring that the final configuration is executable within the robot workspace.

\begin{algorithm}[htbp]
\caption{ Regrip Orientation Selection}
\label{alg:auto_regrip}
\begin{algorithmic}[1]
\State Define candidate orientation set
\For{each candidate orientation}
    \State Compute updated workpiece pose
    \State Evaluate pickup orientation
    \State Compute grip configuration
    \State Check kinematic feasibility
    \If{feasible}
        \State Select orientation
        \State \textbf{break}
    \EndIf
\EndFor
\State Determine required number of regrip steps
\end{algorithmic}
\end{algorithm}
Algorithm~\ref{alg:auto_regrip} summarizes the automatic decision process. The evaluation is performed using the existing planning pipeline, ensuring consistency with orientation determination, grip planning, and trajectory generation.

\subsection{Regrip Execution Sequence}

Once a feasible orientation is selected, the system executes a structured regrip sequence to physically realize the required reorientation. The execution is based on a six-step cycle designed to ensure safe and consistent handling of the workpiece:

\begin{enumerate}
\item Transport the workpiece from the bending station approach position to the orientation table deposit position while maintaining the current grip.
\item Release the workpiece by deactivating the vacuum and performing kinematic detachment.
\item Move the robot to a retract standoff position to ensure collision-free clearance.
\item Re-approach the workpiece at the updated orientation and perform the grasp sequence.
\item Repeat the regrip cycle if multiple orientation adjustments are required.
\item Perform the final grasp and return the workpiece to the bending station.
\end{enumerate}

Each motion segment is executed using smooth trajectory profiles to minimize dynamic loads on the vacuum gripper and ensure stable handling. Intermediate standoff positions are used to guarantee collision-free transitions between grasping and releasing operations.

\subsection{System Integration and Configuration}

The regrip execution sequence operates within the existing motion framework and uses configuration-defined target positions, including the deposit position, re-grasp position, retract standoff, and bending station approach position. These parameters define the physical layout of the cell but do not determine the number of regrip steps.

The decision to trigger a regrip is handled by the planning orchestrator, which evaluates the feasibility of the current configuration based on orientation admissibility and kinematic constraints. The separation between decision-making and execution ensures modularity and allows the regrip planning strategy to be extended without modifying the motion execution layer.

Compared to configuration-driven approaches, the proposed method improves adaptability by determining the minimum required number of regrip steps dynamically. At the same time, it maintains computational efficiency by evaluating a structured set of candidate orientations rather than performing full global optimization. This makes the approach suitable for industrial deployment, where predictable and robust behavior is required.

\section{Opposite-face Bending Workflow}
\label{sec:opposite_side}

After completing all primary-side bending operations, the system evaluates whether additional bends are required on the opposite face of the sheet. These opposite-side bends cannot be executed directly from the initial pickup configuration, as the required face is not accessible to the press brake tool. Therefore, the sheet must be reoriented through a controlled flip operation before continuing the bending process.

\subsection{Pre-Flip Verification and Transition Correction}

Before initiating the flip sequence, the system verifies that the current sheet pose matches the expected starting configuration. This verification is performed using a wrap-safe six-degree-of-freedom pose comparison. A position tolerance of 2~mm and an angular tolerance of 1$^\circ$ define the acceptable deviation.

This check is necessary because the sheet may have undergone regrip operations during the primary bending sequence. If the current pose deviates from the expected reference, subsequent motions would be computed from an incorrect starting configuration.

If the verification fails, a transition correction step is executed. The system first restores the reference orientation using the orientation strategy described in Section~5.5. It then performs a controlled pickup and repositioning sequence to re-establish a consistent and verified coupling between the robot and the sheet.

If the verification is successful, the correction step is skipped, and the system proceeds directly to the flip sequence.

\subsection{Sheet Flip Sequence and Opposite-face bending Execution}

The flip operation is performed using a dedicated flip station within the robotic cell. The sheet is transferred through two predefined reference positions to achieve physically feasible reorientation.

First, the robot transports the sheet to the flip station placement position while maintaining the current grasp. The sheet is then released in a controlled manner. The robot subsequently moves to an intermediate position and re-approaches the sheet from the opposite side, establishing a new grasp that results in the flipped orientation.

This two-stage transfer is used instead of a direct in-gripper rotation. A direct rotation would require a large continuous motion that is not kinematically feasible within the robot workspace and may violate collision constraints.

After the flip operation, the sheet is oriented such that the previously inaccessible face is now aligned with the press brake tool. The system then applies the same validation pipeline used for primary-side bending. This includes zone classification, orientation determination, grip position planning, and trajectory generation.

Using the same validation hierarchy ensures consistent behaviour across both primary and opposite-side operations. It also avoids introducing separate handling logic for different sheet faces.

Figure- \ref{fig:opposite_face_flip} illustrates the complete opposite-side bending workflow, including pre-flip verification, optional transition correction, flip execution, and subsequent bending operations.

After completing all opposite-side bends, any remaining staged operations are executed using the existing multi-stage handling framework. The system then proceeds to the final unloading sequence.

\section{Trajectory Generation}
\label{sec:trajectory}

Trajectory generation transforms a validated target pose into executable robot motion. The input to this stage is an ordered sequence of tool centre point (TCP) poses obtained from upstream planning modules such as grip planning, regrip execution, and opposite-face handling. Each pose defines the desired position and orientation of the end-effector in the robot world frame. The trajectory generator connects these poses through a smooth and feasible motion that can be executed by the robot controller.

Rather than executing a direct transition between poses, the system constructs a continuous trajectory represented by intermediate waypoints. These waypoints define the path followed by the end-effector and ensure smooth motion from the start to the target configuration.

\subsection{Three-Phase LIN Trajectory Structure}

Each trajectory is constructed using a three-phase structure: lift, lateral travel, and descent. In the lift phase, the TCP is raised vertically to a predefined safe height to ensure clearance from the workpiece and surrounding environment. In the lateral travel phase, the robot moves towards the target position at this safe height. During this phase, the orientation is constrained to limit the $RY$ angle, reducing proximity to wrist singularities. In the descent phase, the TCP moves from the safe height to the final target pose, applying the required orientation for task execution.

To separate orientation changes from contact motion, an intermediate rotation pose is introduced above the target. This ensures that large orientation adjustments are completed before the final descent, improving kinematic feasibility near the target.


\subsection{Waypoint Generation and Interpolation}

The trajectory between successive poses is generated through interpolation in Cartesian space. For a start pose $\mathbf{T}_s$ and a target pose $\mathbf{T}_t$, the translational component is interpolated using

\begin{equation}
\mathbf{p}(\lambda) = (1 - \lambda)\mathbf{p}_s + \lambda \mathbf{p}_t
\end{equation}

where $\lambda \in [0,1]$ is the interpolation parameter. The orientation is interpolated using spherical linear interpolation (SLERP) in quaternion space, ensuring smooth rotational motion along the trajectory \cite{Wang2022NURBSSlerp}.

To achieve smooth velocity transitions, the interpolation parameter follows a minimum-jerk profile

\begin{equation}
s(u) = 10u^3 - 15u^4 + 6u^5
\end{equation}

which produces zero velocity and acceleration at the start and end of each motion segment \cite{Sharkawy2021MinimumJerk}.

By sampling this progression at discrete intervals, a sequence of intermediate TCP waypoints is generated that approximates the continuous trajectory \cite{Biagiotti2008Trajectory}.

\begin{lstlisting}[language=Python, caption={Illustrative waypoint generation using minimum-jerk interpolation}, label={lst:minjerk_waypoints}]
def min_jerk(u):
    return 10*u**3 - 15*u**4 + 6*u**5

waypoints = []
for k in range(N):
    u = k / (N - 1)
    s = min_jerk(u)
    p = (1 - s) * p_start + s * p_target
    r = slerp(r_start, r_target, s)
    waypoints.append((p, r))
\end{lstlisting}

The number of waypoints depends on the path length and a predefined step size, ensuring a balance between trajectory smoothness and computational efficiency.

\begin{lstlisting}[language=Python, caption={Illustrative determination of waypoint count based on path length}, label={lst:waypoint_count}]
distance = euclidean_dist(p_start, p_target)
N = max(2, math.ceil(distance / delta_s_max))
samples = [k / (N - 1) for k in range(N)]
\end{lstlisting}

\subsection{Kinematic Mapping and Joint Execution}
Each interpolated TCP waypoint is converted into a corresponding robot configuration using inverse kinematics. This mapping determines the set of joint angles required to achieve the desired end-effector pose. For each waypoint, a feasible joint solution is selected based on continuity with the previous configuration, ensuring smooth transitions and avoiding abrupt joint changes.

As the robot executes the sequence of configurations, all six joints evolve continuously. This produces a smooth end-effector motion that follows the interpolated Cartesian path from the initial pose to the final target pose.

\subsection{Workspace Constraints and Singularity Handling}

To ensure feasibility, each waypoint is evaluated within the robot’s workspace. The TCP pose is transformed into the corresponding flange pose, and the position is checked against the cylindrical workspace limits defined by maximum reach and vertical bounds. If a waypoint exceeds these limits, it is projected onto the nearest valid boundary before further processing.

Singularity avoidance is addressed during the lateral travel phase by limiting the allowable orientation range. This prevents the robot from entering configurations that would result in unstable joint motion or excessive joint velocities. The full target orientation is applied only near the final approach, where the robot is in a more stable configuration.


\subsection{Motion Execution and Path Reduction}

The interpolation process produces a dense set of waypoints. To ensure compatibility with the robot controller, the trajectory is reduced to a manageable number of points by retaining only those that exceed predefined positional or rotational thresholds. This preserves the shape of the trajectory while reducing communication overhead.

The resulting waypoint sequence is transmitted to the robot controller as a series of linear motion commands. The controller executes these commands using motion blending, allowing smooth transitions between consecutive waypoints without stopping at each intermediate position. As a result, the robot follows a continuous trajectory that approximates the planned TCP path.

The overall trajectory generation process forms a deterministic pipeline: validated TCP poses are interpolated into intermediate waypoints, mapped into joint configurations through inverse kinematics, adjusted for workspace constraints, and executed by the robot as a continuous motion from the start to the target pose.

\section{System Integration, Execution Pipeline, and Conclusion}
\label{sec:system_pipeline}

The developed system operates as an integrated pipeline that transforms operator-defined bending inputs into fully executed robot motion. This pipeline coordinates multiple modules, including task planning, trajectory generation, and execution control, ensuring consistent and deterministic system behaviour.

The execution begins with the operator defining the bending configuration, including the selection of bend sides and associated parameters. These inputs are processed by the planning module, which determines the sequence of operations required to complete the bending task. This stage establishes the order of primary-side bends, identifies necessary regrip operations, and determines whether opposite-face handling is required.

Following planning, the system enters the primary bending phase. Each bend is executed sequentially using validated motion strategies. For every operation, a feasible grip position is determined, orientation constraints are applied, and a corresponding trajectory is generated. Regrip sequences are performed when required to maintain stable and feasible grasp configurations throughout the process.

If bending operations on the opposite face are requested, the system transitions to the flip workflow. The sheet is transferred through the flip station, reoriented, and reattached so that the previously inaccessible face becomes available. The same planning and execution principles used in the primary phase are then applied, ensuring consistent handling across both sides of the workpiece.

All robot motion within these stages is executed through the trajectory generation pipeline described in Section~\ref{sec:trajectory}. Each planned TCP pose is converted into intermediate waypoints, mapped to joint configurations through inverse kinematics, and executed as continuous motion using linear interpolation and blending. This ensures smooth and stable end-effector movement throughout the bending process.

After completion of all bending operations, the system performs the post-process unload as part of the execution pipeline. The robot attaches to the finished workpiece, transports it to the designated buffer station, and releases it in a controlled manner. The robot then moves to a predefined safe start pose, restoring the system to a known configuration and ensuring safe operator access to the workspace.

The overall system therefore follows a structured execution pipeline:

\begin{itemize}
    \item Operator input and bend configuration
    \item Planning of bending sequence and regrip strategy
    \item Execution of primary-side bending operations
    \item Regrip handling between operations
    \item Opposite-face handling via flip workflow (if required)
    \item Trajectory generation and motion execution
    \item Post-process unload and system reset
\end{itemize}

\subsection{Conclusion}

\section{System Reliability and Failure Mode Analysis}
\label{sec:fmea}

To evaluate the robustness of the developed robotic bending system, a Failure Mode and Effects Analysis (FMEA) is conducted. This analysis identifies potential failure modes within the system, evaluates their impact on operation, and considers mitigation strategies implemented in the system design.

FMEA is a structured approach used to assess system reliability by analysing three key factors: severity (S), occurrence (O), and detectability (D). The combined effect of these factors is quantified using the Risk Priority Number (RPN), defined as

\begin{equation}
\mathrm{RPN} = S \times O \times D
\end{equation}

where each parameter is rated on a qualitative scale, typically from 1 (low) to 10 (high). Higher RPN values indicate higher priority risks that require mitigation.

\subsection{Mitigation Strategies}

Several design measures are incorporated to reduce the likelihood and impact of these failures. Grip stability is ensured through controlled attachment sequences and orientation constraints. Trajectory feasibility is maintained through workspace validation and structured motion planning. Singularity risks are reduced by limiting orientation changes during lateral motion and separating rotational adjustments from the final descent phase.

\subsection{Discussion}

The FMEA results indicate that the most critical risks are associated with pose accuracy and trajectory feasibility, as reflected by higher RPN values. These risks are mitigated through a combination of constraint-based planning, controlled motion generation, and staged execution.

Overall, the system demonstrates a balanced design in which high-severity failure modes are either low in occurrence or effectively mitigated through detection and control mechanisms. This supports reliable operation of the robotic bending process while maintaining safety and repeatability.

The presented analysis highlights that the integration of planning, trajectory generation, and execution control not only enables automated bending but also contributes significantly to system robustness.
