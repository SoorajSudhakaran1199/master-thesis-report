\section{Introduction and Scope}
\label{sec:introduction_and_scope}
The product development phase translates the selected concept into a fully realised technical system. Based on the structured concept evaluation presented in Section~\ref{sec:concept-decision-wsm}, Concept~B was selected for implementation, as it provides a feasible and systematic solution to the research problem while satisfying the defined functional, non-functional, and software platform requirements outlined in Chapter~\ref{ch:system-concept-methodology}. In particular, Concept~B enables automatic robot program generation, integrated constraint validation, and seamless operation within the drag\&bot runtime environment.
 
The objective of this chapter is to present the complete implementation of Concept~B as an executable software system for automated press brake sheet metal bending. The system generates robot programs automatically from geometric input parameters and configuration data, eliminating manual waypoint definition and reducing operator intervention. The implementation focuses on ensuring deterministic behaviour, repeatability, and safe execution through structured validation and modular system design.
The implementation is structured around four key domains. The chapter first presents the system architecture together with the communication, configuration, and operator interface structures. It then describes the development and simulation environment and the functional subsystems in execution order, including safety validation, orientation determination, grip planning, regrip handling, opposite-side bending, and trajectory generation. The chapter concludes with a Failure Mode and Effects Analysis and a requirement-to-implementation traceability mapping.

The system operates entirely within the drag\&bot virtual simulation environment. Communication with the robot runtime is established through the AnyRobot Interface using an authenticated \ac{websocket} connection, ensuring compliance with SR-01 and SR-02. 
 
All process parameters are loaded from a central \ac{yaml} configuration file at the beginning of each execution cycle. This enables adaptation to different workpiece geometries without modifying the source code, satisfying NFR-02. 
 
Operator input is provided through an interactive 3D sheet bending viewer integrated into the drag\&bot operator cockpit. This interface improves usability and reduces the likelihood of incorrect input selection. 
 
Ubuntu Linux is used as the development platform due to its compatibility with \acs{ros}-based systems and stable integration with the drag\&bot environment~\cite{quigley2009ros}.

Figure~\ref{fig:overall_system_workflow} illustrates the overall system architecture and the sequence of operations from session initialization to bending execution.
 
The remainder of this chapter is organised as follows. Section~\ref{sec:system_architecture} presents the system architecture, including the layered design, module organisation, and data flow. This is followed by the communication stack, configuration architecture, and operator interface. The simulation environment and spatial zone classification are then described. Subsequently, each functional subsystem is presented in execution order, including pre-execution safety validation, workpiece orientation strategy, grip planning, regrip handling, opposite-side bending, and trajectory generation. The chapter concludes with a Failure Mode and Effects Analysis and a requirement-to-implementation mapping.
The overall execution pipeline of the system is illustrated in Figure~\ref{fig:overall_system_workflow}. The workflow begins with configuration selection and parameter initialisation, followed by pre-execution safety validation to ensure that all operating conditions are within acceptable limits. Based on the detected sheet pose, a valid pickup orientation is determined, after which feasible grip positions are computed using constraint-based evaluation. If a direct execution is not possible, the system automatically applies regrip strategies to achieve a reachable configuration. The validated task sequence is then converted into motion commands and executed by the robot. The process iterates over all required bends and includes additional handling for opposite-side operations before concluding with the final unloading stage. This structured workflow ensures deterministic execution and consistent integration of all functional subsystems within the automated bending process.

\section{System Architecture}
\label{sec:system_architecture}
\subsection{Layered Architecture Design and Data Flow}
\label{sec:layered_architecture}
The system adopts a layered architecture in which each module depends exclusively on the module in the layer directly beneath it. This architectural pattern is selected because the press brake automation context imposes three key constraints that cannot be satisfied by an unstructured design: independent testability of constraint evaluation, maintainability and safe replaceability of components, and strict enforcement of safety ordering.
Testability is achieved by enabling modules to be evaluated using synthetic pose data and \acs{yaml}-based configuration inputs, without requiring an active \ac{websocket} connection. This isolation is essential for verifying orientation classification and grip feasibility computations, which cannot be reliably validated from live system behaviour alone.
 
Replaceability is ensured through modular separation, where modifications to the grip planning algorithm are confined to the constraint evaluation layer. The planning and motion layers remain independent of these modules, supporting maintainability and satisfying NFR-02.
 
Safety ordering is enforced structurally by implementing pre-execution validation in a dedicated layer that is executed prior to any motion generation. This guarantees that safety checks cannot be bypassed or reordered, satisfying FR-07 and NFR-03.


Five distinct layers are defined within the system architecture, each with a clearly assigned responsibility. Layer 1 (Input and Configuration) is responsible for acquiring all required parameters from the input file, along with the operator’s bend-side selection, prior to the establishment of any \ac{websocket} connection. Layer 2 (Geometry and Constraint Evaluation) performs the computation of geometric and physical constraints based on input pose data, while remaining strictly limited to evaluation tasks and producing no motion commands. Layer 3 (Planning and Decision Logic) determines the overall execution strategy and coordinates the interaction between Layers 2 and 4, without directly generating motion instructions. Layer 4 (Motion Generation and Communication) serves as the exclusive interface for robot communication, generating \ac{lin} and \ac{ptp} waypoints, converting them into \ac{json} format, and transmitting them via an authenticated \ac{websocket} connection. Layer 5 (Safety and Validation) is implemented as an independent top-level layer that is executed prior to any motion generation and enforces mandatory validation and operator confirmation, preventing further execution until all safety conditions are satisfied. The complete architectural structure is illustrated in Figure~\ref{fig:system_architecture_global_validation}.

The progression of data throughout a bending cycle follows a structured transformation across the system layers. Initially, sheet geometry, bend-side selection, and tool parameters are provided as input. These inputs are processed within the constraint evaluation layer, where raw pose data is transformed into a validated pickup orientation and feasible grip configuration. Based on this information, an execution strategy is determined and translated into motion commands, which are encoded in \ac{json} format and transmitted to the runtime environment.

The reliability of the overall process depends on several critical transformation stages. Any error introduced at these stages propagates through subsequent computations and affects execution outcomes. In particular, accurate orientation determination is essential for successful workpiece acquisition, while grip feasibility evaluation ensures stable handling during transport. During trajectory generation, a balance must be maintained between path accuracy and controller limitations, requiring controlled reduction of trajectory points while preserving motion characteristics.

Three structural properties ensure that the architectural constraints are consistently enforced across the system. First, the \ac{websocket} client and the command type definitions together constitute the exclusive communication layer. No module outside Layer 4 constructs \ac{websocket} messages or performs direct network operations. \subsection{Communication Stack and Authentication Interface Specification}
\label{sec:communication_stack}

All runtime communication passes through the AnyRobot Interface, as it is the only supported external \ac{api} for drag\&bot. Direct \ac{ros} client libraries are excluded because they would couple the planning software to a specific \ac{ros} version, violating NFR-02 \cite{dragandbot_anyrobot_2025} \cite{quigley2009ros}. The AnyRobot Interface translates \ac{json} over a persistent \ac{websocket} channel into native \ac{ros} operations using the RosBridge v2 protocol, enabling the entire planning software to run in standard Python 3 without a \ac{ros} installation on the planning machine.

\par \ac{websocket} is selected over \ac{http} due to its ability to maintain a persistent connection that supports continuous data exchange. Unlike \ac{http}, which follows a request–response model and requires a new connection for each interaction, \ac{websocket} enables uninterrupted communication over a single channel. In applications involving robotic motion execution, where a large number of trajectory points must be transmitted sequentially, repeated connection overhead can introduce noticeable delays. These delays may accumulate and lead to interruptions in command streaming, potentially affecting smooth robot operation. By using a persistent communication mechanism, \ac{websocket} reduces transmission overhead and ensures more stable and efficient delivery of motion commands, making it well suited for real-time robotic control scenarios \cite{Pimentel2012}.
\par Figure~\ref{fig:communication_architecture} presents an overview of the system communication architecture. The planning software establishes a persistent \ac{websocket} connection to the robot controller via a defined network endpoint (e.g., \texttt{ws://192.168.x.x:9091}). Communication is organized through a set of dedicated interfaces, each responsible for a specific function within the system. 

\acs{websocket}-based middleware is widely used in robotics to enable platform-independent communication between external applications and \acs{ros}-based systems \cite{Crick2017}. Such approaches rely on a persistent socket connection and lightweight message serialization to support continuous data exchange required for real-time operation.

In the implemented system, the Ros Bridge v2 interface is used to transmit motion commands, while the \texttt{rosauth} service ensures secure authentication using the \ac{sha512} hashing algorithm. Motion trajectories are transmitted in batches via the \texttt{/command\_list} interface, and real-time object information is retrieved through \texttt{/dnb\_object\_manager/list\_objects}. Gripper control is performed using \texttt{/robot/set\_digital\_ios}, whereas object attachment and detachment are handled through the corresponding manager interfaces. User interactions are managed via the \texttt{human\_interaction/request\_hi} interface.

The \ac{yaml} configuration is not part of the runtime communication. It is loaded once during system initialization and shared across the relevant modules, ensuring that missing or incorrect parameters are detected early before execution begins.

    \centering
    \includegraphics[width=\textwidth]{figures/communication_architecture.png}
    \caption{Communication architecture of the implemented system, illustrating the interaction between the planning software, the drag\&bot runtime environment, and the robot controller (adapted from~\cite{dragandbot_anyrobot_2025}).}
    \label{fig:communication_architecture}
\end{figure}

\par On connection establishment, the \ac{websocket} client performs the rosauth \ac{sha512} authentication handshake, because the drag\&bot \ac{websocket} port is accessible to any process on the local network and an unauthenticated endpoint would allow arbitrary motion command injection. The \ac{mac} is computed by hashing with \ac{sha512} concatenation of the shared runtime secret, the interface identifier, destination, a fixed nonce, session timestamps, and the access level string.

The authentication token is computed based on the procedure defined in the drag\&bot AnyRobot Interface specification~\cite{dragandbot_anyrobot_2025}:

\begin{equation}
\mathrm{MAC} = \mathrm{SHA\text{-}512}(\text{secret} \parallel \text{id\_string} \parallel \text{dest} \parallel \text{nonce} \parallel \text{t} \parallel \text{level})
\label{eq:sha512_mac}
\end{equation}

\par \ac{sha512} is selected due to its strong cryptographic properties, as its 512-bit output makes pre-image and collision attacks computationally infeasible within the operational context of this application. The shared secret is stored as an environment variable to prevent exposure to version control systems. The concatenation order is strictly defined by the AnyRobot interface specification and must be followed precisely. Any deviation from this order results in a mismatch of the generated hash, causing the runtime system to reject the connection.

\subsection{Configuration Architecture and Data File Structure}
\label{sec:configuration-architecture}
The \ac{yaml} configuration file serves as the central entry point for all process-related parameters and provides a flexible mechanism for adapting the system to different workpieces without requiring modifications to the underlying source code, thereby fulfilling NFR-02. At the beginning of each session, the file is parsed once, and the resulting configuration data is stored as a dictionary that is shared across all modules in Layers 2 to 4. The structure of the file is organized into six clearly defined top-level sections, each corresponding to a specific functional aspect of the system architecture, which supports clarity and maintainability.
\ac{yaml} is selected over \ac{json} primarily due to its support for inline comments. This allows engineers to document the meaning and physical relevance of individual parameters directly within the configuration file, eliminating the need to consult external documentation. To ensure robustness and security, the configuration is loaded using a safe parsing method, which prevents the execution of unintended code in the event that the file is modified or corrupted.
A key design decision concerns the handling of spatial consistency during the regrip process. Rather than defining approach and placement poses independently, all such poses are derived relative to a single reference pose defined for the orientation table. For example, the approach position is calculated by applying a fixed vertical offset to the placement pose. This design ensures that any change in the position of the orientation table requires only a single modification within the configuration file. In contrast, storing these poses independently could introduce inconsistencies: if the table position is updated but the corresponding approach position is not, the system may execute motions based on outdated spatial data. Such inconsistencies are particularly problematic because they may not be detected during configuration validation, as each parameter remains individually valid despite being collectively incorrect.

\subsection{Operator Interface and Interactive Three-Dimensional Sheet Bending Viewer}
\label{sec:operator-interface}

Operator input for each execution cycle is provided through an interactive three-dimensional sheet bending viewer developed in this work (hereafter referred to as the \textit{3D viewer}), rather than a conventional text-based interface. This design decision is primarily motivated by the spatial nature of bend side selection. By presenting the workpiece directly as a 3D model, the operator can identify relevant surfaces and orientations more intuitively than by relying on abstract side labels. In practice, this reduces the likelihood of incorrect selections while keeping the interaction simple, as the operator performs only visually guided inputs and the system handles the underlying computations.
\par The 3D viewer is implemented as a web-based application using Plotly Dash and renders the workpiece as an interactive mesh derived from the corresponding \ac{stl} file. It operates as a local service and is integrated into the drag\&bot Operator Cockpit through the Custom URL panel mechanism. A new panel of type \textit{Custom URL} is added to the dashboard via the dashboard configuration interface, where the local viewer address is specified as the target. Once configured, the viewer is rendered as an embedded panel within the cockpit, allowing the operator to interact with the 3D mesh and associated controls without leaving the drag\&bot environment. The configuration is stored as part of the dashboard definition and remains available across sessions, ensuring a consistent setup for repeated operation.
\par This integration ensures that configuration, monitoring, and execution are performed within a single interface, eliminating unnecessary context switching and providing a more coherent workflow from the operator’s perspective. \section{Development and Simulation Environment}
\label{sec:development_and_simulation_environment}
 
With the architectural framework established in Section~\ref{sec:system_architecture}, a controlled environment is required to execute, test, and validate the developed system prior to deployment on physical hardware. This section presents the development and simulation environment used in this work, including the drag\&bot platform, the robot model and tool configuration, and the spatial zone classification strategy used to structure the workspace.
 
\subsection{Simulation Platform, Robot Model, and Tool Centre Point Configuration}
\label{sec:simulation_platform}
 
The drag\&bot platform is used as the primary environment for system development, integration, and validation. It provides a virtual robot controller together with the AnyRobot \ac{websocket} Interface, enabling the planning software to interact with the robot runtime without requiring direct access to physical equipment. This supports safe testing, repeatability, and efficient iteration during development. The use of virtualised environments is consistent with current industrial trends in digital manufacturing and digital twin-based validation~\cite{dragandbot_anyrobot_2025,Tao2021DigitalTwin}.
 
All modules are implemented in Python and executed within an Ubuntu-based environment alongside the drag\&bot runtime. Communication is established through a single authenticated \ac{websocket} connection (e.g., \texttt{ws://<local-ip>:9091}), which is used for motion execution, IO control, object management, and operator interaction. This unified communication structure ensures consistent behaviour across all subsystems.
 
All session-specific parameters are initialised at the beginning of execution and explicitly passed between modules. This avoids hidden dependencies and ensures that all components operate on consistent data, supporting modularity and maintainability.
 
Within this environment, the Universal Robots \ac{ur5e} is used as the manipulator model. The robot provides six degrees of freedom, a reach of approximately 850~mm, and a payload capacity of 5~kg, which are sufficient for handling the sheet metal workpieces considered in this work. The availability of a validated kinematic model within the drag\&bot platform allows all generated motion targets to be evaluated for reachability and feasibility during simulation~\cite{dragandbot_anyrobot_2025,Macenski2022ROS2}.
 
The \ac{tcp} used for all motion targets is defined in the drag\&bot tool management system as \texttt{project\_3\_tcp}, in accordance with requirement SR-03. The \ac{tcp} is specified using the ZYX Euler convention with offsets relative to the robot flange: $x = 0.000$~m, $y = 0.034$~m, $z = 0.194$~m, $RZ = -90.0^\circ$, $RY = -75.0^\circ$, and $RX = 0.0^\circ$. These parameters ensure that all generated poses remain consistent with the physical gripper configuration. The \ac{tcp} identifier is provided through the operator input, allowing future adjustments without modification of the underlying source code.

\subsection{Virtual Cell Layout and Spatial Zone Classification}
\label{sec:zone_classification}
 
The simulated robotic cell within the drag\&bot environment includes the robot, press brake, orientation table, and a tracked sheet object, which serves as the reference for all geometric computations. The spatial configuration of these elements reflects the intended physical setup, ensuring that simulation results are representative of real-world operation.
 
At the beginning of each execution cycle, the system retrieves the six-degree-of-freedom pose of the sheet from the object tracking service. The pose is expressed in the robot world coordinate frame, where the origin is located at the robot base. Accurate pose acquisition is a fundamental requirement in robotic manipulation systems and is widely addressed in modern robotics literature~\cite{Siciliano2016Robotics}. Based on this information, the position of the sheet centroid in the XY plane is used to classify the workpiece into one of four spatial zones.
 
The workspace is partitioned into four regions relative to the robot base. A centroid with negative X and positive Y corresponds to Zone~1 (rear-left), while negative X and negative Y defines Zone~2 (front-left). Positive X and positive Y correspond to Zone~3 (rear-right), and positive X with negative Y defines Zone~4 (front-right). The classification is based on threshold values of $\pm 10$~mm in the X direction and $\pm 50$~mm in the Y direction. These thresholds account for measurement uncertainty and reflect the physical layout of the robotic workspace~\cite{Siciliano2016Robotics}.
 
Zones~3 and~4 lie within the primary reachable workspace of the robot and therefore allow direct execution of pickup and bending operations. In contrast, Zones~1 and~2 correspond to regions with limited reachability. In these cases, the system automatically initiates a repositioning step, moving the workpiece to an intermediate configuration within the reachable workspace before continuing execution. This ensures that all subsequent operations remain within kinematic limits without requiring operator intervention.
 
If the sheet centroid lies within the dead-band region defined by $|x| < 10$~mm or $|y| < 50$~mm, the classification is considered unresolved. This occurs near the coordinate axes, where small variations in tracking data may lead to inconsistent zone assignment. To prevent incorrect execution, the system terminates the current session and prompts the operator to reposition the workpiece before restarting.
 
\begin{figure}[!htbp]
    \centering
    \includegraphics[width=0.8\textwidth]{figures/zone_classification.png}
    \caption{Spatial zone classification of the robot workspace based on the sheet centroid position. \textit{Source: own work.}}
    \label{fig:zone_classification}
\end{figure}
 
Having defined the simulation environment, robot model, \ac{tcp} configuration, and workspace segmentation strategy, the following sections describe the functional subsystems in the order of execution within a bending cycle, beginning with safety validation, followed by orientation determination, grip planning, and trajectory generation.
 
\begin{algorithm}[htbp]
\caption{Spatial zone classification based on sheet centroid position.}
\label{alg:zone_classification}
\begin{algorithmic}[1]
\State Retrieve sheet centroid coordinates $(x, y)$ in the robot world frame
\If{$|x| < x_{\text{th}}$ \textbf{or} $|y| < y_{\text{th}}$}
    \State Return \textit{unresolved zone}
\ElsIf{$x < 0$ \textbf{and} $y > 0$}
    \State Assign Zone 1
\ElsIf{$x < 0$ \textbf{and} $y < 0$}
    \State Assign Zone 2
\ElsIf{$x > 0$ \textbf{and} $y > 0$}
    \State Assign Zone 3
\Else
    \State Assign Zone 4
\EndIf
\end{algorithmic}
\end{algorithm}
 
Algorithm~\ref{alg:zone_classification} summarises the classification logic in an abstract form. The method relies on the sign of the centroid coordinates together with a threshold-based dead-band region to ensure stable classification under measurement uncertainty.

\section{Pre-Execution Safety Validation}
\label{Pre-Execution_Safety_Validation}
 
Safety validation is performed prior to motion generation to ensure that unsafe conditions and infeasible configurations are identified before robot execution, in accordance with NFR-03, NFR-04, and NFR-05 \cite{Siciliano2016Robotics}. The system incorporates three complementary mechanisms: a fixture pose deviation check, a blocking operator confirmation dialog, and a runtime motion error monitoring module. In addition, all trajectory waypoints are generated and verified using robot kinematics to ensure reachability and feasibility before execution, thereby preventing invalid motion commands from being issued \cite{Siciliano2016Robotics}.
 
\subsection{Fixture Pose Deviation Validation}
\label{Fixture_Pose_Deviation_Check}
 
The fixture pose deviation check retrieves the current poses of critical fixtures from the drag\&bot object manager and compares them with reference poses obtained during initial cell calibration. The monitored elements include the primary sheet object at the press brake, the finished-part placement positions on the regrip table, and the placement and attachment references at the flip station. These fixtures are treated as fixed references within the planning system, as all grip positions, trajectory waypoints, and placement operations are computed under the assumption that their positions remain unchanged. Any deviation from these reference poses can therefore result in motion targets that are geometrically valid but physically incorrect.
 
The deviation check is applied uniformly across all spatial zones. Each fixture is evaluated using both positional and orientation criteria. The positional deviation is computed as:
 
\begin{equation}
\Delta_{pos} = \sqrt{(\Delta x)^2 + (\Delta y)^2 + (\Delta z)^2}
\label{eq:fixture-position-deviation}
\end{equation}
 
and the orientation deviation is defined as:
 
\begin{equation}
\Delta_{ang} = \max\left(|\Delta RZ|, |\Delta RY|, |\Delta RX|\right).
\label{eq:fixture-orientation-deviation}
\end{equation}
 
A fixture is considered out of tolerance when $\Delta_{pos}$ exceeds 5~mm or $\Delta_{ang}$ exceeds 0.10~rad (5.7$^\circ$). The positional threshold is selected to remain below the minimum clearance used in grip planning. This ensures that fixture misalignment does not produce misleadingly valid grip configurations. The angular threshold corresponds to the minimum deviation that would affect the accuracy of vacuum cup contact on the sheet surface.
 
The primary sheet object is evaluated using the same criteria as other fixtures. Since the planning system relies on the current sheet pose for all geometric computations, any deviation may lead to incorrect motion generation and is therefore treated as a configuration error.
 
If one or more fixtures exceed the defined thresholds, the system generates a structured warning listing all affected fixtures together with their measured positional and angular deviations. This warning is presented through a blocking human interaction (HI) dialog titled \textit{Fixture position warning}, allowing the operator to either proceed with explicit acknowledgement or cancel execution for further inspection. The operator’s decision is recorded, ensuring that responsibility for accepting out-of-tolerance conditions remains with the human operator.
 
If a fixture is not detected in the object manager response, it is treated as missing and automatically flagged as a validation failure.
 
\subsection{Operator Authorization and Runtime Error Monitoring}
\label{sec:operator-authorization-runtime-monitoring}
 
The operator confirmation dialog is positioned as the first step in the planning orchestrator startup sequence, preceding all subsequent processes including fixture validation, visualization, and motion execution. The dialog enforces a mandatory decision: either initiate the automated workflow or cancel execution. The orchestrator does not proceed until a response is received from the HI service, ensuring that execution cannot begin without explicit operator authorisation. If the operator selects cancel, the process terminates without issuing any command to the robot runtime.
 
In addition to pre-execution validation, runtime supervision is implemented through a motion error monitoring module operating as a background subprocess. This component subscribes to the \texttt{/command\_result} \ac{ros} topic via an independent \ac{websocket} connection, enabling continuous monitoring of execution outcomes without interrupting the main command flow. When a non-zero result code is detected, indicating a motion execution failure, the system immediately triggers a modal HI notification to inform the operator.
 
The monitoring module does not directly interrupt the execution pipeline. Instead, it provides immediate feedback through the HI interface and requires operator acknowledgement before further interaction is permitted. This ensures that execution anomalies are not overlooked while maintaining operator authority over subsequent decisions.
 
Together, these mechanisms establish a layered safety structure. Pre-execution validation ensures safe initial conditions, while runtime monitoring provides immediate feedback on execution failures. Both mechanisms utilise the drag\&bot HI service, ensuring a consistent and controlled interface for safety-related interactions. With these safeguards in place, the subsequent section addresses the workpiece orientation strategy.

\section{Workpiece Orientation Strategy}
\label{sec:workpiece_orientation}
 
Following pre-execution safety validation, the first geometric step in each bending cycle is the determination of a valid pickup orientation for the sheet. This is required because the sheet may be placed in arbitrary orientations within the workspace, while only a subset of these orientations is kinematically feasible for the target bending operation. The orientation strategy evaluates the tracked sheet pose, applies a structured selection process, and produces a validated pickup pose for subsequent grip planning.
 
\subsection{Zone-Based Rotation Admissibility}
\label{sec:zone-based-rz-admissibility}
 
The admissible range of sheet rotation about the Z-axis is defined by a zone-dependent window $[RZ_{\min}, RZ_{\max}]$. This constraint reflects the limited rotational capability of the robot end-effector within different regions of the workspace \cite{Siciliano2016Robotics}. Since the reachable orientation range varies with the spatial position of the sheet, zone classification is performed prior to orientation evaluation. The admissibility limits are retrieved from the configuration to ensure that only kinematically feasible orientations are considered. This prevents the selection of geometrically valid but unreachable poses.
 
\subsection{Pickup Orientation Validation}
\label{sec:pickup_orientation_validation}
 
Before applying the selection strategy, the tracked pose is validated to ensure that the gripper approaches the sheet from above. This is evaluated using the condition $\cos(RX)\cdot\cos(RY)$. If the value is below $-0.10$, the tool Z-axis is oriented downward and no modification is required. Otherwise, a corrective transformation is applied:
 
\begin{equation}
RZ' = \mathrm{wrap}(RZ + 180^\circ), \quad
RY' = -RY, \quad
RX' = \mathrm{wrap}(RX + 180^\circ)
\label{eq:zone-based-opposite-orientation}
\end{equation}
 
This transformation ensures proper tool alignment with the sheet surface without modifying the pickup position.
 
\subsection{Three-Level Orientation Selection Strategy}
\label{sec:three-level-orientation-selection-strategy}
 
To ensure that a valid pickup orientation is always obtained, a three-level selection strategy is applied. The levels are evaluated sequentially, and execution terminates as soon as a valid orientation satisfying admissibility constraints is identified. This guarantees robustness while prioritising geometrically consistent and kinematically feasible configurations.
 
The workpiece is defined using four reference faces established during system commissioning, each associated with a fixed angular offset about the sheet’s local vertical axis ($0^\circ$, $180^\circ$, $+90^\circ$, $-90^\circ$). These offsets allow the system to normalise arbitrary orientations into a consistent reference frame.
 
\paragraph{Level 1: Reference-Face Equivalent Orientation}
 
At the highest priority level, the tracked orientation is converted into a reference-face equivalent by removing the face-specific offset:
 
\begin{equation}
R_{\text{new}} = R_{\text{raw}} \cdot R_z(-d_{\text{face}})
\label{eq:bend-face-corrected-rotation}
\end{equation}
 

The resulting rotation matrix is decomposed into ZYX Euler angles \cite{Siciliano2016Robotics,lynch2017modern}:
 
\begin{equation}
R = R_z(\alpha)\cdot R_y(\beta)\cdot R_x(\gamma)
\label{eq:euler-rotation-composition}
\end{equation}

\begin{equation}
RZ = \operatorname{atan2}(R_{10}, R_{00}), \quad
RY = \arcsin(-R_{20}), \quad
RX = \operatorname{atan2}(R_{21}, R_{22})
\label{eq:euler-angle-extraction}
\end{equation}
 
If the computed $RZ$ lies within the admissibility window, this orientation is selected. This level is preferred as it ensures consistent reference alignment and reduces trajectory complexity.
 
\paragraph{Level 2: Detected-Pose Evaluation}
 
If Level 1 fails, the raw tracked orientation is evaluated directly. This accounts for cases where the initial placement is already feasible and avoids unnecessary transformations. If the raw $RZ$ satisfies admissibility constraints, it is selected.
 
\paragraph{Level 3: Inverted-Pose Fallback}
 
If neither Level 1 nor Level 2 satisfies the admissibility condition, a fallback orientation is generated:
 
\begin{equation}
RZ' = \mathrm{wrap}(RZ \pm 180^\circ), \quad
RY' = -RY, \quad
RX' = -RX
\label{eq:fallback-opposite-orientation}
\end{equation}
 
This transformation expands the reachable orientation set and guarantees that a pickup configuration is always obtained. Since this orientation may not strictly satisfy admissibility constraints, it is marked as \textit{admissibility not confirmed}. This status is propagated to downstream modules, allowing conservative execution strategies to be applied.
 
\begin{algorithm}[htbp]
\caption{High-level orientation selection strategy.}
\label{alg:orientation_selection}
\begin{algorithmic}[2]
\State Retrieve tracked sheet pose and active zone
\State Load zone-specific admissibility window $\{R_Z^{\min}, R_Z^{\max}\}$
\State Validate pickup orientation and apply correction if required
\State Compute reference-face equivalent orientation
\If{reference-face orientation is admissible}
    \State Select reference-face orientation
\ElsIf{detected orientation is admissible}
    \State Select detected orientation
\Else
    \State Compute inverted orientation
    \State Select inverted orientation (admissibility not confirmed)
\EndIf
\State Forward orientation to downstream planning modules
\end{algorithmic}
\end{algorithm}

\section{Workpiece Handling and Gripper Control}
\label{sec:gripper_control}
 
Once a valid pickup orientation has been determined, the system must establish a reliable physical interaction between the gripper and the sheet while maintaining consistency between the physical robot state and the virtual simulation. Any mismatch between the vacuum state of the gripper and the attachment state in the simulation leads to incorrect pose propagation and invalid trajectory computation in subsequent stages. This consistency is ensured through two coordinated mechanisms: digital IO control of the vacuum gripper and kinematic object attachment within the simulation environment.
 
\subsection{Vacuum Gripper Digital Input and Output Sequence}
\label{sec:vacuum-gripper-digital-io-sequence}
 
The vacuum gripper is actuated using two digital output signals mapped within the drag\&bot IO management system. One signal activates the vacuum by closing the suction valve, while the other releases the vacuum by opening the exhaust valve. These signals are strictly mutually exclusive; simultaneous activation is avoided to prevent conflicting pressure states and potential hardware damage.
 
Control commands are issued via the \texttt{/robot/set\_digital\_ios} interface, which transmits structured IO instructions specifying the target output and its Boolean state. To ensure reliable gripping, a dwell period of approximately 250~ms is applied after vacuum activation. This delay allows the suction cups to establish a stable seal with the sheet surface, which is necessary for maintaining grasp stability during subsequent motion \cite{bicchi2000robotic}.
 
A secondary delay of approximately 150~ms is introduced after each IO operation to ensure that the state transition propagates through the communication layer before further commands are issued. This prevents timing inconsistencies between command execution and runtime state updates.
 
\subsection{Kinematic Object Attachment and Detachment}
\label{sec:kinematic-object-attachment-detachment}
 
Within the simulation environment, the physical coupling between the gripper and the sheet is represented through kinematic attachment. When the gripper successfully establishes contact, the corresponding object is attached to the robot tool frame, ensuring that subsequent robot motions are reflected in the object pose. When the vacuum is released, the object is detached and remains fixed in its last known position.
 
Attachment is performed using the \texttt{/dnb\_object\_manager/attach} interface without enforcing a position override. This avoids introducing discontinuities between the tracked object pose and the simulated state, as the tracked pose may not exactly coincide with the instantaneous tool frame position. Position override is reserved only for controlled initialization procedures where explicit alignment is required.
 
Detachment is executed using the \texttt{/dnb\_object\_manager/detach} interface within the same reference frame. To maintain consistency, attachment and detachment operations are always executed in a fixed sequence together with the corresponding IO commands:
 
\begin{itemize}
\item Grasp sequence: vacuum ON $\rightarrow$ dwell $\rightarrow$ attach
\item Release sequence: vacuum OFF $\rightarrow$ dwell $\rightarrow$ detach
\end{itemize}
 
This sequence is encapsulated within centralized helper routines that are invoked by all modules performing grasp or release operations. Centralizing this logic ensures that the physical and virtual system states remain synchronised at all times and prevents inconsistent conditions in which the vacuum state and attachment state do not correspond.
 
With physical grasping and state synchronisation established, the next step is to determine feasible suction cup positions on the workpiece surface.

\section{Grip Position Planning and Feasibility Validation} 
\label{sec:grip_planning} 
 
Following the determination of a valid pickup orientation and the establishment of a consistent gripper control mechanism, the system must identify feasible suction cup placements on the sheet surface. Arbitrary placement is not sufficient, as it may violate geometric constraints or fail to provide adequate holding force during handling. The grip planner therefore evaluates both geometric feasibility and physical stability to ensure a reliable and executable grasp configuration. This structured approach directly addresses the limitations identified in Chapter~\ref{ch:state-of-art}, where manual or heuristic-based gripping strategies lack consistency and adaptability. This approach enables deterministic and repeatable grip planning, which is essential for automated program generation in an industrial environment.

\subsection{Sheet Geometry and Hole Detection} 
\label{subsec:sheet_geometry_holes} 
 
The sheet is modelled as a planar rectangular surface with uniform mass distribution, defined by its length, width, thickness, and mass obtained from the configuration. If the mass is not explicitly specified, it is estimated from the sheet volume and the material density defined in the configuration. 
 
In addition to the outer boundary, internal features such as holes are extracted from the \ac{stl} mesh during the geometry analysis stage. Each hole is represented by its centre position and radius in the sheet coordinate frame. These regions are explicitly excluded from the feasible gripping area, since suction cups cannot form a stable seal over discontinuities. This ensures that only physically valid contact regions are considered during grip planning. 
 
\subsection{Vacuum Holding Force Validation} 
\label{subsec:vacuum_force_validation} 
 
For each candidate grip configuration, the system evaluates whether the available vacuum force is sufficient to retain the sheet under both gravitational and dynamic loading conditions. The contact area of a single suction cup is defined as 
 
\begin{equation} 
A_{\text{cup}} = \pi \left(\frac{d_{\text{cup}}}{2}\right)^2 
\label{eq:cup_area} 
\end{equation} 
 
The total available holding force generated by $n$ suction cups is expressed as 
 
\begin{equation} 
F_{\text{vacuum}} = n \cdot \Delta P \cdot A_{\text{cup}} \cdot \eta 
\label{eq:vacuum_force} 
\end{equation} 
 
where $\Delta P$ represents the pressure differential and $\eta$ accounts for efficiency losses due to leakage and surface conditions. 
 
The required holding force is determined as 
 
\begin{equation} 
F_{\text{required}} = SF \cdot m \cdot \sqrt{a_{xy}^2 + (g + a_z)^2} 
\label{eq:required_force} 
\end{equation} 
 
where $SF$ is a safety factor and $a_{xy}, a_z$ represent dynamic accelerations. 
 
A candidate configuration is considered feasible only if 
 
\begin{equation} 
F_{\text{vacuum}} \geq F_{\text{required}} 
\label{eq:vacuum-feasibility-criterion}
\end{equation} 
 
This formulation follows standard principles of vacuum-based gripping and ensures that only configurations capable of maintaining stable contact under motion are considered for execution \cite{vacuum_handling_standard}. 
 
\subsection{Grip Candidate Search and Selection} 
\label{subsec:grip_candidate_search} 
 
Candidate suction cup positions are generated using a multi-resolution grid-based search over the sheet surface. The process begins with a coarse discretisation to identify feasible regions, followed by progressive refinement to improve placement accuracy in promising areas. Additional candidates are generated near hole boundaries to maximise usable surface area while maintaining required clearances. 
 
Each candidate position is evaluated against geometric constraints. The cup centre must satisfy minimum edge clearance requirements, avoid overlap with hole regions including a defined buffer zone, and comply with spacing constraints in multi-cup configurations. For the two-cup case, candidate positions are evaluated in pairs, with the inter-cup distance constrained to ensure sufficient grip span across the workpiece. 
 
After geometric filtering, candidates are further evaluated using the vacuum holding force criterion described in Section~\ref{subsec:vacuum_force_validation}. Only configurations satisfying both geometric and physical constraints are retained. 
 
The remaining candidates are ranked using a scoring function that balances multiple criteria, including edge clearance, distance from internal features, and spatial distribution across the sheet. In multi-cup configurations, the scoring additionally promotes wider spacing between cups to improve stability during transport. This structured evaluation replaces heuristic placement strategies commonly found in manual programming approaches and ensures consistent selection of robust grip configurations.

\section{Regrip Planning and Execution} 
\label{sec:regrip} 
 
Even when a valid pickup orientation and a feasible grip configuration are established, the current grasp may not permit the robot to reach the required bending pose. This limitation arises when the target configuration lies outside the reachable workspace or when kinematic constraints, such as joint limits or proximity to singularities, prevent a valid motion solution~\cite{lynch2017modern}. To address this, the system implements an automatic regrip planning strategy that determines the required reorientation dynamically. This approach directly addresses the limitations identified in the state of the art, where regrip operations are typically predefined or manually programmed. 
 
\subsection{Regrip Decision Strategy} 
\label{sec:regrip-decision-strategy}
 
In contrast to conventional approaches based on fixed regrip sequences, the proposed system evaluates a discrete set of candidate workpiece orientations and selects a configuration that satisfies kinematic feasibility. This enables the system to determine both the required orientation and the number of regrip steps automatically. 
 
The candidate set consists of discrete orientation increments corresponding to physically achievable rotations on the orientation table. For each candidate orientation, the system performs the following sequence: 
 
\begin{itemize} 
\item Update the workpiece pose according to the candidate orientation 
\item Determine a valid pickup orientation using the strategy described in Section~\ref{sec:workpiece_orientation} 
\item Compute feasible grip positions using the planner described in Section~\ref{sec:grip_planning} 
\item Evaluate kinematic feasibility using inverse kinematics and trajectory validation 
\end{itemize} 
 
A candidate orientation is accepted only when all feasibility conditions are satisfied. The evaluation follows a sequential selection strategy in which candidates are tested in a predefined order, and the first feasible solution is selected. This ensures computational efficiency while maintaining robustness for real-time execution. 
 
The number of required regrip steps is implicitly determined from the difference between the current orientation and the selected feasible configuration. This approach avoids unnecessary intermediate operations while ensuring that the final pose remains reachable and executable within the robot workspace. 
 
\begin{algorithm}[htbp] 
\caption{Regrip orientation selection.} 
\label{alg:auto_regrip} 
\begin{algorithmic}[1] 
\State Define candidate orientation set 
\For{each candidate orientation} 
    \State Compute updated workpiece pose 
    \State Evaluate pickup orientation 
    \State Compute grip configuration 
    \State Check kinematic feasibility 
    \If{feasible} 
        \State Select orientation 
        \State \textbf{break} 
    \EndIf 
\EndFor 
\State Determine required number of regrip steps 
\end{algorithmic} 
\end{algorithm} 
 
Algorithm~\ref{alg:auto_regrip} summarises the decision process. The evaluation reuses the existing planning pipeline, ensuring consistency with orientation selection, grip planning, and trajectory generation. 
 
\subsection{Regrip Execution Sequence} 
\label{sec:regrip-execution-sequence}
 
Once a feasible orientation has been identified, the system executes a structured regrip sequence to realise the required reorientation. The sequence consists of the following steps: 
 
\begin{enumerate} 
\item Transport the workpiece from the bending station approach position to the orientation table deposit position while maintaining the current grasp 
\item Release the workpiece through controlled vacuum deactivation and kinematic detachment 
\item Move the robot to a retract standoff position to ensure collision-free clearance 
\item Re-approach the workpiece at the updated orientation and perform the grasp sequence 
\item Repeat the regrip cycle if additional orientation adjustments are required 
\item Perform the final grasp and return the workpiece to the bending station 
\end{enumerate} 
 
Each motion segment is executed using smooth trajectories to minimise dynamic loads on the gripper and ensure stable handling. Intermediate standoff positions provide safe transitions between grasping and releasing operations. 
 
\subsection{System Integration and Configuration} 
\label{sec:regrip-system-integration-configuration}
 
The regrip execution sequence operates within the existing motion framework and uses configuration-defined target positions, including deposit, re-grasp, retract, and approach poses. These parameters define the physical layout of the cell but do not determine the number of regrip steps. 
 
The decision to trigger a regrip is handled by the planning orchestrator, which evaluates feasibility based on orientation admissibility and kinematic constraints. This separation between decision-making and execution ensures modularity and allows the regrip strategy to be extended without modifying the motion execution layer. 
 
Compared to configuration-driven approaches, the proposed method improves adaptability by determining the minimum required number of regrip steps dynamically. At the same time, it maintains computational efficiency by evaluating a structured set of candidate orientations rather than performing global optimisation. This balance makes the approach suitable for industrial deployment, where predictable and robust behaviour is required.

\section{Opposite-Face Bending Workflow} 
\label{sec:opposite_side} 
 
After completing all primary-side bending operations, the system evaluates whether additional bends are required on the opposite face of the sheet. These operations cannot be executed directly from the initial pickup configuration, as the required face is not accessible to the press brake tool. Consequently, the workpiece must be reoriented through a controlled flip operation before continuing the bending process. 
 
\subsection{Pre-Flip Verification and Transition Correction} 
\label{sec:pre-flip-verification-transition-correction}
 
Before initiating the flip sequence, the system verifies that the current sheet pose corresponds to the expected reference configuration. This verification is performed using a wrap-safe six-degree-of-freedom pose comparison, with a positional tolerance of 2~mm and an angular tolerance of 1$^\circ$. 
 
This validation step is required because the sheet may have undergone regrip operations during the primary bending sequence. Any deviation from the expected pose would propagate errors into subsequent motion planning stages, leading to incorrect trajectory generation. 
 
If the verification fails, a transition correction step is executed. The system first restores the reference orientation using the strategy described in Section~\ref{sec:workpiece_orientation}. A controlled pickup and repositioning sequence is then performed to re-establish a consistent and verified alignment between the robot and the workpiece. 
 
If the verification is successful, the correction step is omitted and the system proceeds directly to the flip sequence. 
 
\subsection{Sheet Flip Sequence and Opposite-Face Bending Execution} 
\label{sec:sheet-flip-opposite-face-bending-execution}
 
The flip operation is performed using a dedicated station within the robotic cell. The workpiece is transferred through two predefined reference positions to achieve a physically feasible reorientation. 
 
First, the robot transports the sheet to the flip station placement position while maintaining the current grasp. The workpiece is then released in a controlled manner. The robot subsequently moves to an intermediate standoff pose and re-approaches the sheet from the opposite side, establishing a new grasp that results in the flipped orientation. 
 
This two-stage transfer is preferred over a direct in-gripper rotation. A direct rotation would require a continuous motion that exceeds the kinematic capabilities of the robot and may violate workspace or collision constraints~\cite{lynch2017modern}. 
 
Following the flip operation, the sheet is aligned such that the previously inaccessible face is oriented towards the press brake tool. The system then applies the same validation pipeline used for primary-side bending, including zone classification, orientation determination, grip position planning, and trajectory generation. 
 
Reusing the same processing pipeline ensures consistent system behaviour across both primary and opposite-side operations. It also avoids the need for separate handling logic, thereby maintaining modularity and reducing system complexity.

After completing all opposite-side bends, any remaining staged operations are executed using the existing handling framework. The system then proceeds to the final unloading sequence.

\section{Trajectory Generation}
\label{sec:trajectory}
 
Trajectory generation constitutes the final stage of the planning pipeline, where validated task-level poses are transformed into executable robot motion. The input to this stage is an ordered sequence of \ac{tcp} poses obtained from upstream modules, including grip planning, regrip handling, and opposite-face operations. Each pose defines the desired end-effector position and orientation within the robot world frame.
 
Rather than executing direct point-to-point transitions, the system constructs a continuous and smooth trajectory composed of intermediate waypoints. This approach ensures kinematic feasibility, reduces dynamic loading, and improves execution stability during sheet handling.
 
\subsection{Three-Phase Linear Trajectory Structure}
\label{sec:three-phase-linear-trajectory-structure}
 
Each motion segment is generated using a structured three-phase trajectory: lift, lateral transfer, and descent. 
 
In the lift phase, the \ac{tcp} is translated vertically to a predefined safe height to avoid collisions with the workpiece, fixtures, or surrounding environment. In the lateral transfer phase, the robot moves towards the target position while maintaining this clearance height. During this phase, the end-effector orientation is constrained to limit excessive joint rotations and reduce proximity to kinematic singularities. Finally, in the descent phase, the \ac{tcp} is lowered to the target pose, where the required orientation for task execution is fully applied.
 
To further improve motion feasibility, an intermediate rotation pose is introduced above the target location. This ensures that major orientation adjustments are completed before the final approach, reducing the risk of instability near contact regions.
 
\subsection{Waypoint Generation and Interpolation}
\label{sec:waypoint-generation-interpolation}
 
The trajectory between successive poses is generated through interpolation in Cartesian space. For a start pose $\mathbf{T}_s$ and a target pose $\mathbf{T}_t$, the translational component is computed as
 
\begin{equation}
\mathbf{p}(\lambda) = (1 - \lambda)\mathbf{p}_s + \lambda \mathbf{p}_t,
\label{eq:linear-cartesian-interpolation}
\end{equation}
 
where $\lambda \in [0,1]$ is the interpolation parameter.
 
Rotational interpolation is performed using spherical linear interpolation (SLERP) in quaternion space, which provides smooth and constant-speed rotation between orientations~\cite{Shoemake1985Slerp}. 
 
To ensure smooth velocity and acceleration profiles, the interpolation parameter follows a minimum-jerk trajectory given by
 
\begin{equation}
s(u) = 10u^3 - 15u^4 + 6u^5,
\label{eq:minimum-jerk-scaling}
\end{equation}
 
which guarantees zero velocity and acceleration at the start and end of each motion segment~\cite{Flash1985MinimumJerk}. Such profiles are widely adopted in robotic trajectory planning to achieve smooth and physically consistent motion behaviour~\cite{Gasparetto2012Trajectory}.
 
By sampling this progression at discrete intervals, a sequence of intermediate \ac{tcp} waypoints is generated that approximates the continuous trajectory.
 
\begin{lstlisting}[language=Python, caption={Illustrative waypoint generation using minimum-jerk interpolation}, label={lst:minjerk_waypoints}]
def min_jerk(u):
    return 10*u**3 - 15*u**4 + 6*u**5
 
waypoints = []
for k in range(N):
    u = k / (N - 1)
    s = min_jerk(u)
    p = (1 - s) * p_start + s * p_target
    r = slerp(r_start, r_target, s)
    waypoints.append((p, r))
\end{lstlisting}
 
The number of waypoints is determined based on the path length and a predefined resolution parameter, ensuring a balance between trajectory smoothness and computational efficiency.
 
\begin{lstlisting}[language=Python, caption={Illustrative determination of waypoint count based on path length}, label={lst:waypoint_count}]
distance = euclidean_dist(p_start, p_target)
N = max(2, math.ceil(distance / delta_s_max))
samples = [k / (N - 1) for k in range(N)]
\end{lstlisting}
 
\subsection{Kinematic Mapping and Joint Execution}
\label{sec:kinematic-mapping-joint-execution}
 
Each interpolated \ac{tcp} waypoint is mapped to a corresponding robot joint configuration using inverse kinematics. For each waypoint, a feasible solution is selected based on continuity with the previous configuration, avoiding abrupt joint changes and ensuring smooth motion across the trajectory.
 
As the robot executes the sequence, all joints evolve continuously, resulting in a smooth end-effector motion that closely follows the planned Cartesian path.
 
\subsection{Workspace Constraints and Singularity Handling}
\label{sec:workspace-constraints-singularity-handling}
 
To ensure execution feasibility, each waypoint is validated against workspace constraints. The \ac{tcp} pose is transformed into the corresponding flange pose, and its position is checked against the allowable workspace limits. If a waypoint exceeds these limits, it is projected onto the nearest feasible boundary.
 
Singularity avoidance is addressed by restricting orientation changes during the lateral motion phase. Large orientation adjustments are deferred to the approach phase, where the robot operates in a more stable configuration. This reduces the risk of excessive joint velocities and improves overall motion robustness.
 
\subsection{Motion Execution and Path Reduction}
\label{sec:motion-execution-path-reduction}
 
The interpolation process generates a dense set of waypoints, which may exceed the processing capacity of the robot controller. To address this, a path reduction strategy is applied, retaining only those waypoints that exceed predefined positional or rotational thresholds. This preserves the essential characteristics of the trajectory while reducing communication overhead.
 
The resulting waypoint sequence is transmitted as a series of linear motion commands, which are executed by the robot controller using blending techniques. This allows smooth transitions between consecutive waypoints without stopping, producing continuous and stable motion.
 
Overall, the trajectory generation module forms a deterministic transformation pipeline in which validated task-level poses are converted into executable robot motion through interpolation, kinematic mapping, constraint validation, and controlled execution.

\section{System Reliability and Failure Mode Analysis}
\label{sec:fmea}
 
To evaluate the robustness and operational reliability of the implemented system, a Failure Mode and Effects Analysis (FMEA) is conducted. This structured methodology identifies potential failure modes within the robotic bending workflow, evaluates their impact on system performance, and assesses the effectiveness of implemented mitigation strategies.
 
FMEA is based on three evaluation criteria: severity (S), occurrence (O), and detectability (D). These factors are combined to compute the Risk Priority Number (RPN), defined as
 
\begin{equation}
\mathrm{RPN} = S \times O \times D
\label{eq:risk-priority-number}
\end{equation}
 
Each parameter is assessed using a qualitative scale from 1 (low) to 10 (high), where higher RPN values indicate higher-priority risks requiring mitigation.
 
\subsection{Identification of Failure Modes}
\label{sec:identification-failure-modes}
 
The analysis focuses on critical stages of the execution pipeline, including pickup orientation, grip planning, trajectory execution, regrip handling, and opposite-face operations. The identified failure modes are summarised in Table~\ref{tab:fmea}.

\subsection{Mitigation Strategies}
\label{sec:mitigation-strategies}
 
Several design measures have been incorporated to reduce both the likelihood and impact of identified failure modes.
 
Geometric consistency is ensured through structured validation stages, including fixture pose deviation checks and orientation admissibility constraints. These mechanisms prevent incorrect pose assumptions from propagating into motion generation.
 
Grip reliability is addressed through combined geometric filtering and physical feasibility validation. By enforcing edge clearance, hole avoidance, and vacuum force constraints, the system ensures that only stable grip configurations are selected.
 
Trajectory-related risks are mitigated through interpolation-based motion generation and workspace validation. The use of minimum-jerk profiles and waypoint filtering ensures smooth motion while avoiding excessive controller load. In addition, singularity avoidance strategies and orientation constraints are applied to maintain kinematic stability throughout execution.
 
Regrip and flip operations are implemented as structured sequences with defined intermediate poses, ensuring collision-free transitions and consistent object handling. The use of deterministic execution pipelines further reduces uncertainty by enforcing a fixed order of validated operations.
 
\subsection{Discussion}
\label{sec:fmea-discussion}
 
The FMEA results indicate that the most critical risks are associated with pose accuracy and trajectory feasibility, as these directly influence all downstream planning and execution stages. These risks are effectively mitigated through layered validation, constraint-based planning, and structured motion generation.
 
Overall, the system demonstrates a balanced reliability profile in which high-severity failure modes are either low in occurrence or mitigated through strong detection and validation mechanisms. This confirms that the proposed architecture not only enables automated bending operations but also ensures safe and predictable execution under varying operating conditions.


\subsection{Conclusion}
\label{sec:implementation-conclusion}
 
This chapter presented the complete implementation of the proposed system for automated press brake sheet metal bending, based on the selected Concept~B. The implementation translates the conceptual design into a fully functional software architecture that integrates geometric reasoning, constraint-based planning, and robotic motion execution within a unified framework.
 
A layered system architecture was developed to ensure modularity, testability, and strict enforcement of execution order. Each functional component, including orientation determination, grip planning, regrip handling, and trajectory generation, was designed as an independent module with clearly defined responsibilities. This structure enables traceability between system requirements and implementation, while also supporting future extensibility.
 
The system demonstrates the capability to generate robot programs automatically from configuration data and geometric inputs, eliminating the need for manual waypoint definition. By incorporating structured validation mechanisms at multiple stages, including pre-execution safety checks, grip feasibility validation, and workspace-constrained trajectory generation, the system ensures reliable and safe operation.
 
A key contribution of this work lies in the integration of adaptive regrip planning and opposite-face handling within a deterministic execution pipeline. Unlike conventional approaches that rely on predefined sequences, the system dynamically evaluates feasible configurations and determines the required manipulation strategy at runtime. This improves flexibility while maintaining computational efficiency suitable for industrial applications.
 
The trajectory generation framework further enhances system robustness by combining smooth interpolation techniques with kinematic validation and path reduction strategies. This ensures that generated motions are both executable by the robot controller and stable under real-world operating conditions.
 
The conducted Failure Mode and Effects Analysis confirms that the system effectively mitigates critical risks through layered validation and structured execution. High-risk scenarios related to pose accuracy, gripping stability, and trajectory feasibility are addressed through a combination of detection mechanisms and constraint-based design.
 
Overall, the implemented system provides a robust and scalable solution for automated sheet metal bending. It achieves a balance between flexibility, safety, and computational efficiency, demonstrating the feasibility of fully automated robot program generation in an industrially relevant context. This implementation forms a strong foundation for further evaluation and validation, as presented in the subsequent chapter.
