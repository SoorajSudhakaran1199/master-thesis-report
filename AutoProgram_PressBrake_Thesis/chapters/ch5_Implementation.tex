\section {System architecture}
\subsection {Layered Architecture Design and data flow}
The system adopts a layered architecture in which each module depends exclusively on module in the layered directly beneath it. This pattern is selected because the press brake automation context imposes three constraints that unstructured flat module design cannot satisfy simultaneals, independently testable constraints evaluation, maintenance safe replicability and structural enforced safety ordering.
Testability is achieved by enabling the module to be evaluated using synthetic pose data and YAML-based configuration inputs, without the need for an active WebSocket connection. This isolation is essential for verifying the orientational classification mathematics and grip feasibility calculations, because that computation cannot be inferred correctly from a live system alone. Replaceability is ensured by a modular architectural approach in which changes to the grip position algorithm are localized within the constraint evaluation layer. The planning and motion layers are structurally isolated and maintain no direct dependencies on constraint evaluation modules, thereby satisfying the requirements of NFR-02. Safety ordering is maintained through a structured design in which pre-execution safety validation is implemented in an independent layer executed prior to any motion commands. This approach ensures that future modifications cannot inadvertently reposition safety checks after motion initiation, thereby satisfying FR-07 and NFR-03.
Five distinct layers are defined within the system architecture, each with a clearly assigned responsibility. Layer 1 (Input and Configuration) is responsible for acquiring all required parameters from the input file, along with the operator’s bend-side selection, prior to the establishment of any WebSocket connection. Layer 2 (Geometry and Constraint Evaluation) performs the computation of geometric and physical constraints based on live tracker data, while remaining strictly limited to evaluation tasks and producing no motion commands. Layer 3 (Planning and Decision Logic) determines the overall execution strategy and coordinates the interaction between Layers 2 and 4, without directly generating motion instructions. Layer 4 (Motion Generation and Communication) serves as the exclusive interface for robot communication, generating LIN and PTP waypoints, converting them into JSON format, and transmitting them via an authenticated WebSocket connection. Layer 5 (Safety and Validation) is invoked at the beginning of every session and enforces a mandatory validation step, preventing further execution until explicit operator confirmation is obtained.
