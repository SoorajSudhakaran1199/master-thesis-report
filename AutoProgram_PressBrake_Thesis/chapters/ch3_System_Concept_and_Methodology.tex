\section{Problem Definition and Objectives}
\label{Problem-Definition-and-Objectives}

Industrial robots are widely used in press brake sheet metal bending processes, primarily through manual programming or predefined programming approaches. These methods are effective in structured production scenarios where part geometry, position, and bending sequences remain constant. However, in modern manufacturing environments where product variation is high, these approaches require frequent manual reprogramming, resulting in increased setup time and reduced efficiency.

A key challenge in robotic sheet metal bending arises from the fact that the geometry of the workpiece changes after each bending operation. These geometric transformations directly affect robot reachability, grip feasibility, and the selection of valid grip points, as well as the generation of feasible motion trajectories. Consequently, handling and regripping operations must be carefully planned at each stage of the process. Previous research indicates that managing these aspects is one of the most complex and time-consuming tasks in robotic bending, particularly when performed manually.

From a methodological perspective, conventional robot programming approaches operate at a low level of abstraction. In such approaches, programmers are required to explicitly define robot paths, tool configurations, and individual waypoints. This results in programs that are tightly coupled to specific robot setups, grip positions, and tool configurations, making them difficult to adapt when reorientation or regripping is required. As system complexity increases, these low-level programming approaches do not scale effectively, particularly in flexible manufacturing environments where frequent adjustments are necessary \cite{Pan2012Survey}.

Although research has explored higher-level programming approaches that integrate motion execution with decision-making in a unified framework, such methods have not been fully applied to press brake sheet metal bending processes where changes in workpiece geometry and position must be explicitly considered. As a result, there remains a lack of a systematic and integrated approach for handling these challenges.

Based on these observations, the central problem addressed in this thesis can be defined as follows:
There is a lack of a systematic approach for the automatic generation of robot programs for press brake sheet metal bending that explicitly considers changing workpiece geometry, handling feasibility, and regripping requirements, while minimizing manual programming effort.

The central objective of this thesis is the automatic generation of robot programs for sheet metal handling and bending operations, thereby reducing manual programming effort and improving adaptability to varying workpiece geometries.

To achieve this objective, this work proposes a conceptual and methodological framework that integrates bending, handling, regripping, and orientation management within a unified workflow. The system is designed to automatically generate robot trajectories and execution logic based on input parameters, without requiring manual definition of waypoints or motion sequences.

The specific objectives of this work are:
\begin{itemize}
    \item Develop a method for the automatic generation of robot programs based on workpiece geometry and process parameters.
    \item Generate feasible robot trajectories while considering geometric, kinematic, and workspace constraints.
    \item Support multi-stage bending operations, including reorientation and regripping of the workpiece.
    \item Develop a method for determining feasible grip points based on geometry, accessibility, and process stage.
    \item Enable integration with an industrial robot programming environment through a communication interface.
    \item Reduce manual programming effort while ensuring consistent and reliable system behaviour.
\end{itemize}

The proposed approach is validated within a virtual simulation environment compatible with industrial robot systems. The scope of this thesis is limited to conceptual development and simulation-based evaluation.

\section{Requirement Definition and Management}
\label{Requirement-Definition-and-Management}

The development of the proposed system is guided by a structured set of requirements derived from the problem definition presented in Section 3.1. These requirements define the expected functionality, system behaviour, and operational constraints, and ensure that the solution aligns with the objective of automatic generation of robot programs for sheet metal bending operations.

To maintain clarity and traceability throughout the development process, the requirements are organised into functional, non-functional, system-level, and software-specific categories. This structured classification supports systematic design, implementation, and validation of the proposed approach.


\subsection{Functional Requirements}
\label{functional-Requirement}

The functional requirements define the core capabilities of the proposed system, with a primary focus on enabling the automatic generation of robot programs for sheet metal bending operations. These requirements describe how the system processes input data, generates robot motion, and ensures feasibility across multiple stages of the bending process.

The most critical requirement of the system is the ability to automatically generate robot programs based on operator-defined inputs, thereby eliminating the need for manual programming of robot trajectories and motion sequences. This requirement directly addresses the limitations identified in existing approaches and forms the foundation of the proposed solution.

To achieve this, the system shall generate feasible robot trajectories for bending and handling operations based on predefined target poses and process parameters. The generated trajectories must satisfy geometric and kinematic constraints to ensure that the robot can physically execute the planned motion within the defined workspace.

The system shall support multi-stage bending processes, including reorientation and regripping of the workpiece. Since the geometry of the sheet changes after each bending operation, the system must determine feasible grip points dynamically based on the current process stage, accessibility, and workpiece configuration. This ensures stable handling and continuity of the bending sequence.

In addition, the system shall validate all generated motions prior to execution. If infeasible conditions are detected, such as unreachable poses or invalid configurations, the system shall prevent execution and initiate a replanning process to generate an alternative feasible solution. If recovery is not possible, the system shall safely terminate execution to avoid unsafe conditions.

Furthermore, the system shall enable simulation-based validation of the generated robot programs within a virtual environment. This allows verification of the planned sequence before execution and ensures consistency between the generated program and the system constraints.

\subsection{Non-Functional Requirements}
\label{non-functional-requirements}

The non-functional requirements define the quality attributes of the proposed system and ensure that it operates reliably, efficiently, and in a manner suitable for industrial applications. These requirements describe how the system performs under various conditions and how it supports usability, maintainability, and robustness.

The system is designed to provide a structured and user-friendly interaction, enabling operators to define process inputs without requiring detailed knowledge of low-level robot programming. This improves accessibility and reduces the complexity associated with traditional programming approaches.

In addition, the system shall ensure reliable and consistent behaviour by producing deterministic outputs for identical input conditions. This is particularly important in industrial environments, where repeatability and predictability are essential for safe and efficient operation.

From a design perspective, the system follows a modular architecture, allowing individual components such as planning, validation, and execution to be developed, maintained, and extended independently. This modularity enhances maintainability and enables future improvements without affecting the overall system structure.

The system also incorporates robustness and tolerance to minor deviations in input parameters and process conditions. It is designed to handle variations in workpiece geometry within the defined constraints while maintaining stable operation and consistent output.

Furthermore, the system supports scalability by enabling adaptation to different process configurations and workpiece variations within the predefined scope. This ensures that the approach remains applicable across a range of similar industrial scenarios.

\subsection{System Constraints and Assumptions}
\label{System-Constraints-and-Assumptions}

The proposed system is developed under a set of clearly defined constraints and assumptions that establish the scope and ensure predictable system behaviour. The geometric modelling of the workpiece is limited to rectangular sheet metal components consisting of exactly four edges aligned with the global coordinate system. Rotated or non-axis-aligned sheet configurations are not considered. A single global wall height parameter is assumed for all bending operations, and variations in wall height across different edges are not supported. In addition, the representation of internal features is restricted to circular holes defined by their centre coordinates and radius. More complex geometries, such as polygonal cut-outs or irregular shapes, are not included in the current implementation.

The bending process is also subject to strict simplifications. Only right-angle (90°) bending operations are supported, and no provision is made for variable or user-defined bend angles. Each edge of the sheet can be associated with only one bending operation, resulting in a one-to-one mapping between edges and bends. This restriction ensures a deterministic and structured bending sequence. Furthermore, the number of bending operations is limited to a maximum of four on each side of the workpiece, including both primary and opposite-side bending stages.

From a system perspective, the robot configuration, tooling setup, and workspace layout are assumed to remain fixed throughout operation. The motion generation process relies on a predefined tool centre point configuration, and all generated trajectories are expressed with respect to this reference. The system assumes the use of a vacuum-based gripping mechanism controlled through a predefined input-output configuration. Changes to tool geometry, tool centre point definition, or input-output wiring are not dynamically handled and require manual reconfiguration of the system.

The implementation also assumes a structured and predefined representation of objects within the execution environment. The system depends on consistent identification and positioning of workpieces and support structures, and deviations from the expected configuration may lead to incorrect execution behaviour. As a result, the workflow is tightly coupled to the predefined virtual cell setup.

With respect to process capabilities, the system supports only vacuum-based gripping strategies. Grip feasibility is evaluated using simplified physical considerations such as pressure distribution, friction, and load capacity. Alternative gripping methods, including mechanical, magnetic, or multi-fingered grippers, are not considered within the scope of this work.

Finally, the scope of the proposed system is limited to rule-based program generation, geometric reasoning, and simulation-based validation. Advanced functionalities such as dynamic collision-free trajectory generation, real-time motion adaptation, and environment-aware path optimisation are explicitly excluded. These constraints ensure that the system remains deterministic, reproducible, and aligned with the intended focus on automatic program generation within a controlled industrial setting.

\subsection{Software Platform and Tool Requirements}
\label{sec:software-platform-tool-requirements}
The software platform and tool requirements define the technological environment, communication framework, and execution context necessary for implementing the proposed system. These requirements ensure that the system supports automated generation, validation, and execution of robot programs within a structured and industrially relevant setup.

The software-related requirements are defined as SR-01 to SR-03 and are further detailed in the following subsections.

The system shall operate within a virtual robot programming environment that provides capabilities for simulation, execution, and validation of robot programs. In this work, the drag\&bot platform is used as the designated virtual environment, enabling structured testing and verification of generated robot trajectories under controlled conditions. This environment ensures consistency between the planning module and the execution context while supporting simulation-based validation of the generated programs.

The system shall communicate with the execution environment through a unified communication interface that enables the exchange of data between system components. This communication is realised using the AnyRobot interface, which provides an abstraction layer for interacting with the robot programming environment. The communication mechanism is based on a \ac{websocket} protocol, allowing bidirectional data exchange for transmitting robot target poses, execution commands, and system feedback. This requirement ensures synchronisation between the planning module and the execution environment during program generation and validation.

Furthermore, the system shall ensure that all generated robot motion targets are defined with respect to a predefined \ac{tcp} configuration. The \ac{tcp} serves as the reference frame for all trajectory computations and motion commands, ensuring consistency between the generated robot program and the configuration of the robot within the execution environment. This requirement guarantees that the generated motions are physically meaningful and compatible with the defined tool setup.

In addition, the system shall support structured data exchange between internal components, including input parameters, geometric representations, generated trajectories, and validation results. The software architecture shall follow a modular design, enabling clear separation between planning, validation, and execution modules. This modularity enhances maintainability, scalability, and future extensibility of the system.

Finally, the system shall enable simulation-based validation of generated robot programs within the defined virtual environment prior to execution. This ensures that the generated trajectories comply with system constraints and process requirements, thereby improving reliability and reducing the need for manual intervention.



\subsubsection{SR-01 Virtual Execution Environment}
The system shall operate within a virtual robot programming environment that supports simulation, execution, and validation of robot programs. In this work, the drag\&bot platform is used as the designated runtime environment for executing and validating all generated robot trajectories.

The drag\&bot environment provides a unified interface for robot motion execution, object handling, and input-output operations, allowing the planning system to interact with the robot model in a controlled and structured manner. This ensures that all generated programs can be evaluated consistently within a virtual representation of the target press brake cell without requiring physical hardware access.

By operating within this environment, the system enables reliable simulation-based validation of robot programs, ensuring that functional requirements related to trajectory generation, handling, and process sequencing are verified prior to execution. The use of a virtual runtime environment also supports reproducibility of results and reduces dependency on physical system availability.

\paragraph{Acceptance Criteria — SR-01}
The system shall establish a stable connection to the virtual runtime environment, and all generated robot motions, service calls, and input-output operations shall be executed and validated successfully within the simulation environment.

\subsubsection{SR-02 Communication Interface Requirement}
The system shall communicate with the robot execution environment through a unified communication interface that enables structured interaction between the planning module and the runtime system. In this work, the AnyRobot interface is used as the exclusive communication layer between the planning system and the execution environment.

The communication shall be implemented using a \acs{websocket}-based protocol, enabling bidirectional data exchange for transmitting robot motion commands, input-output signals, object handling operations, and system feedback. This approach provides a consistent abstraction layer for interacting with the robot programming environment without requiring direct access to robot-specific control interfaces.

By using a unified communication interface, the system ensures that all commands and execution requests are transmitted in a structured and controlled manner, supporting maintainability and compatibility across different system configurations. This abstraction also enables the planning system to remain independent of specific robot controller implementations.

\paragraph{Acceptance Criteria — SR-02}
All communication between the planning module and the execution environment shall occur through the defined communication interface. A valid connection shall be established before command transmission, and all motion, input-output, and service operations shall be successfully executed and acknowledged within the simulation environment.

\subsubsection{Tool Centre Point Definition Requirement SR-03}
The system shall define all robot motion targets with respect to a predefined \ac{tcp} configuration. The \ac{tcp} represents the reference frame of the end-effector and is used as the basis for all trajectory generation and motion planning operations.

All generated robot poses, including approach positions, handling configurations, and placement targets, shall be expressed in relation to the \ac{tcp}. This ensures consistency between the planning module and the execution environment, and guarantees that the generated trajectories correspond to the physical geometry of the tool.

The \ac{tcp} configuration is defined externally and remains fixed during system operation. Any changes to the tool configuration or \ac{tcp} definition require corresponding updates to ensure alignment between the generated trajectories and the execution environment. This requirement ensures that motion accuracy and handling feasibility are maintained throughout the process.

\paragraph{Acceptance Criteria — SR-03}
All generated robot motion targets shall be consistent with the predefined \ac{tcp} configuration, and any modification to the \ac{tcp} definition shall be reflected correctly in the generated trajectories without requiring structural changes to the system logic.

\subsection{System Traceability}
\label{sec:system-traceability}

Requirements traceability is a fundamental principle in systematic engineering development, ensuring that all defined requirements are consistently reflected in the system design, implementation, and validation stages. In the context of the proposed automatic robot program generation system, traceability ensures that the transition from conceptual objectives to executable functionality remains transparent, structured, and verifiable.

Each requirement defined in Section~\ref{functional-Requirement} (Functional Requirements) and Section~\ref{non-functional-requirements} (Non-Functional Requirements), as well as the software requirements (SR-01 to SR-03), is assigned a unique identifier (e.g., FR-01, NFR-01, SR-01). These identifiers serve as persistent references throughout the entire development lifecycle and enable systematic tracking of requirements across different stages of the system.

The requirement identifiers are used consistently to establish clear relationships between requirements, system components, and validation procedures. In particular:

\begin{itemize}
    \item Each requirement is implemented within a specific system module.
    \item Each requirement is verified through a defined test scenario.
    \item No requirement remains unaddressed in the implementation.
    \item All implemented functionalities can be traced back to a corresponding requirement.
\end{itemize}
\paragraph{Forward Traceability}
Forward traceability ensures that every defined requirement is realised in a corresponding system component or functional module. This confirms that all requirements are properly implemented within the system architecture.

\paragraph{Backward Traceability}
Backward traceability ensures that every implemented functionality can be traced back to an explicitly defined requirement. This guarantees that no unnecessary or unjustified functionality is introduced into the system.

By mapping each requirement to corresponding implementation modules and validation scenarios, the development process becomes structured, auditable, and reproducible. This is particularly important in systems involving automated decision-making processes, such as reachability evaluation, grip point determination, regripping logic, and opposite-side handling.

In addition, traceability improves system maintainability and supports future extensions. Changes to system requirements can be systematically analysed by identifying the affected components and validation procedures. This enables efficient impact analysis and reduces development risk.
