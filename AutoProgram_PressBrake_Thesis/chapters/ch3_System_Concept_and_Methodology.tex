\section{Problem Definition and Objectives}
\label{sec:problem-definition-and-objectives}

The state-of-the-art analysis indicates that existing approaches do not fully provide an integrated solution for robotic sheet metal bending. In particular, planning tasks such as grasp selection, regripping, and trajectory generation are often handled separately, which limits the level of automation.

A key challenge arises from the changing geometry of the workpiece during the bending process. Each bending step modifies the part shape, affecting reachability and feasible handling strategies. The problem addressed in this work is the lack of a systematic method for automatically generating robot programs for press brake sheet metal bending that considers changing workpiece geometry, handling feasibility, and regripping requirements within a unified framework.

The objective of this thesis is to develop a method for the automatic generation of robot programs that improves adaptability to varying workpiece geometries while reducing manual programming effort and programming time. In addition, the approach aims to enable usability for non-expert operators by requiring only the specification of the desired output. To achieve this, a unified framework is proposed that integrates handling, regripping, and trajectory generation into a single workflow. The approach focuses on generating robot motions directly from process inputs rather than relying on manually defined waypoint sequences, particularly for multi-stage sheet metal bending operations.

The specific objectives are:
\begin{enumerate}
    \item Automatic generation of robot programs based on geometry and process parameters.
    \item Constraint-aware trajectory generation considering workspace and kinematic limitations.
    \item Support for multi-stage bending, including regripping and reorientation.
    \item Determination of feasible grip points based on accessibility and process stage.
    \item Integration with an industrial robot programming environment.
\end{enumerate}

The proposed method is evaluated in a simulation environment, with a focus on conceptual development and virtual validation.

\section{Requirement Definition and Management}
\label{sec:requirement-definition-and-management}

The system concept developed in this thesis defines a structured set of requirements based on the problem described in Section~\ref{sec:problem-definition-and-objectives}. These requirements specify the expected functionality and describe the intended system behaviour in a clear and transparent manner.

The requirements are organised into functional requirements (\acs{fr}), non-functional requirements (\acs{nfr}), and software requirements (\acs{sr}), based on industrial and company-specific criteria. This structured classification supports consistent system design, implementation, and validation, while also enabling traceability throughout the development process.

Furthermore, the defined requirements provide a basis for evaluating whether the developed system satisfies the intended objectives during the validation phase.

For consistent interpretation, several terms are used with fixed meanings throughout the thesis. An execution-ready workflow is a generated or prepared sequence that can be started in the virtual cell without additional manual waypoint teaching or function-block sequencing. A configuration change denotes an update of workpiece, process, or safety parameters without source-code modification. Deterministic behaviour means that repeated runs under the same scenario definition lead to the same completion, failure, or controlled-stop classification. A controlled stop denotes safe interruption before infeasible or unsafe continuation; it is therefore treated as safe system behaviour, but not as a completed execution trial.

\subsection{Functional Requirements}
\label{sec:functional-requirements}

The functional requirements define the capabilities that the system must provide to enable automatic generation of robot programs for sheet metal bending operations. A primary requirement is that the program must be generated from operator-defined inputs. This directly addresses the limitations of manual programming identified in the previous chapters and forms the core of the proposed solution.

The system must generate feasible robot trajectories for handling and bending operations based on target poses and process parameters. These trajectories must satisfy geometric and kinematic constraints within the defined workspace. Furthermore, the system must support bending on multiple faces of the sheet, requiring multi-stage operations that include reorientation and regripping.

Grip positions must be determined automatically according to the process stage, as variations in workpiece geometry require adaptive grasp selection to ensure stable handling throughout the process sequence. The generated programs and trajectories must be verified prior to execution. If infeasible conditions are detected, such as unreachable poses or invalid configurations, the system must initiate replanning or terminate execution safely when recovery is not possible.

The complete program must be validated in a simulation environment before execution to ensure that the generated sequence is feasible, consistent, and compliant with system constraints. \subsection{Non-Functional Requirements}
\label{sec:non-functional-requirements}

In addition to functional requirements, non-functional requirements define the quality attributes that the system must exhibit. These requirements describe how the system behaves during operation and cover aspects such as usability, maintainability, robustness, consistency, and repeatability.

A key design objective is to ensure usability, allowing operators to define process inputs without requiring detailed technical knowledge. This ensures that usability is considered as a fundamental requirement for practical adoption. The system must produce deterministic and repeatable results for identical input conditions, thereby ensuring consistent behaviour.

The system architecture separates planning, validation, and execution into distinct components, enabling modular development, maintainability, and extensibility without introducing unnecessary dependencies across the system. Maintainability is further supported by a structured design that facilitates modification and future enhancements.

Within the defined scope, the system should tolerate minor variations in input parameters and process conditions while maintaining stable and reliable output. Robustness is addressed by handling variations without compromising system performance or validity of results.

\subsection{Software Platform and Tool Requirements}
\label{sec:software-platform-tool-requirements}

The software platform and tool requirements define the technical environment in which the proposed system is implemented and evaluated. They are grouped as \acs{sr}-01 to \acs{sr}-03 because the virtual runtime, communication interface, and tool reference frame must work together for reliable program generation and execution.

\phantomsection\label{subsubsec:sr-01-virtual-execution-environment}
\noindent\textbf{\acs{sr}-01 Virtual execution environment.}
The system shall operate within a virtual robot programming environment that supports simulation, execution, and validation of generated robot programs. In this work, drag\&bot is used as the runtime environment for the virtual UR5e press-brake cell. The acceptance criterion is that a stable connection to the configured runtime is established before execution and that generated motion, service, object-handling, and input-output operations can be validated in the virtual cell.

\phantomsection\label{subsubsec:sr-02-communication-interface-requirement}
\noindent\textbf{\acs{sr}-02 Communication interface.}
The planning system shall communicate with the execution environment through the AnyRobot interface using WebSocket (web-based communication protocol). This interface provides a controlled abstraction for robot motion commands, input-output signals, object handling, and runtime feedback without requiring direct access to robot-specific controller interfaces. The acceptance criterion is that every relevant runtime request receives acknowledgement before the workflow continues.

\phantomsection\label{subsubsec:sr-03-tool-centre-point-definition-requirement}
\noindent\textbf{\acs{sr}-03 Tool centre point definition.}
All generated motion targets shall be defined with respect to the configured \ac{tcp}. In this thesis, the required \ac{tcp} identifier is \texttt{project\_3\_tcp}, including the documented offsets and orientation parameters. The acceptance criterion is that any future \ac{tcp} modification is handled through configuration and reflected in the generated poses without structural changes to the planning logic.

\subsection{System Constraints and Assumptions}
\label{sec:system-constraints-and-assumptions}

The proposed system is developed under a defined set of constraints and assumptions. At the geometric level, the workpiece model is restricted to rectangular sheet metal parts with exactly four edges aligned with the global coordinate system. A single global wall height parameter is assumed for all bending operations; therefore, edge-specific wall height variation is not supported.

Internal features such as holes are considered only for avoidance during gripping. Circular holes are defined by their centre coordinates and radius, and rectangular cut-outs can be specified using predefined coordinate inputs. However, more complex geometries, such as polygonal cut-outs or irregular contours, are outside the scope of this work.

The bending process is limited to right-angle ($90^\circ$) bends, and user-defined bend angles are not supported. Each sheet edge can be assigned to only one bending operation. Bending can be performed either on the primary side or the opposite side, but simultaneous selection of both sides is not supported. The total number of bending operations is limited to four edges of the workpiece, including both primary and opposite-side bending stages.

From a system perspective, the robot configuration, tooling setup, and workspace layout are assumed to remain fixed during operation. The system assumes the use of a vacuum-based gripping mechanism with a predefined \ac{tcp} configuration. No external perception systems, such as cameras, \ac{lidar}, or other vision-based sensors, are used. All robot programs, poses, grip points, regripping decisions, and motion sequences are generated computationally based on predefined geometric input parameters, operator-defined inputs, and configuration data. Consequently, the system does not rely on real-time sensing but derives handling strategies through deterministic calculations.

Grip feasibility is evaluated using simplified physical considerations, including pressure distribution, friction, and load capacity. Alternative gripping methods, such as mechanical, magnetic, or multi-fingered grippers, are excluded.

Advanced capabilities, including dynamic collision-free trajectory generation, real-time motion adaptation, and environment-aware path optimisation, are not considered. These constraints ensure that the system remains aligned with the objective of deterministic, consistent, and repeatable automatic program generation within a controlled industrial environment.

\subsection{System Traceability}

Each functional, non-functional, and software requirement is assigned an identifier such as \acs{fr}-01, \acs{nfr}-01, or \acs{sr}-01. These identifiers are reused in the implementation chapter and in the validation tables so that every implemented function can be linked back to its requirement and verification activity.
