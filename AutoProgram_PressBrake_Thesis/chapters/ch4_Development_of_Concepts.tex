\section{Purpose and scope of concept development}
Concept development is an essential part of structured design, which consists of the design phase where different principles solutions are developed and evaluated before implementation. This is an essential part of systematic engineering design. By evaluating different options with respect to certain criteria before proceeding, the chances of selecting an inappropriate design path are minimized. REF The concept development phase is crucial for the success of the project, as it allows for the exploration of different design alternatives and the selection of the most suitable one based on a structured evaluation process.
\par The gap in the research, as identified in Section \ref{Research Gap and motivation}, reveals the absence of an effective systematic approach to automatically generate robot programs for press brake sheet metal bending. This approach should consider changes in workpiece geometry, gripping, re-gripping, and pre-execution pose, minimizing manual programming. The gap in the research is addressed in the form of measurable engineering objectives, as discussed in \ref{CH_3_System Concept and Methodology}, with respect to functional requirements FR-01 to FR-07 and non-functional requirements (NFR-01 to NFR-05), which constrain how it must behave; and software platform requirements SR-01 to SR-03 (Table \ref{tab:req_traceability_matrix}), which are fixed by the industrial partner environment and therefore non-negotiable. Three conceptually distinct approaches are developed in this chapter because the research gap can plausibly be addressed by different paradigms, and the selection must be justified rather than assumed
\par Three solution principles are proposed. The first, designated Concept A, proposes a guided teaching approach in which a structured software workflow supports the operator during conventional manual robot programming. Concept B proposes an automatic program generation system in which waypoint, grip positions , regrip sequences and opposite side handling strategies are derived automatically by evaluating the inputs configuration file , with all communication to the robot runtime conducted via the AnyRobot Interface over an authenticated WebSocket channel as required by SR-01 and SR-02.\Cite{dragandbot_anyrobot_2025} Concept C is a CAD integrated offline programming in which a digital cell model is used to generate , validate and execute robot program within a simulation environment \cite{Siciliano2016Robotics},\cite{Pan2012Survey}
\par The concept decision is made using Weighted Sum Model (WSM), a quantitative decision support method in which evaluation criteria are assigned relative weights and each concept is scored against criterion. This method satisfies the requirement that concept selection must be based on structure rather than on qualitative judgment. The morphological box and preferences analysis methods are alternative methods, The WSM is selected because it enables simultaneous multi-criteria weighting and produces a single quantitative score for each concept, which ensures appropriate for comparing concepts.

\section{Concept A – Structured operator Workflow with Guided Teach in programming}
\label{Concept A – Structured operator Workflow with Guided Teach in programming}
\subsection{Methodological Framework}
Concept A retains the conventional teach pendant paradigm as the mechanism for defining robot motion and introduces a software-based layer that structures and sequences the operator interaction. In this method, the operator is guided through a step-by-step workflow that collects process inputs, including the desires bending sequences, bend side selection and current workpiece positions. The operator then executes each action directly via robot teach pendant or control interface using the function blocks.
\par This Concept is grounded in the established practice of teach pendant programming described in section\ref{Manual and Teach Pendant Programming}. As identified in the literature, teach pendant programming is reliable and widely used in structured manufacturing environment where part geometries and process parameters are fixed \cite{Siciliano2016Robotics}. The guidance layer introduced in this concept (A) reduced the risk of operator errors and provides a structured interface than unguided teach pendant operation, but it does not alter the fundamental that all robot position and waypoints are defined through direct physical interaction with the robot.
\par Regripping operation, orientation changes, full side bending operation for a rectangular sheet under this concept A remains the responsibility of the user to define and execute. The system provides instructional prompts but does not execute, validate or generate any waypoints and position data. No interface to the robot runtime environment is required beyond standard teach pendant connectivity, so the concept does not operate within the drag and bot virtual simulation runtime and does not satisfy SR-01 or SR-02 as defined in  Section \ref{Software Platform and Tool requirement}. The system does not possess object tracking subsystems, evaluate geometric constraint, grip position calculations or assess kinematic feasibility before execution.

\subsection{System Structure}
\label{System Structure}
The system structure of concept A consists of two layers. A dialogue management layer runs on an external computer and presents the operator prompt through functional blocks or graphical interface by manual program generation. A robot controller layer receives waypoint generated manually by the operator through teach pendant and execute them. No intermediate computation layer for geometric reasoning, constraint evaluation, or motion generation exists between these layers. The architecture imposes no dependency on object tracking sensor data or trajectory generation interfaces.

\subsection{Critical Evaluation}
\label{Critical Evaluation}
Concept A straightforward to implement and compatible with any industrial robot controller without software modification. The operation of the system is fully transparent and observable by the operator, which reduces the risk of unreachable and kinematics error occur during the unreachable target pose. These characteristics make it suitable for low variety, structured production scenario where process parameters are stable across batches.
\par However , the fundamentals limitation if this concept are significant in the context of research gap ,programming effort is not yet reduced because knowledge of robot kinematics , tooling constraints , regripping strategies and bending sequence algorithm should need to applied by the operator for every session \cite{Siciliano2016Robotics}, \cite{Pan2012Survey}. Minor changes in sheet geometry , workpiece holder placement requires full re teaching of the affected trajectories , which contradicts the flexible objective stated  in section \ref{Problem-Definition-and-Objectives} \cite{Siciliano2016Robotics}, REF 26. Regripping operation and full side bending operations must ne manually planned , which introduces a chances of operator error and increase the cycle time .No pre execution validation of target poses is performed , kinematic configuration are  discovered only during the physical or virtual robot motion which leads to safety risk and a source of unplanned downtime \cite{Siciliano2016Robotics}.
\par The software guidance layer of concept A provides process management but no automation level, it addresses the unstructured operator workflow without addressing root cause, which is the requirement for manual position definition. Concept A does not contribute to the primary objective of automatic program generation and failed to satisfy most of the functional and non-function requirements defined in \ref{tab:functional_requirements}. and REF NFR.

\section{Concept B – Automatic Program Generation based on rules with Integrated Constraint Validation.}
\label{Concept B – Automatic Program Generation based on rules with Integrated Constraint Validation.}
\subsection{Methodological Framework}
Unlike Concept A, which retains manual position definition, Concept B eliminates it entirely. Concept B proposes an automation level, rule based, automated program for generation system in which all robot waypoints, grip positions, regrip sequences, opposite side handling operations and strategies are derives automatically from geometric input parameters and a structures YAML configuration file: operator interaction is limited selection of required output selection before execution and confirmation of generated programs visually. No manual waypoint generation, direct teaching or any runtime operation or decisions are required during program execution.
\par The system communicates with the robot runtime through AnyRobot interface, a robotics application program (API) Developed by KEBA \textbackslash\ Drag and Bot GmbH that provides standardized method for controlling industrial robots from different manufacturers via WebSocket communication\cite{dragandbot_anyrobot_2025}. The planning Software operates as the WebSocket client, the drag and bot runtime act as the server. This architecture establishes a clean separation between the planning computation layer and robot execution layer, which is a recognized design principle \cite{Thramboulidis2013MDE} .
\par Workpiece pose data is retrieved in real time from drag and bot object tracking subsystem and processes by an orientation validation component , which determines whether the tracked sheet orientation is admissible for the planned bending operation by applying a three level priority strategy ,a side normalized orientation is evaluation first , followed by original tracked orientations by the object tracker and finally a 180 degree rotated strategy , when neither of the first two falls within the configurable window. This Three level hierarchy ensures that valid gripping orientations and positions are identified for any initial sheet placement on the cell floor, which eliminates the need for operator prepositioning. Before grip position calculation, the program validated the sheet position is within the robot cell. This is applied to avoid the kinematic reachability error occurred during the program execution. The zone-specific admissibility limits are specific limits are robot cells configuration are configured in the input sections and require no code modification when cell layout changes. This design decision satisfies NFR 02as defined in table \ref{tab:nfr_table} and NFR 05 as defined in table \ref{tab:nfr_table}.
\par Grip position are computed by a parameterized grip planning component s that uses the sheet dimension, mass suction cup diameter , rated shear force and edge clearance margin which all are defined in the input configuration files :candidate grip position reevaluated against edge clearance and cup spacing constraints and against the vacuum holding force which is derived from the relationship between suction pressure , cup contact areas and dynamic loading during transport \cite{VacuumGripperModeling}.Grip feasibility is evaluated before kinematic reachability assessment, ensuring that only variable grip configurations are submitted to the motion generation layer. This ordering prevents unsafe handling states that would result from a grip position that is kinematically reachable but physically unable to reach the sheet during transport \cite{VacuumGripperModeling} .
\par When the current grip configuration does not allow the targeted pose to be reached, an automated regrip cycle is initiated. The cycle places the sheet on a designated orientation table, repositions the robot to reset and then regrasp the sheet at an orientation that restores full reachability. This regrips logic directly satisfies FR03 as defined in table \ref{tab:functional_requirements} .
\par Opposite side bending is also supported through this concept through a dedicated module that executes a structured sheet flip sequence. After all primary bending operations are completed, the program evaluates whether the operated has selected for opposite side bends. If so, the sheet passes to flip position through a coordinated sequence of motion, gripper activation, and object attachment operations targeting positions to flip the sheet. Afte the flip, the opposite bending sequence is executed under the same validation, including orientation normalization, grip feasibility evaluation and reachability assessment before the waypoints is generated. This enforcement of validation across both primary and opposite side bending operation ensures consistent safety behavior throughout th full step bending process \cite{Gupta1998SheetMetalBending}
\par The motion trajectories are generated in linear cartesian motion commands using minimum jerk velocity interpolation profile REF 16: This profile minimizes the third derivatives of position over the motion, producing smooth velocity transition between waypoint that reduce peak acceleration and gripper loading forces during sheet transport. This is requirement for maintaining vacuum grip stability under dynamic conditions \cite{VacuumGripperModeling}.A singularity avoidance strategy ensures the robot arm does not pass through kinematically degenerate configurations during the approach phase \cite{Siciliano2016Robotics}. All motion targets are expressed relative to the pre-defined tool center point registered in the drag and bot tool management system. This reference is mandatory because SR-03 requires that all generated flange poses be consistent with the physical gripper geometry of the KEBA press brake cell, and the defined TCP entry encodes that geometry with the exact pose values specified in Section \ref{Software Platform and Tool requirement} \cite{dragandbot_anyrobot_2025}. 
\subsection{system structure}
\label{system structure Concept B}
The structure of Concept B consists of Five layers as defined in section {System-Architecture-and-Design}. The input and configuration layer that collects all required inputs for the programming. The geometry and constraints evaluation layer applies grip feasibility rules, edge clearance checks and zone-based orientation constraints. The planning and decision logic layer determines the execution strategy, which decides the program to be direct execution or regrip required execution or workpiece flipping strategy, based on reachability and orientation validity . The trajectory planning layer produces linear cartesian waypoints with minimum jerk velocity profiles. The safety and validation layer applies pre-execution pose check before the command is published to the robot runtime.
\par This WebSocket channel of the Any robot interface allows to connect all five layer to drag and bot virtual simulation run time \cite{dragandbot_anyrobot_2025} .The configuration-driven approach allows all process parameters to be trimmed from program logic, allowing the solution to tackle new workpiece geometries simply by modifying the content of configuration files. This was in direct satisfaction of non-functional requirement NFR-02 as described in Section \ref{non-functional-requirements}.
\subsection{Critical evaluation} 
\label{Critical evaluation Concept B}
Concept B is aligned with the research gap stated in Section \ref{Research Gap and motivation} for every dimension identified in the literature. Define waypoints, plan regrips, and sequence work on the opposite side automatically from geometric parameters instead. A pre-execution pose validator guards against unsafe execution states before motion starts. This allows for configuration driven architecture that can adapt to new part geometries without the need for source code changessatisfying FR-01, NFR-03, NFR-04, and NFR-05. Configuration-driven parameterization satisfies NFR-02. The system operates exclusively within the drag and bot runtime via the AnyRobot Interface, satisfying SR-01 and SR-02. All motion targets reference the pre-defined tool center point, satisfying SR-03. All fifteen requirements in Chapter \ref{CH_3_System Concept and Methodology} are therefore addressed by the concept design.
\par The primary constraints that Concept B operates within are those identified within Section \ref{System-Constraints-and-Assumptions}. The system operates within a rectangular sheet geometry with fixed 90-degree bend angle constraints. The integration with the KEBA robot controller hardware, which is part of the KEBA robot driver layer within the drag and bot software stack \cite{dragandbot_anyrobot_2025}, is identified within the future work section and is not included within the scope of this thesis. All validation has been conducted within the drag and bot virtual simulation environment, which is discussed in this section. The virtual simulation environment used for this evaluation is illustrated in figure \ref {fig:Dragandbot_Simulation} .The environment  represents a simulated press brake cell configured with the drag and bot platform , including the robot , workpiece and interactions required for the program execution .These constraints are explicit and not indicative of design flaws but, rather, define the scope within which the design concept operates.

\section{Concept C – CAD Integrated Offline Programming with Digital Twin Simulation}
\label{Concept C – CAD Integrated Offline Programming with Digital Twin Simulation}
\subsection{Methodological Framework}
Concept C proposes a computer aided design (CAD) integrated offline programming (OLP) approach in which a digital model of the sheet metal workpieces and the robot cell used to plan , generate and validate robot program in a simulation environment , without using physical robot interaction during the programming .The OLP  software evaluates bending sequences , grip positions and regrip programming, kinematic reachability and genreted robot program based on the CAD geometry of the workpiece and tooling .The generated programs are validated inside a simulation before transfer to the robot controller for execution.
\par This approach corresponds to the offline programming section \ref{Offline Programming Approaches for Industrial Robots}. Industrial Olp tools such as ABB Robot Studio ,KUKA: sim And FANUC ROBOGUIDE implement this approach and are used in industry for robot program generation in structured production environment \cite{Pan2012Survey} .The digital twin based evaluation and validation reduces the occurrence of risk by identifying unreachable poses and collision condition before real execution, which has been identified as significant advantage over the teach pendant programming. \cite{Bar2018VirtualCommissioning}
\subsection{System Structure}
\label{System Structure_CAD Integrated Offline Programming with Digital Twin Simulation}
This concept consist of four layers .A cad modelling layer provides digital representations of the robot , press brake , tools and workpiece .An OLP and simulation layer uses the URDF(Unified Robot Description Format) representations to plan the algorithm for robot program through built in kinematic solver .A post processing layer converts the generated programs into controller specific syntax’s robot controller layer communicates the program for exception. Accurate digital twin representation of all cell components are required at the modelling layer small errors in modelling the digital twin model propagate as execution error that require manual re programming during commissioning.\cite{Siciliano2016Robotics} \cite{Pan2012Survey}.
\subsection{Critical Evaluation}
\label{Critical Evaluation_CAD Integrated Offline Programming with Digital Twin Simulation}
Concept C offers meaningful automation advantages for structured, high-volume production environments where accurate cell models are available and OLP tool investment is justified. Simulation-based validation provides strong pre-execution assurance, and the approach is supported by mature commercial software \cite{Siciliano2016Robotics}\cite{Bar2018VirtualCommissioning}. These characteristics make it the dominant paradigm in industrial robotic bending automation at the time of writing.
\par For the scope of this thesis, Concept C presents three fundamental disadvantages that result in its rejection. First, the implementation requires accurate CAD models of the complete robot cells, including the robot, press brake, tooling, fixtures, and workpieces — which represents a substantial engineering preparation effort that is not available within the thesis timeframe. 
\par Second, commercial OLP systems involve high license fees while demanding expert-level instruction - resources simply unavailable within this project's constraints REF Engineering Design: A Systematic Approach . Besides cost, mainstream OLP platforms lack native compatibility with both the drag and bot simulation framework and the AnyRobot WebSocket system, which define the core setup targeted here \Cite{dragandbot_anyrobot_2025}. Connecting such a tool would mean building a bespoke bridge to the drag and bot engine - an extra burden unjustified by timeline or ambition.. Even if the first two limitations were resolved, this third limitation would disqualify Concept C, because SR-01 and SR-02 are non-negotiable constraints from the industrial partner environment.

\section{Concept Decision-Weighed Sum Model (WSM)}
\label{Concept Decision-Weighed Sum Model (WSM)}
\subsection{Methodology}
\label{Methodology WSM}
The quantitative concept selection technique used is the Weighted Sum Model. Each evaluation criterion in the WSM is given a weight based on how important it is to the design objectives. Each concept is then scored against each criterion on a scale of 1 to 5, with 5 denoting full satisfaction and 1 denoting non-fulfillment. Each concept's overall weighted score is calculated by multiplying the corresponding score by each criterion weight. The idea that receives the highest total weighted score is chosen.

\subsection{Evaluation Criteria and Weights}
Six evaluation criteria are defined directly from the functional, non-functional, and software platform requirements of  Chapter \ref{CH_3_System Concept and Methodology}. The weight assigned to each criterion reflects its relative contribution to resolving the research gap identified in Section \ref{Research Gap and motivation}, as justified below
\paragraph {Programming Effort Reduction (25\%)}-This criterion carries the highest weightage because it directly addresses the primary research gap. This makes automation easier by reducing a lot of manual programming especially when parts change frequently. This gap is consistently identified in literature as the most significant barrier to increased automation in robotic bending cells.
\paragraph {Automated Regrip and Opposite-Side or sheet flipping Support (20\%)}: According to Section \ref{Robotic Sheet Metal Bending System}, the most difficult and time-consuming parts of robotic press brake bending that are not sufficiently handled by current methods are regripping and opposite-side handling\cite{Aomura2002RoboticBending}\cite{Gupta1998SheetMetalBending}. The 20\% weight reflects that automating these operations is a core deliverable, not a secondary feature, of the research gap resolution per FR-03 and FR-05 in Table \ref{tab:functional_requirements}.
\paragraph {Pre-Execution Pose Validation (20\%)}: Before robot motion is started, infeasible poses must be identified in accordance with safety regulations NFR-03, NFR-04, and NFR-05. In robotic bending cells, executing unreachable target poses is a major source of system failure as well as a safety risk.
\paragraph {Flexibility for Changing Part Geometries (15\%)}: One of the main goals derived from the research gap is the capacity to adjust to new workpiece variations without reprogramming. NFR-02 is directly satisfied by configuration-driven adaptability, and the 15\% weight indicates that this is a secondary goal following the primary automation requirements. 
\paragraph {Platform Compatibility drag and bot Runtime and AnyRobot Interface — SR-01, SR-02 (10\%)}:The industrial partner environment mandates the drag and bot virtual simulation runtime and the AnyRobot Interface as the exclusive execution and communication platform, formalised as SR-01 and SR-02 in Section \ref{Software Platform and Tool requirement}. A concept that fails SR-01 or SR-02 cannot be implemented or validated within the thesis scope regardless of its theoretical merits, which is why a score of 1 on this criterion effectively disqualifies a concept. SR-03 (project\_3\_tcp) applies equally to all platform-compatible concepts and therefore does not independently differentiate them; it is reflected in the Concept B system structure in Section \ref{system structure Concept B}.
\paragraph {Operator Usability (10\%)}: Non-functional requirement NFR-01 says that the system must be usable by non-expert operators with little interaction during normal operation. The 10\% weight shows that usability is an important quality attribute, but it is not as important as the main automation requirements.

\section{Analysis of results and Concept Decision}
\label{Analysis of results and Concept Decision}
The WSM produces total weighted scores of 1.40 for Concept A, 5.00 for Concept B, and 2.70 for Concept C. Concept B achieves the maximum possible score and is therefore selected as the concept to be developed and implemented in Chapter \ref{ch_5:implementation}. The margin between Concept B and the nearest alternative is 2.70 points, which is not a marginal result: it reflects systematic superiority across every criterion, not a single dominant factor.
\par Concept B meets all six requirements to the highest degree, as indicated by its score of 5.00. Because waypoints are automatically derived from geometric parameters and there is no manual teaching step, programming effort is eliminated. Because specialized software modules implement gripper IO control, object attach and detach sequencing, and multi-step rotation under YAML-configurable parameters with all behavior fully specified before runtime, regrip and opposite-side bending achieve full automation. Orientation validation and spatial zone classification are two independent components that structurally guarantee pre-execution validation because they are both called before any motion command is generated, preventing an invalid pose from reaching the motion generator. NFR-02 is satisfied by configuration-driven sheet parameterization. As required by the industrial partner, the system satisfies SR-01 and SR-02 by operating solely within the drag and bot runtime via the AnyRobot Interface. SR-03 is satisfied since all motion targets make reference to the project\_3\_tcp tool center point. Within the parameters of the thesis, the Python-based implementation is completely feasible \cite{Pahl2007EngineeringDesign}. By restricting interaction to necessary pre-execution choices, the dialog-based operator interface complies with NFR-01.
\par Because Concept A does not meet the five most important requirements, it receives a score of 1.10. Regardless of any other characteristics, its platform compatibility score of 1 indicates that it is incompatible with the industrial partner development platform since it does not function within the drag and bot runtime, meeting neither SR-01 nor SR-02. The concepts teach-pendant architecture prevents it from contributing to any aspect of the research objective, as evidenced by the scores of 1 on programming effort, regrip automation, pose validation, and configuration adaptability \cite{Pahl2007EngineeringDesign}.
\par Because Concept C's CAD-based OLP approach tackles waypoint generation, pre-execution validation, and configuration adaptability during the simulation phase, it receives a score of 2.70. However, the CAD approach's lack of runtime constraint evaluation and requirement for per-variant model rebuild rather than configuration file update limit the score. The platform compatibility score of 1 indicates a structural disqualifier: standard OLP tools are unable to integrate with the AnyRobot WebSocket Interface or the drag and bot runtime, which violates SR-01 and SR-02. This platform incompatibility alone would prevent Concept C from being implemented or validated within the thesis environment, even putting aside the resource and cost constraints \cite{Siciliano2016Robotics} \cite{Pahl2007EngineeringDesign}.
\par Three conceptually different methods for automatic robot program generation in press brake sheet metal bending were developed and assessed in this chapter. The evaluation adhered systematic engineering design methodology because it offers an organized framework for evaluating options based on predetermined criteria prior to committing to implementation, which is necessary for a thesis-level concept decision \cite{Pahl2007EngineeringDesign}. All three of Chapter 3's requirement categories—functional requirements FR-01 to FR-07 (Table\ref{tab:functional_requirements}), non-functional requirements NFR-01 to NFR-05 ( Table \ref{tab:nfr_table} ), and software platform requirements SR-01 to SR-03 (Table \ref{tab:req_traceability_matrix}, Section \ref{Software Platform and Tool requirement})—were used to develop the evaluation criteria.
\par Because Concept A operates independently of the drag and bot platform and AnyRobot Interface required by the industrial partner environment, its teach-pendant architecture cannot reduce programming effort, provide automated constraint validation or regrip support, or satisfy SR-01 or SR-02. As a result, the guided teach-in approach was rejected. These failures are structural: according to Table \ref{Problem-Definition-and-Objectives}, FR-01, FR-03, FR-05, and FR-06 require automated geometric reasoning, which the two-layer teach-pendant architecture is unable to supply.
\par Concept C,method of programming offline: Integration with CAD software for creating digital cell models for use in offline programming (OLP). This method was disregarded because required commercial OLP tools do not exist; accurate digital cells are also not included in the thesis scope. Therefore, the approach as a practical limitation has a structural constraint due to its incompatibility with drag and bot's run-time and the AnyRobot Interface (Section 3.2.4, SR-01, SR-02) \cite{Siciliano2016Robotics}\cite{Pan2012Survey}. Consequently, any partial automation benefits associated with this method could not be achieved using simulation techniques due to these constraints also being exhibited in the simulation environment within this thesis.
\par The rule-based automatic program generation system of Concept B was selected because it achieves the maximum weighted score of 5.00 in the WSM, satisfying all fifteen requirements of Chapter \ref{CH_3_System Concept and Methodology}. This automated system eliminates programming time through automatic determination of waypoints, automates regrip and opposite side bend sequences through dedicated software modules, and verifies whether there is an admissible orientation and spatial reachability prior to the generation of any motion; (b) operates solely in the drag and bot virtual simulation runtime, through use of the authenticated AnyRobot WebSocket Interface. This satisfies both SR-01 and SR-02. All motion targets are computed with respect to the project\_3\_tcp (tool centre point); therefore, it meets requirement SR-03. The technical details about Concept B, including the entire software architecture, interface specifications, algorithm derivation and risk analysis can be found in Chapter \ref{ch_5:implementation}.
