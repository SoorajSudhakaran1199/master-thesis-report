\section{Purpose and Scope of Concept Development}
\label{sec:purpose-scope-concept-development}

Concept development is a fundamental stage in systematic engineering design, in which different solution principles are generated and evaluated before implementation. By comparing alternative solutions against defined requirements, the risk of selecting an unsuitable design solution is reduced \cite{Pahl2007EngineeringDesign}.

The research gap identified in Section~\ref{sec:research-gap-motivation} highlights the absence of a systematic approach for automatic robot program generation in press brake sheet metal bending, where existing solutions do not fully address the defined requirements. These challenges are translated into measurable engineering objectives and requirements in Chapter~\ref{ch:system-concept-methodology}, including functional requirements (\acs{fr}-00 to \acs{fr}-07), non-functional requirements (\acs{nfr}-01 to \acs{nfr}-05), and software platform requirements (\acs{sr}-01 to \acs{sr}-03), with the full traceability mapping provided in Appendix~\ref{app:req-traceability-compliance}, Table~\ref{tab:req-traceability-matrix}.

To address this gap, three conceptual solution approaches are developed and evaluated in this chapter. Concept A represents a structured manual programming workflow, Concept B proposes a rule-based automatic program generation approach, and Concept C explores a \acs{cad}-integrated offline programming methodology \cite{Pan2012Survey,Siciliano2016Robotics}.

These concepts are first compared qualitatively and subsequently evaluated using a weighted scoring method based on defined evaluation criteria. The final concept is selected using the \ac{wsm}, a quantitative decision-making method in which evaluation criteria are assigned relative weights and each concept is scored accordingly. This ensures that the concept selection process is systematic, transparent, consistent, and aligned with the defined requirements.

\section{Concept A -- Structured Operator Workflow with Guided Teach-In Programming}
\label{sec:concept-a-guided-teach-programming}

\phantomsection\label{sec:concept-a-methodological-framework}
\noindent\textbf{Method and workflow.}

Concept A follows a structured manual programming approach in which the operator defines robot motions and execution strategies, typically using a teach pendant as described in Section~\ref{sec:manual-teach-pendant-programming}. In this approach, robot trajectories, gripper actions, and execution sequences are created manually by the user, while the system provides a structured interface to organise the programming process \cite{Siciliano2016Robotics}. The created programs are stored and reused for similar future executions.

This represents a conventional programming method, which improves usability by structuring the sequence of operations and reducing unstructured workflows. The operator constructs the robot program manually within the drag\&bot environment by assembling function blocks for motion execution, gripper control, and sequencing logic.

In this context, waypoint generation is performed manually by moving the robot \ac{tcp} to the required positions and recording these points as configured function blocks. All operations, including gripping, regripping, handling, and opposite-face bending, are defined manually by the operator. This highlights the high implementation feasibility of Concept A. The arrangement and configuration of function blocks are illustrated in Figure~\ref{fig:function-block-programming}, where motion commands and gripper operations are explicitly defined.

\begin{figure}[htbp]
    \centering
    \includegraphics[width=0.85\textwidth]{figures/function_block_programming.png}
    \caption{Detailed function-block configuration for manual motion and gripper sequencing in Concept A.}
    \label{fig:function-block-programming}
\end{figure}

As a result, all handling strategies, execution logic, and process decisions depend entirely on operator expertise. No automated planning or validation is performed prior to execution. Feasibility issues, such as reachability constraints, are identified only at runtime, which may lead to unreachable targets, process interruptions, or system failures. This lack of pre-execution validation increases setup effort and reduces reliability, particularly in complex bending scenarios.

Furthermore, changes in workpiece geometry during the bending process are not automatically considered. The operator must manually adapt the program to account for geometric changes, which requires additional effort and expertise. For operations such as opposite-side handling or sheet flipping, the operator must explicitly teach the robot the required motions at specific stages. Consequently, the programming effort increases significantly, especially for multi-stage bending processes.

From a system integration perspective, Concept A can be implemented within the drag\&bot environment using function blocks for robot motion, gripper control, and execution sequencing. However, it does not provide native integration with higher-level automation frameworks such as AnyRobot, and \ac{tcp} definitions must be configured manually.

The concept is relatively easy to implement and does not require complex infrastructure or advanced planning algorithms. However, this simplicity comes at the cost of functionality, as it does not support automatic waypoint generation, regrip planning, geometry-aware adaptation, or integrated validation mechanisms. As a result, Concept A does not address the automation requirements identified in the state-of-the-art analysis.

\phantomsection\label{sec:concept-a-system-structure}
\noindent\textbf{System structure.}

The system structure of Concept A consists of two main layers: a manual workflow construction layer and an execution layer. In the first layer, the operator defines the complete process sequence by specifying robot motions, gripper actions, and task order using function blocks within the programming environment.

In the second layer, the execution environment interprets and executes the manually defined sequence. No intermediate planning layer exists for automatic trajectory generation, geometric reasoning, or constraint evaluation. As a result, the system relies entirely on operator-defined logic and does not incorporate adaptive behaviour or automated validation prior to execution.

\phantomsection\label{sec:concept-a-critical-evaluation}
\noindent\textbf{Assessment.}

Concept A is straightforward to implement and provides full transparency and control to the operator. It is suitable for stable and repetitive tasks with minimal variation. However, the limitations of this approach are significant with respect to the objectives of this thesis.

Although programming effort may be reduced through structured tools such as drag\&bot, the approach still requires substantial expertise in robot kinematics, path generation, and process planning. All robot motions, handling steps, and process logic must be defined manually, resulting in high development effort and increased setup time \cite{Pan2012Survey,Siciliano2016Robotics}.

Furthermore, the approach lacks scalability and adaptability. Changes in workpiece geometry or process conditions require manual reprogramming, which limits its applicability in flexible manufacturing environments. The concept does not support automatic grip point calculation, regrip planning, or trajectory generation. The operator must manually define all intermediate positions, gripper actions, and motion sequences, which limits the level of automation.

In addition, integrated validation and decision-making are not supported. Feasibility checks are not performed prior to execution, and infeasible configurations are often detected only at runtime, leading to inefficiencies and potential operational risks.

Although Concept A can be implemented using industrial platforms such as drag\&bot, it remains a purely manual programming approach. It does not support automatic program generation, adaptive planning, or constraint-aware decision-making. Consequently, it does not fulfil the functional and non-functional requirements related to automation, adaptability, and validation defined in this work. The evaluation of this concept is quantified in the weighted sum model presented in Section~\ref{sec:weighted-sum-model-result}.

For these reasons, Concept A is not suitable as a final solution for addressing the identified research gap and achieving the objectives of this thesis.

\section{Concept B -- Automatic Program Generation with Integrated Constraint Validation}
\label{sec:concept-b-validation}

\phantomsection\label{sec:concept-b-methodological-framework}
\noindent\textbf{Method and workflow.}

Unlike Concept A, Concept B introduces automation into the programming workflow. In this approach, robot motion paths and process logic are directly derived from geometric inputs and configuration parameters. Instead of explicitly defining waypoints, the system automatically generates robot trajectories, grip positions, and execution sequences based on defined constraints.

Waypoint generation is performed algorithmically based on the workpiece position, where intermediate points are determined automatically using planning logic. This reduces direct manual teach-in and is expected to reduce programming effort. The user is required to specify only the target output pose. Regripping operations and opposite-side bending are handled through structured logic that combines sequence control with input-output coordination, enabling consistent handling strategies across different process stages. The number of required regrips and the necessity of sheet flipping are determined automatically based on the desired output configuration.

Validation is integrated into the planning process and evaluates all trajectories dynamically through constraint checking, including orientation, reachability, and geometric feasibility. This ensures that only executable configurations are considered prior to motion generation, thereby improving reliability and reducing runtime errors. The program adapts to different geometric dimensions, workpiece placements, and process parameters without requiring modifications to the underlying program logic. This enables efficient handling of varying workpieces without full reprogramming or repeated simulation setup.

In accordance with the defined requirements, Concept B is implemented within the drag\&bot virtual environment, satisfying the software requirement \acs{sr}-01. Communication with the execution system is established through the AnyRobot interface using a WebSocket-based architecture \cite{dragandbot_anyrobot_2025}. In the implemented architecture, this interface separates planning logic from runtime command execution.

Grip planning is performed using a parameterised approach based on workpiece geometry, suction cup properties, and physical constraints. Candidate grip positions are evaluated against edge clearance, spacing constraints, and vacuum holding force requirements \cite{VacuumGripperModeling}. Only physically feasible and stable configurations are selected for further processing, ensuring safe handling conditions prior to trajectory generation. If infeasible configurations are detected during planning, the system automatically initiates regripping sequences or adjusts the workpiece orientation to maintain feasibility.

Opposite-side bending operations are handled through a structured flipping and repositioning workflow. When opposite-side processing is required, the system automatically determines the need for flipping and executes the corresponding handling sequence. All validation steps, including orientation verification, grip feasibility, and reachability assessment, are consistently applied throughout the process \cite{Gupta1998SheetMetalBending}.

Robot trajectories are generated using linear Cartesian motion commands with smooth velocity profiles, ensuring stable handling and predictable execution behaviour \cite{Siciliano2016Robotics}. All motion targets are defined relative to a predefined \ac{tcp}, ensuring consistency across the system and alignment with execution requirements.

Overall, Concept B represents a configuration-driven approach that enables automatic program generation, integrated validation, and adaptive handling of changing workpiece conditions. The system operates deterministically based on defined input parameters, ensuring consistency, repeatability, and reproducibility of generated robot programs.

\phantomsection\label{sec:concept-b-system-structure}
\noindent\textbf{System structure.}

The system architecture of Concept B consists of five functional layers. The input and configuration layer collects process parameters and geometric data. The evaluation layer applies constraint checks, including grip feasibility, edge clearance, and workspace limitations.

The planning layer determines the required process sequence, including regripping and orientation changes, based on reachability and feasibility conditions. The trajectory generation layer produces executable robot motions, while the validation layer ensures that all generated poses are feasible prior to execution.

These layers are connected to the drag\&bot runtime environment through the AnyRobot interface, enabling direct execution of generated programs. The separation between configuration and logic allows the system to adapt to new geometries without modifying core algorithms, thereby supporting scalability and maintainability.

\phantomsection\label{sec:concept-b-critical-evaluation}
\noindent\textbf{Assessment.}

Concept B directly addresses the research gap identified in Section~\ref{sec:research-gap-motivation} by integrating automatic program generation, constraint-aware validation, and adaptive handling within a unified framework. This is intended to reduce programming and reprogramming effort while improving efficiency.

Compared to manual programming approaches, the concept reduces engineering effort by eliminating explicit waypoint definition and manual sequence design. This supports functional requirements such as \acs{fr}-00, \acs{fr}-03, \acs{fr}-05, and \acs{fr}-07, while the configuration-driven architecture satisfies \acs{nfr}-02 by enabling adaptation to new part geometries without modifying source code. The concept also addresses \acs{nfr}-03, \acs{nfr}-04, and \acs{nfr}-05 through structured validation and deterministic execution behaviour.

The system operates within the drag\&bot runtime environment via the AnyRobot interface, satisfying \acs{sr}-01 and \acs{sr}-02. All motion targets are defined relative to the predefined \ac{tcp}, ensuring consistency with execution requirements.

However, the concept operates under defined assumptions, including simplified workpiece geometry and constrained process conditions. Validation has been performed in a virtual simulation environment. Integration with physical hardware and advanced capabilities such as collision detection are identified as areas for future work.

\section{Concept C -- CAD-Based Offline Programming with Simulation}
\label{sec:concept-c-cad-olp-simulation}

\phantomsection\label{sec:concept-c-methodological-framework}
\noindent\textbf{Method and workflow.}

Concept C follows a \acs{cad}-based offline programming (\acs{olp}) approach in which robot programs are generated and validated within a simulation environment prior to execution. This concept relies on a complete geometric model of the robot cell, including the robot, tooling, press brake, and workpiece.

In this approach, robot trajectories, grip positions, and process sequences are defined and evaluated within a virtual environment based on \acs{cad} models of the workpiece and production setup. Standard formats such as \ac{urdf} are typically used to represent robot and environment models. Motion planning and reachability analysis are performed in advance, without direct interaction with the physical robot, and the generated programs are subsequently transferred to the robot controller for execution.

Regripping and opposite-side bending operations are handled within the simulation workflow by defining motion sequences based on the digital model. These operations can be adapted dynamically by updating the \acs{cad} model when changes in geometry or process conditions occur. However, such modifications require updates to the model and repeated simulation cycles.

A key advantage of this approach is the ability to perform comprehensive pre-execution validation. Offline programming and simulation allow robot programs to be tested in a virtual environment before deployment \cite{Pan2012Survey}. Virtual commissioning supports earlier detection of system inconsistencies and reduces commissioning effort \cite{Lechler2019VirtualCommissioning}. Industrial OLP tools such as ABB RobotStudio, KUKA.Sim, and FANUC ROBOGUIDE implement similar methodologies and are widely used in structured production environments \cite{Pan2012Survey}. These systems rely on accurate geometric and kinematic models, including correct \ac{tcp} definitions, to ensure consistency between simulation and execution.

Higher levels of automation can also be achieved in research-oriented \ac{ros}-based planning frameworks. \ac{ros} provides a software infrastructure for robotic system integration \cite{quigley2009ros}. MoveIt supports motion planning and related manipulation-planning functionality within such frameworks \cite{Coleman2014MoveIt}. Unity-based interfaces can be used for simulation or visualisation connectivity with \ac{ros}~2 systems \cite{UnityROS2Docs}. Perception and localisation stacks such as \ac{slam} can further extend robot-system awareness where mapping is required \cite{Cadena2016SLAM}. However, these architectures are outside the implementation scope of this thesis and are considered here only as alternative concept directions.

Most importantly, \acs{cad}-based \acs{olp} systems and \acs{ros}--Unity architectures do not provide direct compatibility with the required execution environment defined in this thesis. They do not integrate with the drag\&bot platform specified in \acs{sr}-01, nor do they support the WebSocket-based AnyRobot communication interface defined in \acs{sr}-02. Therefore, although Concept C is capable of achieving a high level of automation within its own framework, it does not satisfy the required software platform and integration constraints.

\phantomsection\label{sec:concept-c-system-structure}
\noindent\textbf{System structure.}

The system structure of Concept C follows a multi-layer architecture. The \acs{cad} modelling layer provides digital representations of the robot, press brake, tooling, and workpiece. These models form the basis of the digital twin and must accurately represent the physical system, including geometric dimensions and \ac{tcp} configurations.

The offline programming and simulation layer uses these models to perform trajectory planning and reachability analysis. Validation prior to execution is achieved using kinematic solvers and simulation tools. In ROS-based implementations, this layer can also support automated trajectory generation, inverse kinematics, and constraint-aware motion planning.

The communication and integration layer is responsible for transferring generated robot programs from the simulation environment to the execution system. The execution layer consists of the robot controller, which executes the generated program on the physical system.

The overall architecture depends strongly on the accuracy of the digital model. Deviations between the virtual and physical environments may lead to execution errors that require manual correction during commissioning \cite{Siciliano2016Robotics,Pan2012Survey}. Although ROS--Unity-based extensions provide additional capabilities, they operate as separate environments and require custom interfaces for communication with industrial robot controllers. As a result, the system remains loosely coupled and lacks direct integration with the target execution platform defined in this thesis.

\phantomsection\label{sec:concept-c-critical-evaluation}
\noindent\textbf{Assessment.}

Concept C provides strong advantages in structured industrial environments, particularly where accurate digital models of the robot cell are available. Simulation-based validation enables early detection of collisions, unreachable poses, and process inconsistencies, thereby reducing commissioning effort and improving operational reliability. These characteristics make \acs{cad}-based offline programming a widely adopted approach in industrial robotics.

With the integration of \acs{ros}-based planning frameworks and Unity-based simulation, Concept C can achieve a high level of automation. Automated trajectory generation, inverse kinematics, and constraint-aware motion planning can be performed within the \acs{ros}/MoveIt planning framework \cite{quigley2009ros,Coleman2014MoveIt}, while Unity-based environments can be used as visualisation and simulation interfaces connected to \acs{ros}~2 systems \cite{UnityROS2Docs}.

However, several limitations exist within the context of this thesis. First, the approach depends on accurate and continuously updated \acs{cad} models of the robot cell, including tooling, fixtures, and workpieces. Second, both industrial \acs{olp} platforms and \acs{ros}-based frameworks require specialised expertise and additional development effort for implementation, including \acs{cad} integration and kinematic modelling.

Most importantly, Concept C does not satisfy the defined software platform and tool requirements. The approach depends on external simulation and programming environments that operate independently from the drag\&bot runtime environment specified in \acs{sr}-01. Furthermore, it does not support the WebSocket-based AnyRobot communication interface required in \acs{sr}-02.

As a result, although Concept C enables a high level of automation within its own framework, it cannot be integrated into the required system architecture. This incompatibility represents a fundamental constraint. Therefore, the rejection of Concept C is not based on its technical capability, but on its inability to satisfy the mandatory software requirements. Since \acs{sr}-01 and \acs{sr}-02 are non-negotiable constraints defined by the target industrial environment, Concept C cannot be considered a feasible solution within the scope of this thesis.

\section{Concept Decision Using the Weighted Sum Model}
\label{sec:concept-decision-wsm}
\phantomsection\label{sec:wsm-methodology}

The concept selection in this work is performed using the \ac{wsm}, a structured multi-criteria decision-making method widely used in engineering design. The \ac{wsm} enables quantitative comparison of alternative concepts by evaluating them against a defined set of criteria derived from the system requirements.

Each evaluation criterion is assigned a weighting factor based on its relative importance in addressing the research objectives. The concepts are then evaluated against each criterion using a consistent scoring scale from 1 to 5, where 1 indicates minimal or no satisfaction and 5 indicates a high level of satisfaction. The overall score for each concept is obtained by multiplying the assigned weight with the corresponding score and summing the results across all criteria.

This method ensures that the concept selection process remains transparent, systematic, and aligned with the functional, non-functional, and system-level requirements defined in Chapter~\ref{ch:system-concept-methodology}. It also reduces subjectivity by providing a structured framework for comparing alternative solution approaches.

For the scoring interpretation, a score of 1 indicates that the concept does not satisfy the criterion or satisfies it only minimally. A score of 2 indicates weak fulfilment with major limitations. A score of 3 indicates partial fulfilment under additional effort or constraints. A score of 4 indicates good fulfilment within the scope of this thesis. A score of 5 indicates complete fulfilment without major remaining limitations. The scores are therefore not experimental measurements, but engineering decision scores based on requirement fulfilment, implementation constraints, platform compatibility, expected programming effort, and the limitations identified in the concept descriptions.


\phantomsection\label{sec:evaluation-criteria-weights}

The evaluation criteria are derived directly from the functional requirements (\acs{fr}-00 to \acs{fr}-07), non-functional requirements (\acs{nfr}-01 to \acs{nfr}-05), and software platform requirements (\acs{sr}-01 to \acs{sr}-03) defined in Chapter~\ref{ch:system-concept-methodology}. The assigned weight for each criterion reflects its relative importance with respect to the identified research gap and overall system objectives.

\begin{enumerate}
\item \textbf{Programming effort reduction (20\%):} prioritises concepts that minimise manual waypoint definition and reduce reprogramming effort.
\item \textbf{Automated regrip and opposite-side handling (15\%):} evaluates whether complex handling operations can be generated automatically rather than manually sequenced. Robotic sheet-metal bending requires coordinated bending-sequence, grasp, and repositioning planning \cite{Gupta1998SheetMetalBending}. Repositioning and regrip timing are important planning aspects in robot-assisted bending \cite{Aomura2002RoboticBending}.
\item \textbf{Pre-execution validation and safety (15\%):} assesses reachability, orientation feasibility, handling constraints, replanning, and safe termination.
\item \textbf{Adaptability (10\%):} favours configuration-driven adaptation without changes to the underlying program logic.
\item \textbf{Platform compatibility (15\%):} checks compliance with drag\&bot and AnyRobot constraints, especially \acs{sr}-01 and \acs{sr}-02.
\item \textbf{Operator usability (10\%):} rewards approaches that reduce the need for specialised programming knowledge during operation.
\item \textbf{Level of automation (15\%):} evaluates automatic generation of trajectories, handling decisions, and process sequencing.
\end{enumerate}

\phantomsection\label{sec:analysis-concept-decision}

The \ac{wsm} results confirm the qualitative comparison of the three concepts. Concept B achieves the highest overall score (4,00), followed by Concept C (3,20) and Concept A (1,25). Concept B performs consistently well across all evaluation criteria, particularly in programming effort reduction, automated handling, validation capability, adaptability, and platform compatibility. This balanced performance makes it the most suitable candidate within the defined system constraints.

The low score of Concept A results from its dependence on manual programming. Although the drag\&bot function-block environment can structure the workflow and improve transparency, the operator must still define waypoints, gripper actions, regrip motions, and execution sequences manually. Therefore, Concept A receives low scores for programming effort reduction, level of automation, adaptability, and pre-execution validation. It is not scored higher because it does not generate robot programs automatically and does not provide integrated geometry-aware planning.

Concept B receives the highest score because it directly addresses the central requirements of this thesis. Robot motions, grip points, regrip decisions, and execution sequences are generated from configuration and geometric input rather than manually taught waypoints. It also satisfies the required drag\&bot and AnyRobot integration constraints. However, Concept B is generally scored as 4 rather than 5 because the developed system is evaluated only in simulation and remains limited by predefined configuration data, simplified geometry assumptions, and the absence of physical robot validation.

Concept C receives intermediate-to-high scores for automation and validation because \acs{cad}-based offline programming and simulation environments can support trajectory planning, reachability analysis, and collision checking. However, its score is reduced because it requires \acs{cad} model preparation, simulation setup, specialised engineering knowledge, and repeated model updates when the workpiece or cell configuration changes. Most importantly, Concept C receives the lowest score for platform compatibility because it does not satisfy the mandatory drag\&bot and AnyRobot requirements defined in \acs{sr}-01 and \acs{sr}-02. Therefore, it is technically capable but not suitable for the selected implementation environment.

This distinction is important for the final decision. Concept C is not rejected because it lacks technical capability, but because its main strengths lie in external \acs{cad}, \acs{olp}, or \acs{ros}-based environments that do not satisfy the mandatory platform constraints of this thesis.

Concept A achieves the lowest score, as it relies on manual programming and does not significantly reduce engineering effort. While it is simple to implement and compatible with existing tools, it does not address the primary objective of this thesis, which is the automation of robot program generation.

Based on the weighted evaluation and the defined requirement constraints, Concept B is selected for implementation. The decision is not based solely on achieving the highest score, but on providing the most effective balance between automation, adaptability, validation capability, and full compatibility with the defined software platform.

The implementation of Concept B is presented in Chapter~\ref{ch:implementation}.
